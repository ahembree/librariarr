# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It states the rules and where things live; the reasoning and incident history behind each rule live in code comments and git history (`git log -S '<symbol>'`).

## Project Overview

Librariarr is a media library management webapp for Plex, Jellyfin, and Emby servers. It signs in with Plex OAuth (or local password / SSO), syncs media metadata from connected servers, provides filterable library browsing, and includes a lifecycle rule engine for automated media management (including deletion through Sonarr/Radarr/Lidarr).

**Librariarr is a single-user (single-admin) application.** Setup permits exactly one admin account (`AppSettings.userId @unique`, setup gate in `src/app/api/auth/setup/route.ts`). Do not add multi-tenant defensiveness — see "Single-user model".

### Testing

Vitest 4 against a real PostgreSQL test database (`librariarr_test`, auto-created by global setup).

- `tests/setup/` — global setup, test DB client, session mocks, data factories. `tests/unit/` — pure logic. `tests/unit/hooks/` — React hooks: each file starts with `// @vitest-environment happy-dom` and uses `renderHook`/`act` from `@testing-library/react` (the rest of the suite runs in `node`). `tests/integration/` — route handlers against the real DB with external services mocked.
- Every integration test mocks `@/lib/db` (test Prisma client) and `@/lib/logger`. External services (Plex, Sonarr, Radarr, Lidarr, …) are mocked with `vi.mock()`. Route imports come after all `vi.mock()` calls.
- Auth: `setMockSession()` / `clearMockSession()` (`tests/setup/mock-session.ts`). The mock mirrors the real module, including the API-key branch (`rotateSession` throws, `isSessionValid` is true), `authenticatedAt` stamping, and a session object that answers `in`, spreads and `delete` like the real one.
- `cleanDatabase()` (`tests/setup/test-db.ts`) truncates every table in `public` except `_prisma_migrations` (read from `pg_tables`) and drops the cached library listings (`media-list:`). A test that writes rows directly and then lists again must call `invalidateMediaCaches()`, as the app's writers do.
- Constructor mocks use the `function()` keyword, not arrow functions (Vitest 4). Use `vi.hoisted()` for variables referenced inside `vi.mock()` factories.
- Call handlers directly: `callRoute(GET, opts)` / `callRouteWithParams(POST, { id }, opts)`; `expectJson<T>(response, status)` parses and asserts the status.
- Factories (`tests/setup/test-helpers.ts`): `createTestUser`, `createTestServer`, `createTestLibrary`, `createTestMediaItem`, `createTestRuleSet`, `createTestSonarrInstance`, `createTestRadarrInstance`, `createTestLidarrInstance`, `createTestSeerrInstance`, `createTestExternalId`, `createTestLogEntry`, `createTestApiKey` (returns `{ key, row }`).
- Test files are type-checked by `pnpm build` (tsconfig includes `tests/`): a test that runs but fails `tsc` breaks the build.
- Config: sequential (`pool: "forks"`, `fileParallelism: false`), test timeout 15 s, hook timeout 30 s. `vitest.config.ts` points `BACKUP_DIR`, `IMAGE_CACHE_DIR` and `LOG_ARCHIVE_DIR` at a per-run temp dir (CI cannot write the `/config` defaults); `tests/unit/setup/runtime-dirs.test.ts` fails if any is unset or under `/config`. A new env-overridable `/config` path goes in both. A test needing its own directory sets the variable before the module loads.
- **Coverage requirement:** scope is `src/lib/**/*.ts` and `src/app/api/**/*.ts`. Every new or modified file there must have tests: each new route handler under `src/app/api/` gets an integration test in `tests/integration/`, each new `src/lib` module a unit test in `tests/unit/`. A fully covered lib does not make its route covered — bugs hide in the seams (session, validation, rate limiting, DB writes).

### Browser E2E (Playwright)

Real-browser tests in `e2e/*.spec.ts` (Playwright, separate from Vitest; config `playwright.config.ts`).

- **Run (recommended):** `pnpm e2e:docker` — `docker-compose.e2e.yml`: Postgres + the real production image (built from `Dockerfile`) + the official `mcr.microsoft.com/playwright` image (browsers pre-baked; it sets `E2E_BASE_URL`, so the config skips its own web server). **Host:** `pnpm build && pnpm e2e:install && pnpm e2e` (needs egress to `cdn.playwright.dev`). **CI:** `.github/workflows/e2e.yml` on PRs and `workflow_dispatch`.

- **Seeding:** `e2e/seed.ts` writes directly via `pg` (`seedUnreachableServer`, `seedGroupedLibraries`, `storeDashboardLayout`, …), idempotent and cleaned before and after so every other spec keeps an empty DB. Writing past the app leaves its in-memory caches stale, so a spec that reads a cached answer calls `dropAppCaches(page.request)` first (seeded specs do it in `beforeEach`).

- Specs, one per area: `navigation`, `sidebar`, `search-palette`, `settings`, `library`, `library-filters`, `library-refresh`, `lifecycle`, `lifecycle-refresh`, `tools`, `logs`, `logout`, `dashboard`, `dashboard-server-render`, `dashboard-refresh`, `dashboard-custom-cards`, `dashboard-insights`, `mobile`, `mobile-layout` (every page at 375px and 320px), `api-keys`, `seeded-library`, `seeded-detail-pages`, `security-headers`, `realtime-push`, `onboarding`, `ai-chat`, `login-restore`, `reauth-popup`, `unauthenticated`. Add new user-journey specs here. `realtime-push.spec` is the only check that runs the job worker, the realtime manager and the routes as the separate module copies a production build gives them; `security-headers.spec` is the only one that shows which `next.config.ts` header entry wins for a path.
- **Excluded from the production image:** `@playwright/test` is a devDependency; `.dockerignore` excludes `e2e/`, `playwright.config.ts` and reports; `tsconfig`/`eslint` exclude `e2e/`. The compose Playwright image tag `${PLAYWRIGHT_VERSION}` is derived from the `@playwright/test` version in `pnpm-lock.yaml` by `scripts/playwright-version.mjs` (set by `pnpm e2e:docker`/`e2e:docker:down` and `e2e.yml`); a bare `docker compose -f docker-compose.e2e.yml …` refuses to start without it.

## Architecture

**Stack:** Next.js 16 (App Router) · React 19 · TypeScript · PostgreSQL 18 · Prisma 7 · Tailwind CSS v4 · shadcn/ui · Docker

### Route Structure

- `src/app/(authenticated)/` — protected pages; `layout.tsx` validates the session and redirects. Dashboard (`/`), System Logs (`/system/logs`), Settings, Library, Lifecycle and Tools (below).
- `src/app/login/`, `src/app/onboarding/` — public. After sign-in the login page goes to `/` or `/onboarding` by the response's `hasServers` (`userHasServers`, `src/lib/api/has-servers.ts`, returned by `POST /api/auth/local/login` and both `plex/token` branches).
- `src/app/api/` — API routes; all require a session except the auth endpoints. `src/app/api/v1/` is the public API (see "Public API").

**Settings (`/settings`)**

- `page.tsx` holds the state and handlers; the 8 tabs in `settings/tabs/` render from props. Exception: the Integrations tab keeps its own form state through one `useIntegrationInstances(behavior, { instances, refresh })` per type (`settings/use-integration-instances.ts`; pure helpers `changesConnection`, `editRequestBody`, `testConnectionBody` in `settings/integration-instances.ts`) rendered by `IntegrationInstanceSection`, and stays mounted once opened (`forceMount`). Shared types in `settings/types.ts`. `MediaServerConnectionFields` is the server form both onboarding and Add Server render.
- Each tab's code loads on demand through `lazySettingsTab` (`settings/lazy-tab.tsx`), listed first in that tab's `TAB_CODE.<tab>.load`; a new tab needs a `TAB_CODE` entry. Each tab renders once its own data is in (`loadedTabs`), the open tab's requests issued first; a new fetcher goes in the list of every tab that renders its data.
- The open tab IS the URL hash, read through `useHashTab(validTabs, fallback)` (`src/hooks/use-hash-tab.ts` over `src/lib/url-hash.ts`, written with `replaceUrlHash`). Never read the hash once in a `useState` initializer — on a client-side navigation that is the previous page's hash.
- The opening reads arrive in one request: fetchers read through `bundleOf(bundleRef).get(path)` (`src/lib/settings/request-bundle.ts`), and the first read of each path in `SETTINGS_BUNDLE_PATHS` (`src/lib/settings/settings-bundle-paths.ts`) is answered by `GET /api/settings/bundle?paths=…`, which runs each route's own GET (`{ parts: { [path]: { status, body } } }`) under one session check (`withSharedSession`, `src/lib/auth/shared-session.ts`), creating the settings row first. Later reads go to the route itself. **A new bundled fetcher's GET must be callable with no arguments** (`withSession(async (session) => …)`, or an optional request) and be added to both `SETTINGS_BUNDLE_PATHS` and the bundle route's `HANDLERS`. The SSO and API-key sections' first reads are preloaded the same way (`preloadAuthSections` via `createPreloadedReads`, `settings/preloaded-reads.ts`, answered once).
- The System tab loads only when opened (`/api/system/info?updateCheck=false`, image-cache stats, changelog); its update status and dot come from `/api/system/update-check` at low priority. Without `updateCheck=false`, `/api/system/info` (and the v1 mirror) include `updateInfo`.

**What's new dialog** — `WhatsNewDialog` (`src/components/whats-new-dialog.tsx`, mounted in `AuthenticatedShell`) shows every release note newer than `AppSettings.lastSeenVersion` up to the running version (`GET /api/settings/whats-new`; `selectWhatsNew` and the release-please parser `parseReleaseSections` in `src/lib/version/release-notes.ts`; `ReleaseNoteSections` renders for both it and the System tab). It reads `fetchReleaseNotes()` (100 releases), never the 10-item changelog; `truncated` flags older notes past that page. It opens only once the running version's release is listed. Closing `PUT`s the shown version under `FOR UPDATE`, never stepping it back. Setup stores `installedVersion()`; a restore keeps the newer of the file's and the in-use value (`keepSeenReleaseNotes`).

**Library** — `/library/movies`, `/library/series` (with `/seasons` and `/episodes`), `/library/music`. Detail pages:

- All seven detail pages load through `useMediaDetailRecord(id, { mediaType, plays, integrations?, children?, playLinks?, tickOn?, refetchOnTick? })` (`src/hooks/use-media-detail-record.ts`; with `useBackOverride`, `useDetailChildren`, and `DetailPageStates`/`RatingChips`/`genreChips` in `src/components/media-detail-parts.tsx`). It calls `prefetchMediaDetail` beside the record fetch once per id (first play-history page via `mediaPlaysUrl`, `/arr-info`, `/seerr-info`, the child list) and ignores a `sync:completed` whose `libraryTypes` leave out the page's type. Artist and album pages pass `integrations: false`.
- Show, season, artist and album pages read their child list by the record's id (`?itemId=` on `series/seasons`, `series`, `music/albums`, `music`; scope resolved by `loadDetailScope` in `src/lib/api/detail-scope.ts`, 404 when not the user's or not of the list's type), so `detailChildrenUrl` starts with the record.
- **`detailPrefetch`** (`src/lib/media/detail-prefetch.ts`): a 30 s store of GET answers keyed by URL, each handed out once by `take`, errors never kept; `peek` reads without consuming (the hover popover), so the record is still there for the click. Everything that reads by id (`PlayHistory`, `IntegrationsSection`, detail pages, `MediaDetailContent`, `useMediaDetailPanel`) goes through `detailPrefetch.fetch`. Library cards (`MediaCard`'s `prefetchMediaId`) and `MediaTable` rows warm the record on intent (`intentHandlers`, `src/lib/intent-prefetch.ts`: pointer resting `INTENT_DELAY_MS` 120 ms, mouse/pen press or focus — never a touch press). Keep URL builders shared so both sides hit the same key. Records and play pages are dropped with the list cache on every media-changing event.
- **Play history**: `PlayHistory` (`src/components/play-history.tsx`) renders per-play rows (user / date-time / episode). Show and season pages render it as a full-width section over `GET /api/media/series/watch-history`. The episode page, `/library/movies/[id]` and `/library/music/track/[id]` pass it through `MediaDetailContent`'s `historySection` slot (`variant="card"`; movie and track with `mediaItemId singleItem` over `GET /api/media/[id]/plays`), which replaces the built-in per-user aggregate card and skips its live `/api/media/[id]/history` fetch (`hasHistorySection`). `MediaDetailSidePanel` fills the same slot (series identity + season/episode for an episode, its own id otherwise). `singleItem` drops the title line; `PlayRow` links out only for a SERIES row.
- `/api/media/[id]/history` (live per-user aggregate for one item, from the server) and `/api/media/[id]/plays` (stored per-play rows) are deliberate siblings, not substitutes. The two play routes share `src/lib/media/play-history.ts` (`PLAY_HISTORY_SELECT`, `serializePlayRow`, `fetchPlayHistory`, `parsePlayHistoryPaging`) and differ ONLY in how they resolve in-scope items — add columns there, never to one route. `series/watch-history` matches on `seriesKey` (prefers a `seriesKey` param; legacy `parentTitle` matched case/space-insensitively), resolves in-scope episode ids first, includes every user's plays, and does **not** apply dedup (a play belongs to the copy that was played).
- Play lists page 5 at a time (`PAGE_SIZE`) through the shared `src/components/pagination-controls.tsx` (also used by `/library/history`), **centred** (the fixed `BackToTop` button covers the right corner). Last/Next use `totalCount`, not `hasMore`; `multiServer` comes from servers seen across every loaded page in the scope.
- `detailLoaded`: the movie, episode and track pages and the side panel (`useMediaDetailPanel`'s `panelProps.detailLoaded`) already load the full `/api/media/[id]` record, so `MediaDetailContent` reads streams and credits from `item` instead of fetching again. If the panel's request fails with a seed on screen, the flag turns false and the content fetches the record itself.
- The detail hero paints the grid card's poster under the full-size one when this tab already loaded it (`posterPlaceholderFor`, `src/lib/loaded-images.ts`, fed by `FadeImage`'s `onLoad`; never on a direct visit). The side panel's 80px poster requests `CACHE_WIDTH_GRID`.

**Lifecycle** — `/lifecycle/rules` (Movies/Series/Music tabs), `/lifecycle/matches`, `/lifecycle/pending`, `/lifecycle/exceptions`.

**Tools** — `/tools/streams` (Stream Manager: active sessions, maintenance mode, transcode manager, blackout schedules), `/tools/preroll` (presets, schedules, combine modes), `/tools/trash` (TRaSH Guide Sync), `/tools/ai` (AI Analysis).

**Notable API areas**

- `api/tools/sessions/` — active sessions, SSE stream, termination, artwork proxy. Every reader shares one poll of the media servers through `readSessionsSnapshot` (`snapshot.ts`, pinned to `globalThis`): a poll begun within `SESSIONS_SHARE_WINDOW_MS` (4 s) is reused unless `noteSessionsChanged` ran since it began (realtime `session-changed`/`server-status`, `server:changed`, a termination); a poll that fails outright is not kept.
- `api/tools/{maintenance,transcode-manager,blackout,preroll}/` — maintenance toggle with delay, transcode criteria, blackout CRUD (one-time and recurring), preroll presets/schedules/path validation.
- `api/integrations/{radarr,sonarr,lidarr,seerr,tracearr}/` — every route file is one line, `export const { GET, POST } = builder(CONFIG)`, built from `src/lib/integrations/instance-routes.ts` (configs `RADARR` … `TRACEARR`, `INTEGRATIONS`; builders `instanceCollectionRoutes`, `instanceItemRoutes`, `instanceTestConnectionRoutes`, `instanceTestRoutes`, `instanceRecycleBinRoutes`, `instanceMetadataRoutes`). Builders declare each handler as `const METHOD = withSession(…)` (`tests/unit/auth/reauth-callers.test.ts` follows the export into the builder). A blank key or `MASKED_VALUE` keeps the stored key for all five; a failed test answers `Failed to connect to <Label>`. An add/edit/delete drops the instance's cached metadata and, for Arr apps, calls `invalidateArrMetadataCache()`. `[id]/metadata` (rule editor / Query dropdown values, no per-item map) is cached 60 s per instance under `integration-metadata:` (`readInstanceMetadata`: single-flight, failures answered but not kept, gzipped). `GET /api/integrations/instances` returns all five instance lists in one request; `?withMetadata=1` adds `seerrUsers`.
- `api/integrations/tracearr/` — also `[id]/servers` (the Tracearr-side server list for the per-server mapping) and `status` (see "Watch history & Tracearr").
- `api/tools/trash/` — `instances`, `catalog`, `profiles` (includes `instanceFormatNames`), `status`, `assignments` (the consent gate), `sync` (dry-run/diff or apply). Resource types: `CUSTOM_FORMAT`, `QUALITY_PROFILE`, `QUALITY_DEFINITION`, `NAMING`, `PROFILE_CF` (guide CF scores overlaid onto any quality profile, keyed by profile name).
- `api/settings/api-keys/`, `api/auth/reauth/*` — see "Authentication, sessions and step-up" and "Public API".
- `api/v1/` — see "Public API".

### Key Libraries

**Core**

- `src/lib/db.ts` — Prisma singleton. Import `@/lib/db`, NOT `@/lib/prisma`.
- `src/lib/auth/` — sessions, `withSession`, step-up; see "Authentication, sessions and step-up". `src/lib/api-keys/` — see "Public API".
- `src/lib/validation.ts` — every Zod schema + `validateRequest` (see "API Request Validation").
- `src/lib/api/sanitize.ts` — `sanitize()`, `sanitizeErrorDetail()` (see "API Response Security").
- `src/lib/api/json-response.ts` — `jsonResponse(request, body, init?)`: `NextResponse.json` with gzip (**Next.js 16 does not compress Route Handler responses**). Use it for any route that can return more than a few KB. Bodies under 4 KB or requests without `Accept-Encoding: gzip` get plain JSON (integration tests read them unchanged). Lists over 1,000 rows (up to three levels deep) serialise a slice at a time (`stringifyYielding`, byte-identical to `JSON.stringify`); the flat list routes shape rows with `mapInSlices`. Both yield to the event loop.
- `src/lib/progress/stream.ts` — `progressStreamResponse(run, { request })`, the NDJSON progress protocol (query, query actions, rule preview, AI chat, history sync): gzip with a sync flush per line, the result written through `writeJsonYielding`, the run aborted by the request signal. A new streaming route passes `request`.
- `src/lib/cache/` — `appCache`, `invalidateMediaCaches()`; see "In-Memory Cache".
- `src/lib/dedup/` — see "Multi-Server Dedup". `src/lib/filters/build-where.ts` — see "Filter Utilities".
- `src/lib/url-normalize.ts` — `stripTrailingSlashes(url)` (client-safe), the one trailing-slash rule: instance URLs stored and compared without them, issuers matched ignoring them.
- `src/lib/concurrency.ts` — `mapWithConcurrency` (pool, fails fast), `settleWithConcurrency` (never stops).
- `src/lib/logger.ts` — `logger` (backend), `apiLogger` (API), `dbLogger` (database); console + `LogEntry` table; debug needs `LOG_DEBUG=true`. `GET /api/system/logs?count=false` skips the total (the page's 5 s refresh counts every 6th tick, `COUNT_EVERY_TICKS`); `/api/system/logs/sources` uses a recursive-CTE loose index scan.
- `src/lib/rate-limit/rate-limiter.ts` — see "Rate limiting".
- `src/lib/backup/backup-service.ts` — see "Backup & Restore". `src/lib/theme/accent-colors.ts` — accent presets (OKLCH). `src/lib/discord/client.ts` — see "Notifications".

**Media servers**

- `src/lib/plex/` — OAuth flow and API client. `getDetailedWatchHistory` reads `/accounts` strictly and throws on failure; `getAccounts()` stays lenient (per-item panel, excluded-users picker). History pages through `forEachHistoryPage`, which ends on a short page only when the container reports no `totalSize` or it has been reached — never assume the requested page size was honoured.
- `src/lib/media-server/jellyfin-base.ts` — `getDetailedWatchHistory` scopes to `IncludeItemTypes=Movie,Episode,Audio`, walks `USER_HISTORY_CONCURRENCY` (3) users at a time, and **propagates transient per-user failures** (a swallowed one hands the native full replace a partial history); only 401/403/404 skip a user (WARN). `sessionPath` `encodeURIComponent`s the id and refuses `.`/`..`.
- `src/lib/media-server/http-instrumentation.ts` — `instrumentMediaServerClient`, the interceptor chain both clients install: circuit breaker (unless `BYPASS_BREAKER`), timing/debug logging, breaker reset on success, then `configureRetry` last. `normalizeMediaServerUrl` (trailing slashes stripped) is the one base-URL spelling for axios, the breaker key and hand-built URLs.
- `src/lib/media-server/client.ts` — `MediaItemNotFoundError`, `isMediaItemNotFound` (that error or HTTP 404).
- `src/lib/media-server/item-types.ts` — the **non-media container guard** `isMediaItem`/`partitionMediaItems`: collections, box sets and playlists are never stored. It is a deny-list, so an unknown real type keeps syncing. Plex filters server-side (`PlexClient.getLibraryItemsPage` sends `type=1` for movies) so `totalSize` stays consistent with the page. `isItemForLibraryType` makes a library store only its own type (MOVIE→`movie`, SERIES→`episode`, MUSIC→`track`) — needed by the incremental sync, since a new episode makes Plex/Jellyfin emit entries for its season and show too.
- `src/lib/media-server/realtime/` — see "Realtime & events".

**Integrations**

- `src/lib/integrations/http.ts` — **`createIntegrationHttp(appName, baseURL, headers, { timeout })`** (+ `apiKeyHeaders(apiKey)`) is how every integration client gets its axios instance. It registers, in order: trailing-slash strip, request start time, `configureRetry`, then the AxiosError → `IntegrationError` converter. **The retry must be registered before the converter** (axios runs response interceptors in registration order and the retry needs the raw AxiosError). A new client uses this rather than wiring its own interceptors. `tests/unit/integration-clients-retry.test.ts` drives each client's real chain against a local HTTP server.
- `src/lib/http-retry.ts` — `configureRetry`: 3 retries (1/2/3 s). GET/HEAD retry 5xx, timeouts and mid-exchange transport errors; writes retry only a failure that provably preceded sending (`EAI_AGAIN`), since a reset can follow an applied write. An aborted request (`ERR_CANCELED`) is rethrown untouched (never retried, never trips the breaker). `NO_RETRY` (`{ ...NO_RETRY }` in a request config) opts out — every `testConnection` and the rule editor's recycle-bin probe use it. `NO_BREAKER_MARK` keeps a failure from marking the server down (artwork fetches).
- **Bounding dead instances**: `/api/media/[id]/arr-info` and `seerr-info` query enabled instances in parallel, each capped by `withTimeout` (`src/lib/api/bounded.ts`, 10 s). Action loops track `UnreachableInstances` (`src/lib/lifecycle/unreachable-instances.ts`): after a host-level failure the manual/query path fails the remaining items without calling the instance, and the scheduled executor leaves them PENDING. Host-level (`isHostLevelFailure`) = a connection that could not be made (`ECONNREFUSED`/`ENOTFOUND`/`EHOSTUNREACH`/`EAI_AGAIN`…) or a **GET/HEAD** with no response or 502/503/504 after retries — **never a write's timeout or gateway error** (Sonarr's bulk episode-file delete routinely outlives the timeout while healthy). `IntegrationError.method` carries the method. TRaSH sync caches getter promises so a failed read fails every target at once.
- `src/lib/arr/` — Sonarr/Radarr/Lidarr clients (15 s timeout, title validation via `normalizeTitle()`) extending `ArrClientBase` (`arr-client-base.ts`: connection test, tags, quality profiles, languages, media management, bulk tag removal; Lidarr uses `/api/v1`). `instances.ts` (`ARR_FAMILY_FOR_TYPE`, `findArrInstance(s)`, `familyOfArrInstance`) is the one instance lookup by family; `family-data.ts` (`loadArrFamilyData`) reads a family's library into an `ArrDataMap`, instances in parallel.
  - Array query params the Arr apps bind as `int[]` use `paramsSerializer: { indexes: null }`.
  - By-external-id lookups (`getMovieByTmdbId`, `getSeriesByTvdbId`, `getArtistByMusicBrainzId`) return only a record carrying the requested id, never `data[0]` (Lidarr's single answer under a merged id is accepted).
  - An import-list exclusion is added only by the whole-record deletes (`addImportExclusion`/`addImportListExclusion`); the rule editor and Query action bar offer it for those alone (`deletesArrRecord`).
  - `IntegrationError.validationMessages` holds an Arr 400's `errorMessage`s and becomes `detail`. The `[id]/recycle-bin` routes return `externalUrl || url` as `arrUrl`.
  - An execution run shares an `ArrExecutionContext` (`lifecycle/actions.ts`): each instance's family and tag list read once, the instance row re-read per action. An action resolves its Arr record once for its tag step and main step (`ActionArrSession`). Removing a rule set's tags from every record is one bulk-editor request per instance.
  - **Member-scoped file deletes act only on what they can prove.** Sonarr resolves each matched episode by S/E and skips one whose `originallyAvailableAt` is more than two days from Sonarr's `airDate`; a multi-episode file is deleted only when every episode in it matched. Lidarr resolves a track by MBID, then disc+track on the album its title names (title must agree), then exact `trackTitleKey` on that album — never the same title on another album. An action none of whose members resolve throws (FAILED). `ActionOutcome.deletedMemberIds` feeds `computeDeletedBytes` (`src/lib/lifecycle/deleted-bytes.ts`).

### Sync engine (`src/lib/sync/`)

- `sync-server.ts` (`syncMediaServer`) is the full sync. Its one raw `INSERT … ON CONFLICT` (`buildUpsertSql`, shared with the incremental sync via the exported `processBatch`) writes **`playCount` and `lastPlayedAt` with `GREATEST`** (`GREATEST_ON_UPDATE`), never a bare `= EXCLUDED`: both inputs can legitimately read zero for media somebody else watched (admin-account metadata; an empty `WatchHistory` after a source switch), and DELETE rules read these columns. Keep the monotonic guarantee to play state only.
- Watch counts come from the stored history, **per library** (rating keys are unique only within a library): `loadLibraryWatchCountsFromHistory(serverId, libraryId)` for the full sync, `loadWatchCountsFromHistory(serverId, ratingKeys, libraryId)` for the incremental one. Media-server clients have no `getWatchCounts()`.
- Enrichment runs through a pool of `ENRICHMENT_CONCURRENCY` (10) (`settleWithConcurrency`); the next batch enriches while the current one upserts. A TV library's `parentSummary` is one `UPDATE … FROM unnest(…)` per library. The per-250-item heap line only logs (`logHeapAndCollect(…, { collect: false })`); forced `gc()` runs only between pages and libraries.
- **Vanished libraries** (`purgeVanishedLibraries`): full unscoped syncs only, and only when `getLibraries()` returned at least one syncable library. The `Library` delete cascades to items, streams, external ids, watch history, matches and exceptions; each removal logs WARN with the cascaded exception count.
- **Stale items**: purged only when `librarySeenCount >= libraryTotal`, and each candidate is confirmed with the server (`confirmGoneFromLibrary`): deleted only on `isMediaItemNotFound` (Plex's empty-container 200 maps to it), when it now sits in another section/library (`resolveLibraryKey` on Jellyfin/Emby), or when its rating key now names another type or a container. A timeout, 5xx or failed lookup keeps the row. `tests/integration/sync/artwork-cache-scope.test.ts` runs the purges against the real image cache.
- `libraryItemCount` (real media upserted; drives the "server returned nothing, refuse to wipe" guard) and `librarySeenCount` (every row traversed, containers included, compared with the server's total) are **separate counters** — never merge them. Skipped containers still count toward `librarySeenCount`/`processedItems`, and the page offset advances by the raw page size.
- A failed enrichment fetch never upserts the bulk listing item over a stored row: the row is only touched (its old `serverUpdatedAt` forces a retry); a new item is stored with `serverUpdatedAt` NULL.
- **Plex watchlist**: `PlexClient.getWatchlistGuids()` pages plex.tv 100 at a time to `totalSize` and returns `null` — never an empty set — on failure or an incomplete answer. Unknown (`watchlistUnknown`) → each stored flag (from the per-page prefetch) is carried onto the item right before `processBatch` (after `enrichBatch`). Known → one `UPDATE … SET "isWatchlisted" = EXISTS(…)` over the whole library after the page loop (unchanged items skip the upsert).
- `sync-watch-history.ts` places native plays through `ratingKeyResolver`: an ambiguous rating key is placed by the entry's `librarySectionId`, otherwise skipped and logged.
- **Run lifecycle and events**:
  - `sync:started` is emitted once, after the slot is acquired and the disabled-server check passes.
  - Every terminal path calls `settleDataset()` (canonical recompute + `invalidateMediaCaches()`, once, gated on `processedItems > 0 || datasetChanged`) **before** its event; the `finally` is only a backstop. `datasetChanged` covers a purge-only run. A CANCELLED exit (`finishCancelled`) emits `sync:completed` only when something changed, else `sync:failed`; the disabled-server bail emits `sync:failed`.
  - The PENDING → RUNNING update sits inside the `try` and is conditional on `status='PENDING'`.
  - Stop is honoured at every checkpoint, including the watch-history phase through `watchForCancel` (`src/lib/sync/cancel-watch.ts`, polls the flag every 2 s into the importers' `AbortSignal`; Plex and Jellyfin/Emby `getDetailedWatchHistory({ signal })`).
  - **Every `TASK_SYNC_SERVER` enqueue sets `SyncServerPayload.trigger`** in plain words (`"scheduled sync"`, `"manual sync request for this server"`, `POST_DELETE_SYNC_TRIGGER`, …), logged on the "Starting sync … triggered by" line (absent → "an unrecorded caller"). Set it at every new enqueue site.
- **Requested syncs** (`POST /api/servers/[id]/sync` — Sync and Sync All — and `POST /api/sync/by-type` — the library pages' Sync):
  - The route creates the PENDING `SyncJob` itself (`startedAt = requestedAt`; duplicate check and insert under a per-server `pg_advisory_xact_lock`, `sync-request:`), passes its id as `SyncServerPayload.syncJobId`, enqueues at `REQUESTED_SYNC_PRIORITY` (-10) and emits `sync:started`. An enqueue failure closes the row FAILED (500).
  - The run claims the row through `claimSyncJob`: the requested row while PENDING; nothing if CANCELLED; else any unclaimed PENDING row for the server (a jobKey collision dropped the id); else a fresh row (a FAILED requested row is a retry).
  - The sync task's "already running" guard counts **RUNNING only** (and closes a requested row FAILED if it ever skips); the watch-history task and incremental sync still treat a PENDING row as covering them.
  - `enqueueJob` never lets a keyed enqueue make a queued job less urgent (`keepQueuedPriority`, reading `graphile_worker.jobs`).
  - `by-type` enqueues one job per library (`skipWatchHistory: true`) with its own PENDING row each (reused only for the same still-queued job — `queuedSyncJobIds` in `jobs/client.ts`, read from `graphile_worker._private_jobs`), then one `TASK_SYNC_WATCH_HISTORY` per server. A server can therefore hold one RUNNING and several PENDING rows: `POST /api/sync/cancel` ends every PENDING row directly (CANCELLED + `sync:failed`) and flags every RUNNING one; `GET /api/servers` returns the RUNNING job first; the dashboard draws one line per server (`activeSyncPerServer`, `src/lib/sync/active-sync.ts`). `tests/integration/sync/by-type-stop.test.ts`.
  - Priority cannot pre-empt a running job, so `TASK_TRACEARR_BACKFILL` yields between pages when `requestedSyncWaiting` (a PENDING `SyncJob` under an hour old) via `syncTracearrHistory`'s `yieldTo` — a resumable `"stopped"`, deliberately not an `AbortSignal` (an abort mid-request reads as `"errored"`).
  - **"Is this sync mine" compares time**, never status or a remembered job id: the route returns `requestedAt` (server clock, before the enqueue) and `isSyncRequestSettled` (`src/lib/sync/sync-request.ts`) settles a request only on a terminal job whose `startedAt` is at or after it. Settings drops settled requests in `fetchServers`, refetches once when the POST returns, arms its 15 s fallback poll on a pending request, and scopes every release to the request's own sequence id.
- `sync-progress.ts` throttles `sync:progress` 2 s per server and clears the throttle at sync end. `sync-completed-meta.ts` (`syncCompletedMeta`) adds a scope to `sync:completed`: `libraryTypes` (sorted types written or removed; absent when unknown) and `incremental: true` from the realtime incremental sync. `latest-outcome.ts` picks the sync indicator's idle state.
- **Incremental sync** (`sync-incremental.ts`, `syncMediaServerItems()`, `TASK_SYNC_INCREMENTAL`): fetches and upserts only the changed rating keys (`processBatch`) and deletes removed ones (a `getItemMetadata` 404 is a deletion; a transient error returns `"fell-back"` and the task enqueues a full sync — never a guessed delete). It skips the server-wide play-count/history scans and stale detection. Because the upsert overwrites every column it writes, it must:
  1. read `playCount`/`lastPlayedAt` from stored history (`loadWatchCountsFromHistory`), maxed against metadata;
  2. carry `isWatchlisted` forward from the stored row **on Plex only** (Jellyfin/Emby read `IsFavorite` from the item);
  3. fetch each show's metadata (series-level GUIDs) **before any write** and fall back on failure — a missing `showGuidsMap` entry clears the episode's external ids.
  Mapping failures are per item: an unplaceable id is counted `unresolved`, logged and dropped. `libByKey` loads disabled libraries too (their items are recognised and skipped); deletes are scoped `AND l."enabled"=true`; `existingByRatingKey` maps to a list (ambiguity → unresolved). New Jellyfin/Emby items are placed through `client.resolveLibraryKey(ratingKey)` (`/Items/{id}/Ancestors` → the `CollectionFolder` id). It still falls back for a section key with no `Library` row (`newLibrarySeen`), a change set over 100, a transient fetch error, a full sync already running, or any unresolved id on Jellyfin/Emby. `PlexClient.getItemMetadata` returns `Metadata?.[0]` with `librarySectionID` merged down from the container. It ends with `recomputeCanonical` (scoped to the before/after `dedupKey`s), `invalidateMediaCaches()` and `sync:completed`.
- **Post-delete re-check** (`PostDeleteResync`, `src/lib/lifecycle/post-delete-resync.ts`, used by the scheduled executor): deleted items, their acted-on members and — for a whole show or artist — every row of the group in its library are re-fetched through `syncMediaServerItems`. A server falls back to a targeted library sync (`POST_DELETE_SYNC_TRIGGER`, `skipWatchHistory: true`) past `POST_DELETE_INCREMENTAL_LIMIT` (100; pinned to the incremental limit by `tests/unit/lifecycle/post-delete-limit.test.ts`), for a group too large to name, or on fallback/throw.

### Watch history & Tracearr

- A `WatchHistory` row is **one play event** (per-item aggregates are `MediaItem.playCount`/`lastPlayedAt`). `source` is `"NATIVE"` (the server's history API; also the migration default) or `"TRACEARR"`. Native rows populate only `serverUsername`/`watchedAt`/`deviceName`/`platform`. Tracearr rows add `sourceEventId` (the resume-chain id; `@@unique([mediaServerId, sourceEventId])`, NULL for native rows), `referenceId`, completion columns (`watched`, `percentComplete`, `state`, `progressMs`, `durationMs` (summed in-window watch time), `totalDurationMs` (runtime), `segmentCount` (>1 = resumed), `stoppedAt`), client columns (`player`, `product`) and stream columns (`isTranscode`, `videoDecision`, `audioDecision`, `bitrate` kbps, `resolution`, source/stream codecs, Json `transcodeInfo`, `subtitleInfo`, `streamQuality`).
- **Completed-play predicate** — `src/lib/media/watch-completion.ts`: `completedPlaySql(alias)` (raw SQL) and `COMPLETED_PLAY_FILTER` (Prisma), i.e. `watched IS DISTINCT FROM false` / an explicit `OR [true, null]` — both must admit the NULL a native row carries. A partial or still-running Tracearr play is stored and shown but must not count as a play: because `playCount`/`lastPlayedAt` are monotonic, one such row would permanently disarm every "not played in N months" rule. Consumers that must use it: **both** helpers in `watch-reconcile.ts` (change both or neither), the `watchedByUser` rule in **both** phases (Phase-1 relation filter in `conditions/where-builder.ts` and the Phase-2 eager loads in both engines), the removed-item eager load in `/api/lifecycle/rules/[id]/diff`, and **both** Seerr watch-correlation paths (`request-stats.ts`, `/api/seerr/users/[userKey]/requests`). `watch-analytics.ts` deliberately does not (engagement, not deletion). A new consumer must decide explicitly.
- **`src/lib/sync/watch-reconcile.ts`** — item sync derives play state from account-scoped metadata (Plex admin token views; Jellyfin/Emby admin `UserData`), so the server-wide per-user `WatchHistory` is reconciled into `playCount`/`lastPlayedAt` (and through them `seriesLastPlayedAt`, `watchedEpisodeCount`, `watchedEpisodePercentage`). Monotonic (`GREATEST`/`Math.max`). `reconcileWatchStateFromHistory(serverId, { mediaItemIds? })` runs (non-fatal) after every `syncWatchHistory` — scoped to the items written after an append, a Tracearr run or recovery (nothing when nothing was written), unscoped after a native full replace or with `reconcileAll` — and unscoped in `syncMediaServer` whenever `skipWatchHistory` is set.
- **Native path** (`syncWatchHistory`): full replace (delete this server's rows, re-insert what the server reports) in 5,000-row `unnest` batches (`BATCH_SIZE`). When the realtime manager enqueues `TASK_SYNC_WATCH_HISTORY` with `incremental: true` it appends instead — only with a client asserting `supportsHistorySince` (Plex), `watchHistorySyncedAt` set, and a stored row to resume from: Plex is asked `viewedAt>=` (newest stored play − 1 h; written into the URL verbatim — Plex ignores the percent-encoded form), older entries are dropped client-side, and the overlap is deduped on item + user + `watchedAt`. Both modes take a per-server `pg_advisory_xact_lock` (the History page's Refresh runs outside `MAIN_QUEUE`). The scheduled dispatcher, Refresh and the full sync keep the full replace (which also reconciles plays the server deleted). On abort the native path **throws** (rolling back the replace).
- **Progress** (`src/lib/sync/watch-history-progress.ts`): `POST /api/media/history/sync` streams one phase per server (`key` = server id), terminal result `{ success: true, counts }` (a failed server `-1`). Native reports a real `fraction`; Tracearr omits it (keyset API, no total) and reports counts, rendered as an indeterminate bar — **never synthesise a percentage**. The reporter and `AbortSignal` are optional; only the streaming route supplies them.
- **Source per server**: `MediaServer.tracearrServerId` + an enabled `TracearrInstance` → Tracearr import; no mapping → native; mapped but the instance is disabled/deleted → **skipped outright** (a native fallback deletes the imported rows and double-counts after re-enable). The importer drops any `NATIVE` rows for the server once its own rows have landed. The serving instance is found by asking each enabled instance which servers it monitors (`listServers()`; a single instance short-circuits; an unreachable one is skipped). Changing the mapping in `PUT /api/servers/[id]` (either direction, Tracearr→Tracearr included) wipes that server's `WatchHistory` once, resets `tracearrBackfillComplete` (`tracearrMappingChanged`), clears `watchHistorySyncedAt` in the same write, and is refused (409) when another server already maps that `tracearrServerId`. Play state is not walked back, and **Tracearr-side deletions do not propagate**.
- **Client** (`src/lib/tracearr/tracearr-client.ts`, read-only axios) spans two API versions: `/api/v1/public/health` for connectivity and the server list (the only place `server_id` UUIDs are enumerated), `/api/v2/public/history` for plays (carries `rating_key` + TVDB/TMDB/IMDB ids, keyset-paginated, **newest first**; plays under 2 minutes are absent — never read a missing row as a join failure). A 429 is retried once with a bounded delay. A `HistoryRecord` is a resume-chain aggregate: a re-sighting must UPDATE the row. `findOldestPlayAt(tracearrServerId, { signal?, floor? })` bisects `until` at hour precision (~19 calls for 7 years); stored once per server in `MediaServer.tracearrOldestPlayAt`, best-effort.
- **Import** — `syncTracearrHistory(serverId, { onProgress?, signal?, passes?, deadlineMs?, yieldTo? })` → `{ count, backfillPending }`:
  - **FORWARD** pass: `since = MAX(watchedAt) − 1 h`, reaching further back for a still-open chain at the boundary, clamped to 7 days; skipped with no watermark. **BACKFILL** pass: `until = MIN(watchedAt)` (inclusive; the boundary play is merged), walking older until exhausted. A lone forward watermark is unsafe on a newest-first API: an interrupted first import would abandon all older history.
  - Boundaries come from the rows (`resolveImportWindow`: three subqueries — not one `FILTER` aggregate, which defeats the `(mediaServerId, source, watchedAt)` index). `MediaServer.tracearrBackfillCursorAt` records how far a backfill walk reached (measured per walk, never inherited from the forward pass). `tracearrBackfillComplete` is the only other persisted state; it is treated as false when the server holds no Tracearr rows (`staleBackfillState`, reset in the DB).
  - `walk()` returns `"exhausted"` **only** when `nextCursor === null`; cancel, page cap, stalled cursor, deadline, yield and fetch/write errors are `"stopped"`. Only an exhausted walk that **saw at least one record** may mark the backfill complete.
  - `syncWatchHistory` runs `passes: "forward"` only (bounded; the user may be waiting) and enqueues `TASK_TRACEARR_BACKFILL` while `backfillPending` (derived from the flag), unless that job is backing off (`isJobRetrying`).
  - On cancel the importer breaks at the next page (the signal also aborts the HTTP call and rate-limit waits) and keeps what it wrote — resumable in both directions; the route reports `cancelled: true`.
  - **The account-name map is a precondition of every writing pass** (forward, backfill, recovery): `getServerAccountNames()` maps `server_user_id` → the media server's own username (the vocabulary `serverUsername` and `watchedByUser` use; `user.username` is Tracearr's cross-server label). Missing **or empty** → the run writes nothing and the backfill reports `"errored"`.
  - Upsert on `@@unique([mediaServerId, sourceEventId])` is `ON CONFLICT DO UPDATE`, **non-regressive** (`since` also narrows the aggregation): `GREATEST` for `percentComplete`/`progressMs`/`durationMs`/`segmentCount`/`stoppedAt`, `watched` and `isTranscode` latch, descriptive columns `COALESCE(excluded, stored)`.
  - `writeBatch` runs in a transaction that selects the `MediaServer` row `FOR SHARE` with the expected `tracearrServerId` (`TracearrMappingChangedError` → `"stopped"`), and re-checks item existence just before inserting (the walk's catch stays the backstop for the residual race).
  - `MAX_PAGES` (20,000) is a runaway-cursor backstop only; the per-page dedup set is page-scoped. The next page is prefetched while the current one is written (aborted if unused). The join index is built lazily on the first page holding this server's records and handed to recovery. Instance-ownership probes run in parallel.
  - `watchHistorySyncedAt` is written at the end of any run whose account map loaded and whose archive walk is complete.
- **Joining** (`src/lib/sync/tracearr-join.ts`) — **a dropped play beats a wrong one** (a wrong `serverUsername` arms `watchedByUser` DELETE rules and nothing revisits the row). `rating_key` → `MediaItem.ratingKey` on the server, then corroborated: the type must match, plus `contradictsIdentity` at the same granularity — **episodes compare `grandparent_rating_key`** (never provider ids: Tracearr sends episode-level ids while we store series-level ones; never season/episode numbers); movies and tracks compare provider ids where both sides carry one. Absence on either side is accepted. The provider-id fallback (`tmdb_id` → `imdb_id`, never TVDB) is for movies and tracks only — **never episodes**. Every ambiguity (two rating-key hits, a multi-episode id match) is a skip. The index is built once per run with two queries.
- **`TASK_TRACEARR_BACKFILL`** (`tracearr-backfill`, payload `{ serverId }`, `MAIN_QUEUE`, `maxAttempts: 3`): runs the backfill pass for a 5-minute slice (`TRACEARR_BACKFILL_SLICE_MS` — bounded below by the per-run join-index cost, above by `MAIN_QUEUE` being serial), then `invalidateMediaCaches()`, then re-enqueues while `backfillPending` (not after an `"exhausted"` walk with nothing found). Its jobKey `tracearr-backfill:<serverId>` is **shared** with `syncWatchHistory`'s enqueue so a Refresh mid-backfill collapses onto it. All resume state is in the DB, so a killed slice just resumes.
- **Re-added items**: `WatchHistory.mediaItem` is a required FK with `onDelete: Cascade`, so deleting an item deletes its plays and a re-add reads as never watched. Once the archive walk is complete, the backfill task runs `recoverHistoryForNewItems`: items created in the last 7 days, a capped number per run, one `rating_key` request each, skipping items Tracearr already answered for (`answeredItems`, in memory); it stops at the first host-level failure or 429. Bulk destruction (`/api/media/purge`, disable with `deleteData`) calls `restartTracearrBackfill` (`watch-evidence.ts`: flag false, cursor = now). The backfill's end-of-slice state write is compare-and-set.
- **Status route** (`GET /api/integrations/tracearr/status`): `backfillFraction` measures **time covered, not records** (many fetched plays are never stored because their media is gone): `1` when complete; `null` without `oldestPlayAt`, without rows, or with a non-positive span; otherwise `clamp01((newestImported − reached) / (newestImported − oldestPlayAt))`, `reached` = `tracearrBackfillCursorAt` ?? `oldestImported`. **`null` (indeterminate bar) and `0` are different states.** `activeImport` (`{ pass, startedAt, pages, imported, oldestReached }` or `null`) comes from the in-process registry `src/lib/sync/tracearr-import-activity.ts` — entries per run, addressed by the handle `beginTracearrImport` returns (never by server id), pinned to `globalThis`. Settings renders one status line per server (`TracearrImportStatusLine` → `TracearrLiveImportLine`).
- Import progress is pushed: `tracearr:import-progress` (`meta.serverId` only) after each page **commits**, throttled 2 s per server (`IMPORT_PROGRESS_THROTTLE_MS`, module-level map), plus once unthrottled at run end. Settings and History refetch the status route; a 30 s `useFallbackPoll` covers a dropped stream (also while any import is live).

### Realtime & events

- **Browser push layer**: `src/lib/events/event-bus.ts` (`eventBus`, pinned to `globalThis`; `subscribe` isolates a throwing listener) → `src/app/api/events/stream/route.ts` (SSE, filtered by `session.userId`) → `src/hooks/use-realtime.ts` (`useRealtime(type, cb)`).
- **Every `AppEventType` must have at least one `useRealtime` subscriber** (`tests/unit/events/event-subscriber-coverage.test.ts`); add a `SERVER_ONLY` entry with a reason if one genuinely has no browser consumer.
- **Events carry no figures** — `meta.serverId` and nothing else (`sync:progress`, `tracearr:import-progress`, `session-changed`, `watch-history:updated`), or a scope such as `sync:completed`'s `libraryTypes`/`incremental`. Receivers refetch the route that owns the number.
- `watch-history:updated` is deliberately NOT `sync:completed` (which makes every listing refetch; the backfill emits per slice for hours) — `src/lib/sync/watch-history-events.ts`. `emitWatchHistoryUpdated` calls `invalidateMediaCaches()` before announcing.
- **The shared `EventSource` must not close on navigation**: it is ref-counted, `releaseSource()` defers the close by `IDLE_CLOSE_DELAY_MS` (10 s), and `AuthenticatedShell` holds `useRealtime("settings:changed", checkMaintenance)` — **do not remove the shell's `useRealtime` call**; it is load-bearing for the transport. There is no replay (no event ids), so on a re-open every subscriber's callback runs once (`fireResync`; a callback subscribed to several types runs once; all in one request scope). A 401 is told apart from a drop by a `HEAD` probe (the route exports `HEAD` explicitly) and stops the retry loop. `useRealtimeEvents(types, cb)` subscribes to several types at once.
- `beforeRealtimeEvents` registers a callback that runs before every subscriber's callback for an event (once per event, and before every reconnect resync); the shell uses it to drop the client caches (see "Frontend data loading").
- **Shared requests**: `fetchJsonShared` / `fetchShared` (`src/lib/shared-fetch.ts`; `fetchShared` also returns status and an error body, `SharedResponse`) share one request per synchronous turn (dropped in a microtask). Inside a realtime event, `useRealtime` runs callbacks in the event's request scope (`runInRequestScope`, `newRequestScope`), so every subscriber of that event shares the request.
- `isRealtimeLive()` / `useRealtimeLive()` — true once the current stream has delivered an event (the route sends `connected` first, carrying `lastEventAtByType`); false while connecting, after a drop, or behind a proxy holding events back. `resyncIfEventsSince(at)` refetches through the subscribers of every event type emitted at/after `at` (all subscribers if the report is unreadable).
- **Polls are fallbacks**: run them through `useFallbackPoll(callback, intervalMs, enabled?)` (`src/hooks/use-fallback-poll.ts`, polls only while `useRealtimeLive()` is false) — never delete one. Sidebar sessions and maintenance 5 min, Settings server list 15 s (sync progress comes from `/api/sync/status` on each `sync:progress`, `settings/sync-progress.ts`), Tracearr status 30 s. Plain intervals remain only for the dashboard Integrations health tile, the History page's import notice, the General tab's realtime-status line, System Logs' auto-refresh, and `/api/tools/sessions/stream`'s own 5 s server-side tick.
- **A change the page itself started is re-read once**: `SyncLibraryButton`'s and `SyncIndicator`'s `onSyncComplete` fire only for an end their fallback check saw with no event; the History page's Refresh ignores `watch-history:updated` while its own sync runs and re-reads once at the end; Matches' and Pending's Execute/Re-evaluate use `useRealtimeRefetch`.
- **Media-server realtime** (`src/lib/media-server/realtime/`, `ws`, socket injected via `SocketFactory`): one self-healing connection per enabled server (keyed by `MediaServer.id`), started by `startRealtime()`. Normalizers (`normalize-plex.ts`; `normalize-jellyfin.ts` for Jellyfin and Emby) emit canonical `session-changed` / `library-changed` / `watch-changed` / `server-status` on `realtimeBus` (separate from `eventBus`). `connection.ts` reconnects with backoff (1 s→60 s) + keepalive and dedups the Jellyfin/Emby `Sessions` firehose with a position-free signature. `manager.ts` reconciles connections with the DB (honours `AppSettings.realtimeSync`; on `server:changed`/`settings:changed` plus a 60 s pass; concurrent reconciles coalesce) and routes events:
  - session → leading-edge-throttled enforcer tick (immediate, floored to once per 2 s);
  - library → debounced `TASK_SYNC_INCREMENTAL` with the accumulated changed/removed ids; a full `TASK_SYNC_SERVER` only past 100 items; an item-less `library-changed` contributes nothing;
  - watch → debounced `TASK_SYNC_WATCH_HISTORY` (`incremental: true`, jobKey `watch-history:<serverId>`).
- **Plex normalizer**: `timeline` is the only source of `library-changed` (adds, updates and deletions all appear there); `activity` is ignored entirely. Entries whose Plex `type` is a container (18 collection, 15/16 playlist) or whose `sectionID < 0` (extras) are dropped; entries are deduped by `itemID`; an entry with no `type` is kept. Deletions (`state=9`/`metadataState=deleted`) are flagged in `LibraryChangeDetail.deletedIds` (the id still travels in `changedIds`).
- **Self-write registry** (`self-writes.ts`, pinned to `globalThis`): `markSelfWrites(serverId, ratingKeys)` / `isSelfWrite(serverId, ratingKey)`, 2-minute TTL (`SELF_WRITE_TTL_MS`). `lifecycle/collections.ts` marks the collection and **every current member** before each Plex collection write; `RealtimeManager.accumulateLibraryChange` drops marked ids — **never a deletion** (`deletedIds`, Jellyfin `removedIds`). Suppressed echoes are logged once per burst through their own debouncer (never the sync debouncer).
- Bridged to `eventBus` (so they reach the browser): `server-status` (only on a `connected`↔`disconnected` transition) and `session-changed` (throttled 2 s per server). `RealtimeServerConfig` carries `userId` so the bridge needs no DB read. `GET /api/tools/realtime/status` lists each enabled server's connection state (`getRealtimeManager().getStatuses()`) for Settings → General.

## Critical Conventions

### Single-user model

Librariarr runs with exactly one admin account:

- **Schema**: `AppSettings.userId @unique` — the DB rejects a second admin row.
- **Setup gate**: `src/app/api/auth/setup/route.ts` and `src/app/api/auth/plex/token/route.ts` reject creating a second user.
- **Check-setup**: `src/app/api/auth/check-setup/route.ts` uses `findFirst()` because there is one and only one admin.

Code references `session.userId` because per-user resources (`MediaServer`, `RuleSet`, `LifecycleAction`, …) carry a `userId` FK — a normal relation, not a sign that more than one user can exist. **Never** add per-user cache keys, multi-tenant invalidation patterns, "no cross-tenant leak" tests or "tenant isolation" comments.

### Route Session Guard

Every signed-in route handler is wrapped in `withSession` (`src/lib/auth/with-session.ts`), which answers 401 `{ error: "Unauthorized" }` itself and hands the handler a `LoggedInSession` whose `userId` is a string:

```typescript
import { withSession } from "@/lib/auth/with-session";

export const GET = withSession(async (session, request: NextRequest) => {
  const items = await prisma.ruleSet.findMany({ where: { userId: session.userId } });
  return NextResponse.json({ items });
});

// Dynamic segments: the route context follows the request (params is a Promise in Next.js 16).
export const DELETE = withSession(async (session, request: NextRequest, { params }: { params: Promise<{ id: string }> }) => { … });
```

- It reads `getSession()`, so revocation, the settings bundle's `withSharedSession` and `withApiKey`'s principal all apply.
- Declare only the parameters the handler reads: a handler of `(session)` alone is callable with no arguments (the settings bundle relies on that).
- Do not write an inline `getSession()` + `isLoggedIn` check in a new route. Inline checks are only for the sign-in flows and where something must run first (a rate limit — `ai/chat`, `settings/ai/test`; the same-origin check — the SSO routes; the bundle's path validation).

### API Request Validation

All mutation routes validate through `src/lib/validation.ts`:

```typescript
import { validateRequest, someSchema } from "@/lib/validation";
const { data, error } = await validateRequest(request, someSchema);
if (error) return error;
```

- All Zod schemas live in `src/lib/validation.ts` (never inline in a route), imported from `zod/v4`.
- Validation failure → 400 `{ error: "Validation failed", details: [...] }`; malformed JSON → 400 `{ error: "Invalid JSON in request body" }`.
- `validateOptionalRequest` for an optional body (`POST /api/servers/[id]/sync`): no body validates as `{}`, a present body must parse and match.

### API Response Security

- Routes returning server/integration records wrap them in `sanitize()` (`src/lib/api/sanitize.ts`), which recursively masks `accessToken`, `apiKey`, `plexToken`, `passwordHash`, `backupEncryptionPassword`, `oidcClientSecret`, `aiApiKey` with `"••••••••"` (`MASKED_VALUE`).
  ```typescript
  return NextResponse.json({ server: sanitize(server) });
  ```
- Error text — including a failed connection's — goes through `sanitizeErrorDetail()` (strips internal paths, private IPs and `*.plex.direct` hostnames).
- **A settings route returns only the fields its tab reads, never a whole `AppSettings` row** (it holds the backup passphrase, OIDC secret, AI key and Discord webhook, which `sanitize()` does not mask by name there). Always `select` on `appSettings` reads that reach a response (`tests/integration/settings/settings.test.ts`).
- Integration edit flows test through server-side `[id]/test-connection` (POST `/api/integrations/{type}/{id}/test-connection`), never by sending stored keys to the browser. The `[id]` PUT tests the connection only when the URL (trailing slashes aside) or the key actually changes, and the forms require a passing test only then (`changesConnection`). Arr/Seerr forms send `externalUrl` only when it changed; add/edit errors show the first validation `details` entry via `integrationSaveError`.
- Auth endpoints are rate-limited (see "Rate limiting") and answer 429 with `Retry-After`.
- Media queries verify ownership: `findFirst` with `library: { mediaServer: { userId: session.userId } }`, never a bare `findUnique({ where: { id } })`.

### Authentication, sessions and step-up

- **Session** (`src/lib/auth/session.ts`): iron-session encrypted cookie, 30 days (`ttl` and `maxAge` share `SESSION_LIFETIME_SECONDS`). **The cookie carries identity only** — `userId`, `isLoggedIn`, `sessionVersion`, `authenticatedAt` and the transient OIDC handshake — never a credential. `SessionData` has no Plex token field; the two readers (`GET /api/auth/plex/servers`, `POST /api/servers` by machine id) take it from the User row through `getStoredPlexToken` (`src/lib/plex/auth.ts`). `Secure` is inferred from `x-forwarded-proto` unless `COOKIE_SECURE` is set.
- **`getSession()` enforces revocation**: a cookie whose user is gone or whose `sessionVersion` mismatches (or is absent) reads as `isLoggedIn: false`. `getRawSession()` skips the check and is for login flows only. Logout increments `sessionVersion`. `GET /api/auth/logout` also refuses `Sec-Fetch-Site: cross-site`/`same-site`.
- **Every login path uses `rotateSession()`**, never `getSession()` — setup, local login, both Plex token branches, the OIDC callback and forward-auth. It signs the visitor out, returns a fresh session and stamps `authenticatedAt` (epoch ms). It reads the cookie store twice on purpose (iron-session rejects `destroy()` → write → `save()` on one object); route tests mock it, so `tests/unit/auth/session-rotation.test.ts` is the only check of the real semantics.
- **Under an API key the cookie is never read**: `getSession()` returns a frozen session for the key's owner (the request's `ApiKeyPrincipal`, `src/lib/api-keys/principal.ts`, an `AsyncLocalStorage` only `withApiKey` writes; `save`/`destroy` throw), and `getRawSession()`/`rotateSession()` throw (`tests/unit/auth/session-api-key.test.ts`).
- Passwords: `src/lib/auth/password-rules.ts` (8 characters to 72 UTF-8 bytes) is shared by `authSetupSchema`, `changePasswordSchema` and the three forms; login accepts any length.
- **CSRF**: `src/proxy.ts` applies `isTrustedMutationOrigin` (`src/lib/url.ts`, host-only) to every non-GET `/api/*` request, `/api/v1` included.
- **Recent sign-in (step-up)**: `hasRecentLogin` (`src/lib/auth/recent-login.ts`, `RECENT_LOGIN_WINDOW_MS` 15 min), refused through `reauthRequired` (`src/lib/auth/reauth.ts`: 403 `reauth_required` carrying `methods` — `plex`/`oidc`/`forward`/`password` from `loadReauthContext`; with no method under usable SSO it warns against signing out and points to `SSO_DISABLE_OVERRIDE`). Required by:
  - creating an API key — an account with a usable password instead sends `currentPassword` (400 `password_required`, 403 `password_incorrect`);
  - a first local password (`change-password` with no `passwordHash`), `POST /api/auth/plex/link`, `POST /api/settings/sso/link`, `/api/settings/sso/link/oidc/start`;
  - backup create, download and restore (a backup holds the Plex token; listing and deleting are not gated);
  - `POST /api/servers` with a `machineId` and no `accessToken` (looks the token up itself, owned servers only);
  - `PUT /api/servers/[id]` when any server's URL changes (trailing slashes aside) or `tlsSkipVerify` turns on while its stored token stays;
  - Arr/Seerr/Tracearr `[id]` PUT and `[id]/test-connection`, `PUT /api/settings/ai` and `POST /api/settings/ai/test`, when a new URL would receive the stored key (`refuseStoredKeyToNewUrl`, `src/lib/integrations/stored-key-guard.ts`);
  - `PUT /api/settings/sso` turning SSO on, switching `ssoMode`, changing `forwardAuthUserHeader`, or changing the issuer while OIDC SSO is on (a link stored before issuers were recorded is accepted under any issuer);
  - turning password sign-in back on (`turnsPasswordSignInOn(before, after, hasPassword)` — `PUT /api/settings/auth` enabling local login; `PUT /api/settings/sso`, `POST /api/settings/sso/revert`, `DELETE /api/settings/sso/link` disabling SSO) or Plex login back on (`turnsPlexSignInOn`).

  **Keep this list closed**: a new route that adds a sign-in method or long-lived credential, or returns or forwards a stored Plex token, must call it. A route that relays a media server's responses must restrict what it asks for, since every request carries the admin token: `/api/tools/sessions/image` fetches only `isSessionArtworkPath` paths (`src/lib/media-server/artwork-path.ts`) and passes on only `image/*` bodies; `GET /api/auth/plex/servers` returns no `accessToken`. `tests/integration/auth/stolen-cookie-chain.test.ts` runs the stale-cookie → backup → Plex token → sign-in → API key chain.
- **Reauth routes** (none links, rotates or signs anyone in; each checks its method is in `loadReauthContext`'s list, then stamps `authenticatedAt` on the existing session):
  - `POST /api/auth/reauth/password` — charged in the shared `PASSWORD_CONFIRM_BUCKET`.
  - `POST /api/auth/reauth/plex` — the Plex id must equal `plexId`; offered only while Plex login would be accepted; refreshes the stored token.
  - `POST /api/auth/reauth/oidc` — a `prompt=login` handshake in a popup with `session.oidcFlow = "reauth"`. The callback checks `ssoIdentityMatches` and sends the popup to `/login/reauth?status=ok|error=…`, which reports via `postMessage` AND the `librariarr-reauth` BroadcastChannel (COOP can sever `window.opener`). Each attempt sends a `nonce` carried in the OIDC `state` as `<random>.<nonce>` (`reauthNonceFromState`, copied from the IdP's returned `state`); the waiting page accepts only a report with its own nonce. The wait ends on a report, Cancel/unmount or 10 minutes — never on `popup.closed` after the IdP navigation. A confirmation that can no longer finish reports `session_lost` / `state_mismatch` and clears only its own handshake. The OIDC login start clears any leftover `oidcFlow`.
  - `POST /api/auth/reauth/forward` — the proxy's identity header with `FORWARD_AUTH_SECRET` enforced; `forward_auth_unconfigured` while it is unset.
- **Client**: `src/lib/auth/reauth-client.ts` holds the four confirmations and `fetchWithReauth` — a `reauth_required` 403 opens the `ReauthDialogHost` prompt (mounted in `AuthenticatedShell` and on `/onboarding`) and repeats the request once confirmed; a dismissed prompt yields 403 `reauth_cancelled`; concurrent requests join the open prompt; an unmounting host answers false. The API-key dialog renders `ReauthPanel` inline (it never calls `onConfirmed` after unmounting). **Every call to a recent-login-guarded route goes through `fetchWithReauth`**: `tests/unit/auth/reauth-callers.test.ts` finds every route method that can call `reauthRequired` or `refuseStoredKeyToNewUrl` and fails on a plain `fetch` to one unless listed in `CAN_TRIGGER` or `CONFIRMS_INLINE`. Settings downloads backups by fetching the blob (a navigation cannot show the prompt).
- **Password sign-in off** (`src/lib/auth/password-sign-in.ts`): `passwordSignInEnabled` = `localAuthEnabled` and SSO not usable, or `SSO_DISABLE_OVERRIDE`. While off, a password is accepted for nothing: the local login refuses, the API-key step-up and `change-password` treat the account as passwordless (recent sign-in required, `currentPassword` never compared), `/reauth/password` answers 400, and `loadReauthContext` omits it. `GET /api/settings/auth` returns `passwordSignInEnabled`; the SSO section calls back after each change so the page re-reads it.
- **Sign-in settings writes** (`PUT /api/settings/auth`, `PUT /api/settings/sso`, `POST /api/settings/sso/revert`, `DELETE /api/settings/sso/link`) check and write under one advisory lock (`lockSignInSettings`) inside the write's transaction, re-reading state through the transaction client (`getSsoSettings(db)`, `loadPasswordSignInState(db)`) — never the global client inside the lock (`tests/integration/settings/sign-in-settings-race.test.ts`). `/api/settings/auth` keeps at least one of Plex login, local auth or SSO usable. `PUT /api/settings/sso` refuses, while SSO stays on, settings whose issuer (`currentSsoIssuer`) the admin is not linked under (`ssoLinkedToIssuer`).
- Linking Plex never changes `plexLoginEnabled`; `POST /api/auth/plex/link` returns it, and every link site (Settings → Authentication, Add Server → Plex, onboarding) opens `PlexLoginPrompt` (`src/components/plex-login-prompt.tsx`) while it is off.
- **SSO** (`src/lib/sso/`): OIDC (Authorization Code + PKCE) and forward-auth. Manual linking only — an admin must link an `ssoSubject` before SSO login is accepted. With `AppSettings.ssoEnabled` the local form is hidden; `AppSettings.plexLoginEnabled` (default true) independently hides the Plex button without unlinking the token.
  - **Forward-auth requires `FORWARD_AUTH_SECRET`** (`forward-secret.ts`): requests must carry `X-Librariarr-Proxy-Secret`. Without it `isSsoUsable`/`ssoUnusableReason` (`config.ts`) read forward-auth as not configured (the login page falls back to local/Plex), `PUT /api/settings/sso` refuses to enable it (`GET` returns `forwardAuthSecretConfigured`), `hasForwardAuthSecret` is false, login and reauth refuse with `forward_auth_unconfigured`, and `getSsoSettings` logs an ERROR once. The comparison is one `timingSafeEqual` over length-prefixed buffers (deliberately not hashed); a wrong header redirects with `sso_error=untrusted_proxy` (the login page's message map is keyed by these codes).
  - **The OIDC issuer must be `https://`** (`issuer-url.ts`, `oidcIssuerProblem`, shared by `ssoConfigSchema`/`ssoTestSchema`, `isSsoUsable` and `discoverOidc` → `InsecureIssuerError`); `http://` only on a loopback host or with `OIDC_ALLOW_INSECURE_HTTP=true`. `resolveRedirectUri` builds from `getExternalBaseUrl`; a discovery document without `issuer` is refused.
- **Discord on API-key changes**: create and delete fire `notifyApiKeyChange` (`src/lib/api-keys/notify.ts`) when a webhook is set and `AppSettings.discordNotifyApiKeys` (default **true**) is on — never awaited, never failing the request. `settings/discord` exposes it as `notifyApiKeys`.

### Rate limiting

`src/lib/rate-limit/rate-limiter.ts` — in-memory `RateLimiter` (`check(key, cost = 1)`, `peek(key)` without counting, `refund(key, window)` only in the window `check` returned; constructor `maxEntries`).

- `authRateLimiter` — 10 attempts / 15 min per address (≤ 10,000 addresses). **Every route that verifies a credential is charged only on failure** through `peekAuthRateLimit` + `reserveAuthAttempt` (reserved before the compare; `attempt.succeeded()` gives it back and remembers the address): the local login, `plex/token`, the OIDC callback, the forward-auth login, every `reauth/*` route, the API-key step-up and `change-password`. Password confirmations (reauth, API-key step-up, `change-password`) share `PASSWORD_CONFIRM_BUCKET`, charged after the session check. `checkAuthRateLimit` (charged every call) is only for routes that start a flow (a Plex PIN, an OIDC handshake) and the setup-phase routes under `SETUP_BUCKET` (setup, setup-time backup list and restore).
- `authGlobalRateLimiter` — 60 / 15 min per bucket across every client, applied only to addresses no sign-in has succeeded from (`knownAddresses`, 30 days sliding, ≤ 10,000; `isKnownAddress`, `rememberAuthenticatedAddress`). `tests/integration/auth/login-lockout.test.ts`.
- `aiRateLimiter` — 30 / 5 min (`checkRateLimit(request, aiRateLimiter, …)`).
- Public API — deliberately nothing per address (a shared Docker or `"unknown"` address would let anyone lock every integration out): `apiKeyCredentialFailureLimiter` (20 failures / 15 min per presented key, ≤ 10,000 tracked), `apiKeyFailureLogLimiter` (50 WARN rows / 15 min — bounds logging only), `apiKeyRequestLimiter` (600 / min per key; a full listing costs `FULL_LISTING_REQUEST_COST` = 20), `apiKeyUnknownLookupFloor` (1,000 lookups of non-existent keys / min, global) and `apiKeyVerificationFloor` (100 scrypt verifications / min, global). Both floors exempt a key verified in the last 15 minutes.

### Public API (`/api/v1`)

Third-party applications use `/api/v1`, authenticated only by API key (Settings → Authentication → API Keys). Keys never work on any other route, and `/api/v1` never accepts the cookie session. Keys are independent of the login session (logout and password changes revoke cookies, not keys).

- **Keys** (`src/lib/api-keys/`): `scopes.ts` (client-safe) is the ONE scope registry — `resource:action` scopes, each `read` or `write`, write scopes `implies` their read scope (expanded at creation, so a scope added later never widens an old key), `lifecycle:execute` marked `destructive`, `READ_ONLY_SCOPES`. `keys.ts`: `lbr_` + 43 base62 chars (rejection-sampled), stored only as salted scrypt `hashApiKey` (`scrypt$N$r$p$salt$hash`) plus a 10-char display `prefix` that is also the lookup (`@@index([prefix])`). `name-rules.ts` (client-safe) is the one key-name rule. Creation counts and inserts under a per-user `pg_advisory_xact_lock` (`MAX_API_KEYS` 50; names unique per user → 409).
- **Management** (`api/settings/api-keys/`, cookie session only): `GET` (never `keyHash`; `API_KEY_PUBLIC_SELECT`), `POST` (plaintext `key` exactly once, `Cache-Control: no-store`; `normalizeScopes`; step-up — see above), `[id]` `DELETE`.
- **Guard** (`guard.ts`, `withApiKey(scope, handler, opts?)`):
  - refuses a key anywhere in the URL (400, `containsApiKey`: known parameter names in any case, or `lbr_…` in path, name or value; query parts are decoded once more via `safeDecode`, the path twice);
  - reads `Authorization: Bearer` or `X-Api-Key` (a non-Bearer `Authorization` is ignored; with both, the `lbr_`-shaped one wins; two different `lbr_` keys → 400);
  - finds rows by `prefix` (≤ 5) and verifies scrypt constant-time once per key per process (`verifiedKeys`, 15 min sliding, `verificationsInFlight` single-flight) — not an authorization cache: the row is re-read every request, so deletion revokes at once;
  - expired → 401 `API key has expired` (logged once per 15 min, not charged); scope → 403 + `WWW-Authenticate … insufficient_scope`; rate limits as above; `lastUsedAt`/`lastUsedIp` written at most once a minute; handler run inside `runAsApiKey`; audited (never the key); `Cache-Control: no-store` (a handler's `public` becomes `private`); DB error → 503.
  - The `limit=0` cost uses `isFullListingLimit` (`src/lib/api/pagination.ts`), never a string compare, and is charged only on routes wrapped `{ limitZeroMeansAll: true }`; unpaged full listings (rule matches, actions, exceptions) use `{ fullListing: true }`. `tests/unit/api-keys/v1-routes.test.ts` derives and pins both flags. `getApiKeyGuard(handler)` exposes the scope.
- **Exposing a route**: add `src/app/api/v1/<same path>/route.ts` re-exporting the imported handler, e.g. `export const GET = withApiKey("media:read", appGet)`; its `getSession()` then resolves to the key's owner. Exceptions to the mirror pattern: `me` (any valid key) and `jobs/{sync,detection,execution}` (`run-job.ts` over `runJobNow` in `src/lib/jobs/run-now.ts`, shared with Settings' Run now; a sync whose enqueue failed for any server is `ok: false`). **Never wrap** a handler that reads the stored Plex token, writes the session, streams (SSE/NDJSON), manages credentials (auth, SSO, backups, API keys), or runs heavy work inline and unserialized (`/api/lifecycle/rules/run` — the API offers the queued, jobKey-deduplicated `POST /api/v1/jobs/detection`).
- **Every new v1 route needs**: an `API_OPERATIONS` entry (`src/lib/api-keys/openapi.ts`), a row in `tests/integration/api-v1/routes.test.ts` (401 without a key, 403 with every other scope, the handler's status with the right one), a row in `docs/src/content/docs/docs/advanced/api.mdx`, and an update to the pinned method/path/scope table in `tests/unit/api-keys/v1-routes.test.ts`. GET needs a read scope, every other method a write scope (`null` = any valid key, introspection only); a POST that only reads (e.g. the query engine) is not exposed rather than excepted.
- **Scope power is judged by what it can lead to**: removing a lifecycle exception deletes only a row, but it unprotects media, so `DELETE /api/v1/lifecycle/exceptions[/id]` needs `lifecycle:execute`; adding one is `lifecycle:write`. **New scope**: add to `API_SCOPES`/`API_SCOPE_INFO`/`API_SCOPE_GROUPS` (`implies` for a write scope's read), then the docs' scope table; existing keys never gain it.
- **Inputs**: a value a v1 route puts in a media-server or Arr URL path is one encoded segment — validate at the schema (`terminateSessionSchema` takes only `^[A-Za-z0-9_-]{1,128}$` ids) and encode at the client (`sessionPath`). **Every write input a v1 route reaches is bounded** with `.max()` (terminate message ≤ 500 and ≤ 200 ids, exception reasons ≤ 1000, `actionExecuteSchema` ≤ 1000 ids, `libraryKey` and every id string ≤ 200); add one to any schema a new v1 write reaches. The bulk exception DELETE/PATCH lists (`MAX_EXCEPTION_IDS_PER_REQUEST` 100,000, for the Exceptions page's grouped rows) are the deliberate exception — the v1 DELETE validates `apiExceptionDeleteSchema` (25) first and PATCH is not exposed. A v1 wrapper may take less than its app route: `PUT /api/v1/tools/maintenance` validates the strict `apiMaintenanceSchema` and rebuilds the body (no exemption list or Discord toggle).
- **Outputs**: `GET /api/v1/servers`, `/media/{id}`, `/sync/status`, `/lifecycle/rules`, `/lifecycle/rules/matches`, `/lifecycle/actions`, `/lifecycle/exceptions` (and its POST) and `/tools/sessions` are `withApiKey(scope, withoutServerInternals(handler))` (`src/lib/api-keys/trim-internals.ts`, guard outermost): it calls the handler without the client's `Accept-Encoding`, drops `filePath`/`partFile` everywhere, `url`/`externalUrl`/`serverUrl`/`machineId`/`userId` from anything that is a media server, and any `userId` equal to the key owner's id; runs `sanitizeErrorDetail` over string `error` fields; and re-emits through `jsonResponse`. `tests/integration/api-v1/no-file-paths.test.ts` calls every JSON read endpoint over seeded paths. `GET /api/v1/tools/sessions` reads through `readSessionsSnapshot`. `GET /media/search` refuses `q` over `MAX_SEARCH_QUERY_LENGTH` (200, in `limits.ts`). `extractActionError` and the sync engine's FAILED write sanitize before persisting; `describeActionError` is for logs only.
- **A key can never delete in bulk** (limits fixed in code in `src/lib/api-keys/limits.ts`, deliberately not a setting). Only four endpoints can lead to a deletion — `POST /lifecycle/actions/execute`, `POST /jobs/execution`, `DELETE /lifecycle/exceptions[/{id}]`, all `lifecycle:execute` — and `tests/integration/api-v1/deletion-safety.test.ts` pins that list plus every app handler any v1 file imports, then attacks each path:
  1. **Every item is named** — the execute wrapper validates the strict `apiActionExecuteSchema` (`mediaItemIds` required, 1–25), and the handler repeats the check under a principal.
  2. **25 per request, 100 per rolling hour across every key**, via `reserveApiDestructive` (`destructive-budget.ts`, pinned to `globalThis`): reserved on the final destructive count after every other guard, refused whole (400 over the per-request cap, 429 + `Retry-After` over the hour), a refusal charges nothing, an Arr failure is not refunded — but `release(n)` gives back what provably never happened (`notAttempted` items, actions left PENDING or skipped in an API-queued run). Non-destructive actions are not charged.
  3. **Removing exceptions is charged** (`removeExceptionsCharged`, `exception-removal.ts`: counts only existing, owned exceptions and settles on what the handler actually removed). The by-id app route is a `deleteMany` (404 on a lost race).
  4. **An execution run queued through the API is held, never trimmed**, when its destructive survivors exceed 25 or the hourly budget (`executeLifecycleActions(userId, { viaApiKey })`; WARN on every hold, Discord at most once per 15 min). `runJobNow(…, { viaApiKey })` queues under jobKey `execution-api:<userId>` with `viaApiKey` in the payload (`LifecycleExecutionPayload`) and does NOT advance `lastScheduledLifecycleExecution`. Scheduled and Settings-triggered runs are never limited.
- **The OpenAPI document is generated, never stored**: `API_OPERATIONS` (one entry per route: method, path, scope, params, body) → `buildOpenApiDocument(baseUrl, version)` (`openapi-response.ts`, via `jsonResponse`). Served cookie-only at `GET /api/settings/api-keys/openapi` (Download button and `/settings/api-docs`, with the relative server URL `/api/v1` via `relativeServer`) and to any key at `GET /api/v1/openapi.json`. The viewer mounts the bundled `swagger-ui-dist` ES bundle in an effect — never `swagger-ui-react`, never a CDN; `persistAuthorization` off; dark theme `swagger-dark.css` scoped to `.api-docs`. `swagger-ui-dist` needs `@scarf/scarf` denied in `pnpm-workspace.yaml` (or `pnpm install --frozen-lockfile` fails with `ERR_PNPM_IGNORED_BUILDS`). `openapi.ts`, `scopes.ts` and `limits.ts` must stay free of path aliases and Node imports: the docs build imports `openapi.ts` via `scripts/generate-openapi.ts` → git-ignored `docs/public/openapi.json`. `tests/unit/api-keys/openapi.test.ts` checks the table against every route file's scope and every documented query parameter against the handler's source (a `.get("name")` or a shared parser); documented list limits are `DOCUMENTED_LIST_LIMIT`, pinned to `pagination.ts`.

### API Pagination

- Params: `page` (1-based, default 1), `limit` (default 50, capped at 100–200; `0` = all), `offset`, `sortBy`, `sortOrder`. The flat list routes (`movies`, `series`, `music`) and the grouped `series/grouped`, `music/grouped`, `music/albums/all` (`{ maxLimit: MAX_GROUPED_LIST_LIMIT }`, 200) parse them through `parseListPagination` (`src/lib/api/pagination.ts`) → `{ page, limit, skip }`. `offset` overrides the page-derived skip and applies even with `limit=0` ("everything after the first N" — what progressive loading uses).
- **Every pageable list route orders by a total order** — append `{ id: "asc" }` after the user's sort; without a unique tiebreaker, rows straddling a page boundary duplicate or vanish ("stable ordering" in `tests/integration/media/movies.test.ts`).
- N+1 trick: fetch `limit + 1`; if over, pop and set `hasMore: true`. Response: `{ items: [...], pagination: { page, limit, hasMore } }`.
- `startsWith` for server-side alphabet filtering (A–Z, or `#` for non-alpha).
- Each flat route's `SORT_COLUMNS` must include every column `MediaTable` offers a sort header for (`tests/integration/media/table-sort-columns.test.ts`); `history-sort-columns.test.ts` does the same for the History page's `SORT_MAP`.
- A descending `NULLS LAST` sort matches no B-tree index. `/api/media/history` therefore runs a descending sort on a play column (`PLAY_SORT_OUTPUT`) as an index walk over the non-null rows, reading null rows only when the page reaches past them, up to `SPLIT_MAX_REACH` (10,000); deeper pages keep the plain query (`tests/integration/media/history-order.test.ts`).
- List payloads **exclude `summary`** (only the hover popover renders it, fetched via `summaryUrl`). List state is typed `MediaListItem` (`Omit<MediaItemWithRelations, "summary">`, `src/lib/types.ts`), so reading a summary from a list is a compile error. `MediaTable` is generic over its row type with `MediaListItem` as the floor.

**Series and season listings aggregate in SQL for every server count** (`/api/media/series/grouped`, `/api/media/series/all-seasons`; the multi-server form only adds the `dedupCanonical` conjunct). Each runs two statements in parallel: a narrow aggregate (counts, sums, maxes, quality counts, scalar firsts ordered by season, episode, id) and a `DISTINCT ON` representative row per group (artwork-preferred) for `mediaItemId`/`thumbUrl`/`summary`/`genres`; the resolution-label CASE is computed in a subquery pinned with `OFFSET 0`. Aggregates are ordered by group key for a stable sort. The label CASE is `resolutionLabelSql()` (`src/lib/resolution.ts`), the SQL twin of `normalizeResolutionLabel()` (`tests/integration/media/resolution-label-sql.test.ts`); shared fragments `firstNonNullSql`/`qualityCountsSql` live in `src/lib/media/series-sql.ts`. Search and `startsWith` go through `escapeLike()`. `loadMissingSummaries` (`src/lib/media/group-summaries.ts`) fetches the blurb by primary key only for groups whose art row has none (`summaryItemId`).

- Both routes apply `applyCommonFilters`: a show or season qualifies when ANY episode matches, and its figures stay whole-group. Last-played, added-at and (Series) watchlist filters are answered only on the group's own figures (`applySeriesFilters`; all-seasons' own check), never per episode. Show-level date filters (`parseDateFilter`) read UTC calendar days. The Series page sends every filter to the route and filters nothing client-side.
- Resolution matches the quality chip's label through `loadResolutionSpellings` (`src/lib/filters/resolution-spellings.ts`, `applyCommonFilters`' fourth argument — every listing route passes it). "Other" takes a NULL resolution only on these two routes (`{ resolutionOtherIncludesNull: true }`, the fifth argument).

**Artist and album listings aggregate in SQL too** (`/api/media/music/grouped`, `/api/media/music/albums/all`, fragments in `src/lib/media/music-sql.ts`): three parallel statements (aggregate, `DISTINCT ON` representative row, codec counts), keyed `LOWER(TRIM(parentTitle))` for an artist and `artist::album` (with `Unknown Artist`/`Unknown Album` placeholders) for an album, display title from the representative row, ordered by key. Filters stay Prisma's: when `search`, `startsWith` or `applyCommonFilters` narrows the listing, Prisma resolves matching ids first and the aggregate runs over `mi.id = ANY($n)`.

### Multi-Server Dedup

- `resolveServerFilter(userId, serverId, libraryType)` (`src/lib/dedup/server-filter.ts`) is the **required first step** of every media query route: `{ serverIds, isSingleServer, preferredTitleServerId, … }`. When `isSingleServer` is false, add `where.dedupCanonical = true`.
- `dedupKey` is a normalized hash of item metadata; `dedupCanonical = true` marks the preferred copy. `recomputeCanonical(userId, { dedupKeys? })` (`src/lib/dedup/recompute-canonical.ts`) picks a copy on an **enabled** server first, then the preferred title server, then the oldest, then the lowest id — one `ROW_NUMBER` pass writing only changed rows; `dedupKeys` scopes it.
- `getServerPresenceByDedupKey` (flat routes) and `getServerPresenceByGroup` (grouped; SERIES by `seriesKey`, MUSIC by normalized `parentTitle`) attach `servers[]` (sorted by server name then id; a server holding two copies links the oldest). `groupKeys` limits presence to the returned groups: `series/grouped` (`seriesPresenceSource`) and `music/grouped` read it after paging when a page, search or letter narrows the answer, alongside the aggregate for a filter's qualifying keys up to `PRESENCE_SCOPE_MAX_KEYS` (500), and for the whole library otherwise. `getServerPresenceForGroup` is the one-group form.

### Series identity

Episodes are stored, not shows, so a show is derived — and it is keyed on **`MediaItem.seriesKey`**, never on `parentTitle` (same-titled different shows — The Office UK vs US — would merge, blending the aggregates destructive rules read and letting a `DELETE_SONARR` resolve the wrong series).

- **The key** (`src/lib/media/series-key.ts`, the one shared helper): `computeSeriesKey` returns `tvdb:<id>` → else `tmdb:<id>` → else `title:<lower(trim(parentTitle))>`, from the **series-level** external ids every episode stores (the sync resolves show-level Guids via `grandparentRatingKey`). `resolveSeriesKey(row)` prefers the stored column and recomputes only for a row that predates it. `seriesKeySqlExpression()` is the SQL twin (backfill, migration 0015). Keep the three in lockstep (`tests/integration/media/series-key-backfill.test.ts`).
- Not `grandparentRatingKey`: it is per server, so the same show on two servers would split. `seriesKey` merges the same show across servers (shared TVDB id) and separates same-titled shows.
- **Written by the sync**: `buildRowParams` in `sync-server.ts` (SERIES rows; others NULL) and the incremental sync; legacy rows are backfilled by `backfillSeriesKeys` in `runBackfillIfNeeded` at startup.
- **Read everywhere series group**: `series/grouped`, `seasons`, `series`, `all-seasons`, `watch-history` (accept `seriesKey`, legacy `parentTitle` fallback), `group-summary`, `search`; the query engine's grouped SQL and its actions route; both rule engines; the stats layer (`library-stats.ts`, `breakdown.ts`, `watch-analytics.ts`); `lifecycle/exception-guard.ts` (`protectionKey`); the Exceptions page grouping. Anything counting or ranking distinct shows keys on `seriesKey`. Series detail responses return `seriesKey` for use as the React key and for the detail routes.
- The rule engines group **per library** (`libraryId::seriesKey`, in `evaluateSeriesScope`/`groupSeriesResults`/`aggregateEpisodesIntoSeries`) so a show on two servers stays two aggregates, which `detect-matches` collapses by Arr id. The library listings merge across servers by pure `seriesKey`.

### Artist identity

No artist-identity column exists: tracks carry the artist as `parentTitle`, and every track stores its ARTIST's MusicBrainz id as `MUSICBRAINZ`. `src/lib/media/artist-key.ts` (client-safe) holds the rules; `normalizeArtistTitle` (same function as `normalizeSeriesTitle`) is used by every artist-title comparison.

- **Grouping** (`splitArtistGroupByMbid`): the artist-scope engine (`evaluateMusicScope`) and Test Media group by `parentTitle`, splitting a title group by id ONLY when every track carries an id and there are two or more distinct ones. Any untagged track keeps the group whole.
- **One artist under two ids** is invisible to the grouping, so `executeDeleteLidarr` runs `refuseSplitArtistDelete` (`lifecycle/actions.ts`): it throws (FAILED) when Lidarr resolves another id carried by the same title in the library to the same artist, or when the title carries more than `MAX_SPLIT_ID_CHECKS` (10).
- **Whole-artist exception guard** (`protectionKeys` + `isGroupProtected` in `exception-guard.ts`, used by every protection check): an artist is known by its normalized title AND its id, and an exception protects a target sharing EITHER — over-blocking only skips a delete. `findExceptionProtectedGroups` looks exceptions up by the targets' ids and by title case-insensitively. `hasProtectionGroup` is the "has a group" gate. `protectionKey` remains the title/SERIES key.
- Display listings (artist view, server presence, Exceptions grouping, query batching) still group by normalized title; `collapseActionItems` keys an artist by its id.

### Naming series and episodes

An episode row's `title` is the episode's name; the show is `parentTitle`. Name TV items through `src/lib/media/display-title.ts` (client-safe):

- a **show** → `seriesTitleOf`;
- **one episode** → `formatEpisodeTitle` → `"<Show> SxxExx"` (unnumbered: `"<Show> — <episode title>"`), or `formatMediaItemTitle` for a row of any type; `formatEpisodeCode` is the bare `S01E02`. The episode's own title is fine only where the show is already on screen or as secondary detail.
- **lifecycle actions** → `actionTargetTitle` (`src/lib/lifecycle/action-target.ts`): named by the show, `"<Show> SxxExx"` only when the action acts on exactly one episode. That episode need not be the representative, so callers pass the members' rows as `memberEpisodes` (`loadMemberEpisodes` in `member-episodes.ts`, or rows `loadGroupMemberStats` already loaded). Used by the executor's logs and Discord summaries, `executeActionsForItems`, force-retry and the Pending rows (`buildActionMediaItem`); the name goes to `executeAction` as `targetTitle`. A run action is named from its snapshot (`snapshotTargetTitle`). `actionTitleSnapshot` is what every COMPLETED/FAILED write stores (`mediaItemTitle`/`mediaItemParentTitle`: a series action keeps its show, parent null; `mediaItemSeasonNumber`/`mediaItemEpisodeNumber` for a one-episode action only). The scheduled executor stores the members it actually acted on.
- **All Episodes grid** heads each card `"<Show> SxxExx"`, lists by show then SxxExx (`sortBy=parentTitle`), with the episode title as the extra line (`episodeTitle`); a season's grid uses `SEASON_EPISODE_TOGGLES`.
- **Playback sessions** carry `seasonNumber`/`episodeNumber` (episodes only); `formatSessionMediaTitle` names an episode from `grandparentTitle` — never `parentTitle` (the season there).

### Cross-bundle singletons

In a production build the job worker and the realtime manager (started from `instrumentation.ts`) load their own copy of every module, and the route handlers another. **Any in-process state both sides read or write — a bus, registry, cache, lock — must be pinned to `globalThis` unconditionally** (`globalForX.x ??= new X()`), never with the dev-only HMR idiom (`if (process.env.NODE_ENV !== "production") global… = …`), which is one object in dev and tests and two in production.

- `tests/unit/events/cross-bundle-state.test.ts` walks the import graph from `instrumentation.ts` and every route/page/layout and lists the module-level state of each module both load; each must be pinned or listed in its `ALLOWED` map with a reason.
- `tests/unit/events/no-dev-only-global-pin.test.ts` refuses the dev-only pattern under `src/` (only `src/lib/db.ts` is allowed).
- `tests/unit/events/process-singletons.test.ts` loads each shared registry twice under `NODE_ENV=production` — add new ones there. `e2e/realtime-push.spec.ts` runs the real production build.
- State only one side touches (e.g. the rate limiters) needs no pin. Pinning can change behaviour: the shared media-server circuit breaker (`health-cache.ts`) is why `testConnection` sends `BYPASS_BREAKER` + `NO_RETRY` (`tests/unit/media-server/connection-test-breaker.test.ts`) and `fetchImage` sends `NO_BREAKER_MARK`.

### In-Memory Cache

`appCache` (`src/lib/cache/memory-cache.ts`) — in-process (no Redis), not persisted, **pinned to `globalThis`** (`tests/unit/cache/memory-cache.test.ts`):

- `get<T>(key)`, `set(key, data, ttlMs?)`, `getOrSet(key, compute, ttlMs?, { shouldCache? })` — single-flight; an `invalidate`/`invalidatePrefix`/`clear` hitting a key mid-compute keeps that result out of the cache. Use `shouldCache(value)` to keep a bad result (a `partial` Seerr walk) out while still answering waiters — never cache-then-`invalidate`.
- `invalidate(key)`, `invalidatePrefix(prefix)`, `clear()`. Default TTL 60 s; bounded (`maxEntries`, expired-then-oldest).
- **Library listing responses** (`movies`, `series`, `music`, `series/grouped`, `series/all-seasons`, `music/grouped`, `music/albums/all`, and their v1 mirrors) are cached under `media-list:` (`LIST_RESPONSE_CACHE_PREFIX`, `src/lib/cache/list-response-prefix.ts`) by `withListResponseCache(name, handler)` (`src/lib/api/cached-list-response.ts`): 60 s, keyed by name + sorted query, the gzipped body kept (decompressed for callers without gzip), only 200s ≤ 8 MB, bounded by `LIST_RESPONSE_CACHE_MAX_ENTRIES` (24) and `LIST_RESPONSE_CACHE_MAX_TOTAL_BYTES` (48 MB), identical concurrent requests sharing one run, unauthenticated requests passed straight through.
- Other users: `resolveServerFilter`, `recently-added:` (`/api/media/recently-added`), `watch-history-filters:` (10 min), `stats:` (10 min), `group-summary:` (e.g. `/api/media/[id]/series-summary`, 5 min), `integration-metadata:` (60 s, not media-derived), `arr-metadata:`/`seerr-metadata:` (45 s, preview only).
- **Always call `invalidateMediaCaches()`** (`src/lib/cache/invalidate.ts`) after any mutation that changes media items, server membership, dedup canonical selection, or title/artwork preference — sync, purge, server CRUD, the library enable/disable route (`PUT /api/servers/[id]/libraries`), the dedup/title-preference settings routes. It drops every media-derived prefix: `server-filter:`, `stats:`, `group-summary:`, `cross-tab:`, `custom-stats:`, `timeline:`, `distinct-values` (incl. `distinct-values:genres`), `watch-history-filters:`, `recently-added:`, `image-meta:`, `query-action-live:`, `query-distinct-values`, `media-list:` (`tests/unit/cache/invalidate.test.ts`). Never hand-roll partial invalidation. Rule set create/rename/delete calls `invalidateRuleSetNameCaches()`.

### Filter Utilities

`src/lib/filters/build-where.ts` centralizes media filter logic:

- `applyCommonFilters(where, params, genreSpellings?, resolutionSpellings?, { resolutionOtherIncludesNull? })` mutates a `Prisma.MediaItemWhereInput` from the standard params. Multi-select values are pipe-separated (`?resolution=4K|1080P`); condition filters are `op:value` pairs with logic (`?yearConditions=gte:2020|lte:2024&yearLogic=and`). `applyStartsWithFilter(where, field, startsWith)` handles `#` and A–Z.
- **Every user-supplied value that lands in a LIKE-shaped comparison goes through `escapeLike`** (`src/lib/filters/escape-like.ts`, re-exported from `conditions/where-builder.ts`) — Prisma `contains`/`startsWith`/insensitive `equals` and raw `ILIKE` all treat `%`/`_` as wildcards (list `search`, `contains` multi-selects, `startsWith`, `media/search`'s `q`, the history ILIKEs, `system/logs`, the language filters). Escape at the site of use, never in a parser (double escaping searches for a backslash).
- **Genre is case-insensitive**: pass every stored spelling (`loadGenreSpellings`, `src/lib/filters/genre-spellings.ts`, cached under `distinct-values:genres`) as the third argument; each selected genre ORs `array_contains` over its spellings.
- **Every number and date is clamped to its column's range** (`int` ±2^31, `bigint` ±2^63, float ±1e308, dates 0001-01-01 – 9999-12-31), keeping its meaning (`comparisonOpToFilter`, `intEqualsFilter`), so out-of-range input never 500s.
- **Track-count filters** (`audioStreamCountConditions`/`subtitleStreamCountConditions`, each with its `…StreamCountLogic`; movies only) go through `parseStreamCountFilters` + `filterIdsByStreamCounts` (`src/lib/filters/stream-count.ts`): one `unnest($1::text[])` LEFT JOIN over the ordered candidates, then the page is cut. Only Movies offers them (`MediaFilters`' `streamCountFilters`), and only the Series tab offers show-level filters (`seriesAggregateFilters`).

### Prisma and Database

- Import as `import { prisma } from "@/lib/db"`. The client is generated to `src/generated/prisma` (types: `@/generated/prisma/client`).
- `fileSize` is `BigInt`: serialize to string in API responses, convert back on the frontend.
- Production runs `prisma migrate deploy` then `prisma db push` (the entrypoint always runs both). Schema changes need a migration file for production (`prisma-migration` skill); dev uses `db push`.
- **Mind Postgres' JIT on new raw aggregates**: any statement whose estimated cost passes `jit_above_cost` (100,000) pays ~600 ms of compilation. Correlated per-row subqueries cross it easily (`EXPLAIN ANALYZE` shows a `JIT:` section). Prefer a join or a batched `id = ANY($1)` lookup.
- **A list as long as a library never goes into one `in` list** (32,767 bind parameters per statement; Prisma splits a lone `in` on a plain `findMany` but not on a `groupBy` or beside a relation filter or second list → P2029). Send ONE array parameter in raw SQL (`= ANY($1::text[])`) or slice through `inChunks`/`findInChunks` (`src/lib/conditions/in-chunks.ts`, `IN_CHUNK_SIZE` 10,000), inside one transaction when it must be all-or-nothing (`tests/integration/lifecycle/large-id-lists.test.ts`).
- **Indexes earn their place with an `EXPLAIN ANALYZE`**, recorded in the migration (see `0030_query_indexes`). An index no plan picks still costs every write.
- **Some indexes exist only in migration SQL** (`0030`): the expression index `MediaItem(type, LOWER(TRIM("parentTitle")))` and partial GIN trigram indexes on `title`/`parentTitle`/`albumTitle` (created in a guarded `DO` block that skips them with a NOTICE when `pg_trgm` is unavailable). The entrypoint's `db push` leaves expression/partial indexes alone (a plain undeclared index would be dropped; Prisma's `partialIndexes` preview would drop them unless declared). Databases built by `db push` alone (dev, test, e2e) lack them, so a plan measured there is not the production plan.

### Data Patterns

- TV episodes are individual `MediaItem` rows with `parentTitle` (series name), `seasonNumber`, `episodeNumber`; series identity is `seriesKey` (above).
- `LibraryType`: `MOVIE`, `SERIES`, `MUSIC`.
- External IDs (TMDB, TVDB, IMDB, MUSICBRAINZ, MBID) live in `MediaItemExternalId` — Arr correlation: movies via TMDB → Radarr, series via TVDB → Sonarr, music via the artist's MusicBrainz id → Lidarr.
- `WatchHistory` rows are play events — see "Watch history & Tracearr".
- Dynamic range normalizes to "Dolby Vision", "HDR10+", "HDR10", "HLG" or "SDR"; audio profile to "Dolby Atmos", "Dolby TrueHD", "DTS-HD MA", "DTS:X", etc.
- Calendar-day fields (`originallyAvailableAt`, `arrReleaseDate`, `arrInCinemasDate`, `arrFirstAired`, `lastEpisodeAiredAt`) are stored as UTC midnight, carry `dateOnly: true` (`DATE_ONLY_FIELDS` in `fields.ts`) and are displayed with `formatDateOnly`; instants use `formatDate`. A new calendar-day field must set the flag.

### Query table criterion columns

Every condition field can be a column in the Query page's table. `src/lib/query/column-fields.ts` (client-safe) derives the list from `CONDITION_FIELDS` minus fixed columns (`BUILTIN_COLUMN_FIELDS`). Values are fetched on demand by `POST /api/query/column-values` (`computeQueryColumnValues`, `src/lib/query/column-values.ts`) for the rows on screen and visible columns only, in the table view only. `ColumnValueLoader` (`src/lib/query/column-value-loader.ts`, wrapped by `useQueryColumnValues`) splits requests at `MAX_COLUMN_VALUE_ITEMS` (50,000) and drops answers for a result set that is no longer the latest. Scoped to enabled servers and the run's selection; a grouped series row is answered from its per-library aggregate (stream counts read null); Arr reads the run's selected instance, Seerr every enabled one; an unavailable source yields null plus a `warnings` entry. `tests/unit/query/column-values.test.ts` requires every condition field to be a fixed column or handled by `columnValueOf`.

### Rule Engine

- Rules are recursive `ConditionGroup`s (`src/lib/conditions/types.ts`) with AND/OR, stored as JSON in `RuleSet`. Rules and groups support `negate`; group negation is pushed down to rules before evaluation (`pushDownGroupNegation`, `src/lib/conditions/negation.ts`) so both phases share NULL semantics.
- **Legacy flat rule sets** are converted by `src/lib/rules/legacy.ts` (pure, client-safe): `legacyRulesToGroups` (engine; enabled rules only — a rule's `condition` connects to the NEXT rule: buckets split after each enabled AND rule, OR within, AND between) and `legacyRulesToEditorGroups` (editor; same buckets, disabled rules kept in place). Only enabled rules place bucket boundaries.
- **Two-phase evaluation**: Phase 1 converts rules to Prisma WHERE; Phase 2 post-filters in memory (Arr/Seerr metadata, stream aggregation, wildcards, array fields). Engines load only what a rule set reads: the three lifecycle engines (`evaluateLifecycleRules`, `evaluateSeriesScope`, `evaluateMusicScope`) load candidates with `omit: UNREAD_ITEM_COLUMNS` (cast/crew, tagline, original title, file path, playback bookkeeping), and streams only for a stream rule (`hasStreamRules`). Stream query groups' Phase 2 is `evaluateStreamQueryGroupInMemory` (`src/lib/conditions/stream-query-eval.ts`); every "lowest id" pick uses `compareIds` (`compare-ids.ts`).
- **The lifecycle engine (`src/lib/rules/lifecycle-engine.ts`) and the query engine (`src/lib/query/query-engine.ts`) share one implementation of both phases — fix operator/NULL semantics once, in the shared functions**:
  - Phase 1: the single `ruleToWhere` dispatcher in `src/lib/conditions/where-builder.ts` (both pass it to `buildGroupConditions`).
  - Phase 2 Arr/Seerr: `evaluateArrRule`/`evaluateSeerrRule` exported from `lifecycle-engine.ts` (`query/arr-filter.ts`, `query/seerr-filter.ts` are re-export shims).
  - JSON-array fields (`genre`, `labels`, `country`) are evaluated **only** in Phase 2 through `matchArrayField` (`src/lib/conditions/array-field-eval.ts`), **case-insensitive** for every operator, `[]` = empty. `genreLabelsHandler` returns `{}` and `hasArrayFieldRules` forces Phase 2, like `resolution`.
  - `hasExternalId` through `matchExternalIdField` (`external-id-eval.ts`); the NAME-LIST fields `arrTag`, `seerrRequestedBy`, `watchedByUser`, `matchedByRuleSet` through `matchNameListField` (`name-list-eval.ts`).
  - Shared evaluators return `boolean | null`: `null` = unknown operator, and the caller must then match nothing **without** applying `negate` (a `default: false` through `negate` fails open to match-all).
  - `watchedByUser` also has a Phase-1 clause (`watchHistory: { some|none }`): every value it hands an insensitive `equals` goes through `escapeLike` (that compiles to `ILIKE`); its `in` form compiles to `LOWER(col) IN (…)` and must NOT be escaped.
- **Stream language fields** (`audioLanguage`, `subtitleLanguage`) are fail-closed on absent data: an item with no KNOWN language of that type (none, `""`, `Unknown`) matches no operator, positive or negative, and `negate` does not flip that. Phase 1 ANDs a "has a known language of this type" conjunct onto the **finished** clause, after `applyNegate`, for `equals`/`contains`/`notEquals`/`notContains` (not `isNull`/`isNotNull`); Phase 2 bypasses `negate` there. Codec fields (`streamAudioCodec`) keep plain semantics.
- File size rules: user input in MB, converted to bytes for queries.
- **Series-aggregate fields** (`episodeCount`, `watchedEpisodePercentage`, …) are evaluated only against an aggregated series record. A SERIES rule using one goes through the aggregate path (`evaluateSeriesScope` / `aggregateSeriesAndFilter`) **regardless of `seriesScope`** — `hasSeriesAggregateRules` is part of the Phase-1 gate in both engines (`where-builder` returns `{}` for them). Preview and diff route `seriesScope=false` + an aggregate field through `evaluateSeriesScope(…, true)`, as detection and test-item do.
- **Cross-system fields** (`matchedByRuleSet`, `hasPendingAction`, `serverCount`) come from `fetchCrossSystemData(ids, { excludeRuleSetId })` and are enriched on every path: the series- and artist-scope engines, the query engine's grouped paths and test-item fold them across a group's members with `foldCrossSystemData` (matched by any, pending if any, highest server count), and the aggregate engines and the Query table carry the folded values. A grouped match's `itemData.memberIds` all count as matched (member lists intersected in JS — a SQL join of them hits JIT). **Has Pending Action** counts an action stored against the item, naming it in `matchedMediaItemIds`, or naming another copy (`copyIds` or same `dedupKey`), excluding **the evaluating rule set's own** actions (`excludeRuleSetId`, passed by detection, the diff, the preview and Test Media) so a rule set never cancels and reschedules its own action. The server-count `groupBy` goes out in 10,000-key slices (`inChunks`). The flat engine returns rows with the values on them so a match records them among its matched criteria.

### Lifecycle Processing Workflow

Three phases, orchestrated by `src/lib/lifecycle/processor.ts`.

**Phase 1 — Detection** (`detectAndSaveMatches` in `detect-matches.ts`)

- **Incremental** (default, the scheduler: adds new matches, removes stale ones) or **full re-evaluation** (atomic delete + recreate; "Re-evaluate All", or after a rule set edit clears its matches).
- **Run metadata** (`createRunMetadata`, `src/lib/lifecycle/run-metadata.ts`, decided up front from every rule set of the run): Arr metadata per owner, type and rule-set instance; Radarr custom-format scores (`/moviefile`, 100 ids a request, `MOVIE_FILE_QUERY_CONCURRENCY` 4) only when a rule set uses **Custom Format Score** (`hasCustomFormatScoreRules`); Seerr walked once per owner for every needed type. A failed read is remembered so later rule sets needing it skip at once. Detection and execution always read fresh; **only the rule editor's preview, diff and Test Media read through a 45 s single-flight cache** (`loadPreviewMetadata` in `preview-metadata.ts` → `fetchArrMetadataForPreview` under `arr-metadata:`, `fetchSeerrMetadataForPreview` under `seerr-metadata:`; a read with scores serves one without, never the reverse). `invalidateArrMetadataCache()` runs on Arr instance writes and after an execution run that attempted an action; Seerr's via `invalidateSeerrCaches()`. Test Media asks each in-scope instance for the one record (`fetchArrRecordForPreview`) unless a preview just cached the library.
- **A rule set's Arr criteria are read from its own `arrInstanceId`** (`resolveArrInstanceScope` in `fetch-arr-metadata.ts`) — the instance its action runs against. `fetchArrMetadata(userId, type, onProgress?, arrInstanceId?)`, `hasEnabledArrInstances(userId, type, arrInstanceId?)` and `checkLifecycleRuleEvaluability`'s fifth argument take it — pass it at every call site (`processLifecycleRules`, `runDetection`, `detectAndSaveMatches`, the run route, and the preview/test-item/diff routes from the editor's unsaved value; diff falls back to the stored one). A disabled scoped instance makes the rule set unevaluable. An id naming no instance of the family reads every enabled instance, oldest first, and a title on several keeps the oldest's record. `RuleSet.arrInstanceId`/`LifecycleAction.arrInstanceId` have no FK, so the Arr instance DELETE routes call `detachDeletedArrInstance` (`src/lib/arr/detach-instance.ts`) in the deleting transaction: PENDING actions bound to it are cancelled, its rule sets lose the id and have their action turned off (a "Do Nothing" action without tags stays on).
- **Evaluability guard** (`src/lib/lifecycle/evaluability.ts`, the single policy point; enforced by `processLifecycleRules`, `runDetection` and — defense in depth — `detectAndSaveMatches` via `checkLifecycleRuleEvaluability`; the preview/test-item/diff routes return its reason as a 400): an external dependency that cannot be answered must never be evaluated as empty (an empty map makes `foundInArr = false` vacuously true for the whole library).
  - Arr fields with no enabled instance of the family (or the scoped instance disabled) → skipped, matches untouched, warning logged. Seerr fields with no enabled Seerr instance → same.
  - Seerr fields on MUSIC are **permanently** unevaluable (`invalidForLibraryType: ["MUSIC"]` rejects them at create/update); detection **disarms** such rule sets (clears matches, cancels PENDING actions) and `executeLifecycleActions` cancels their actions as a backstop.
  - **Play activity**: a criterion reading play activity may only be answered where play activity is known. Every field marked `readsPlayActivity` in the registry (`watchedByUser`, `playCount`, `lastPlayedAt`, `seriesLastPlayedAt`, `latestEpisodeViewDate`, `watchedEpisodeCount`, `watchedEpisodePercentage`) triggers `hasPlayActivityRules` (`conditions/helpers.ts` for groups, `rules/lifecycle-engine.ts` for either shape); a new play-derived field must set the flag. `checkWatchHistoryCompleteness(userId, serverIds?)` is the shared check (also used directly by the query-actions route). A server is un-established when `MediaServer.watchHistorySyncedAt` is null (a **positive** marker: null = unknown) or when it is Tracearr-mapped with `tracearrBackfillComplete` false. Its `reason` names the server and which case applies (the rule editor mirrors it per server as `playHistoryFault`). **Pass `serverIds` at every call site** (`processLifecycleRules`, `runDetection`, preview/diff from body or rule set, `test-item` from the item's server, query-actions from `query.serverIds`).
  - `src/lib/media/watch-evidence.ts`: `markWatchHistoryEstablished(serverIds)` after every successful sync, even one finding no plays; `invalidateWatchHistoryEvidence(serverIds)` / `invalidateServersWithoutWatchHistory()` from **every path that destroys watch history in bulk** (it cascades with the media): the `/api/servers/[id]` PUT source switch, `/api/media/purge` (both branches), disable with `deleteData`, and `restoreBackup` (row-derived variant). **Every withdrawal needs a writer that can undo it** (the Tracearr importer re-establishes the marker at the end of any complete run).
  - The ad-hoc query-actions route has the analogous guard: it refuses Arr rules with no selected/existing Arr server for the action's type, Seerr rules with no enabled selected instance or on a MUSIC action, and un-established play history.
- Matches are enriched with `matchedCriteria`, `actualValues`, `arrId` and `servers[]`. `runDetection(userId, ruleSetId?, fullReEval?, failures?)` records rule sets whose evaluation threw in `failures`; `/api/lifecycle/rules/run` reports them in `skipped` (sanitised).
- **Grouped matches** record the episodes/tracks they act on in `itemData.memberIds` — a series match in either scope, an artist-scope music match. Scheduling copies them onto the action (`matchedMediaItemIds`), and the manual execute route reads them from the stored match for every scope.
- **Multi-server collapse**: when a rule set targets more than one server, matches resolving to the same Arr record (same TMDB/TVDB/MBID) collapse into one (merging `servers[]`), so a title never schedules two destructive actions or double-counts `deletedBytes`. Keyed on the Arr identity, not `dedupCanonical`. With Arr metadata fetched only items that resolved to an Arr record collapse; with none fetched, the collapse keys on the external id alone whenever an action is armed. Collection-only rule sets keep one match per server copy. **Track-scope music** keys on artist MBID + `dedupKey`, and with an artist-level action armed (`groupsTracksByArtist` in `cross-server-copies.ts`: any Lidarr action except member-scoped file deletes and Do Nothing) an artist's tracks fold into one match with `memberIds`.
  - The kept copy (`collapseCopies`, ranked by `copyRank`) is the one already matched, else one a held match lists in `copies`, else the lowest id — never the engine's unordered row order. The others go in `itemData.copies` (`id`/`libraryId`/`ratingKey`/titles) and in `RuleMatch.copyIds` (`TEXT[]`, GIN-indexed, written by every detection write; queried with `hasSome`). Consumers that are per copy: `buildContributionsFromMatches` (each server's own Plex collection), `fetchCrossSystemData`, and the rule diff.
  - **Carry-over**: when the kept copy stops matching while an absorbed copy still matches, the held match and its PENDING action MOVE to that copy (`mediaItemId` rewritten in place; a member-scoped action's members re-expressed by `dedupKey`), in both run modes, whatever the server count (`planActionCarryOver`, which never moves the Arr id).
  - Members merge as distinct items (a later copy's member with the same `dedupKey` is dropped).
  - `crossServerCopyKeys`/`arrIdSourceFor`/`copyIdsOf`/`arrExternalIdsOf` live in `src/lib/lifecycle/cross-server-copies.ts`, shared with `/api/lifecycle/rules/[id]/diff` (which uses the editor's unsaved `actionEnabled`/`actionType`, optional on `ruleDiffSchema`, and returns folded rows as `copyIds`).
  - Incremental runs rewrite a held match's `itemData` only when its members, servers or copies changed (`collapseFingerprint`) or its identity did (`identityFingerprint`, `match-identity.ts`: title, `parentTitle`, year, external ids), as one `UPDATE … FROM jsonb_to_recordset` per 500 matches (`REFRESH_CHUNK`); carry-over uses `updateMany`. Never `update` (P2025 on a row deleted mid-run rolls back the batch).
  - Detection records the Arr-family id on every match it stores (`arrExternalIdsOf`), so scheduling copies the id the item matched with.
- **An exception protects every copy of an item** (same `dedupKey` on any server/library): `findExceptedItemIds` (`exception-guard.ts`, candidate ids as ONE `= ANY($1::text[])` parameter, `dedupKey`s intersected in JS). Used by detection's individual-scope filter, the scheduled executor, the manual execute route, force-retry, the query-actions route and the rule diff. Grouped-scope filtering keys through `findExceptionProtectedGroups` + `protectionKey`. The exceptions POST (individual and bulk series/season/artist/album scopes) disarms exactly what the next detection run would drop (`disarmExcludedItems`) — never more — and removes the kept copy and every listed copy from the match's Plex collection, each in its own library (`removeItemFromCollections(…, libraryId)`). An excepted representative of a per-episode group is replaced by the lowest remaining member id.

**Phase 2 — Action scheduling** (in `processLifecycleRules`)

- Cancels PENDING `LifecycleAction`s for items no longer matched; creates new ones with `scheduledFor = now + actionDelayDays` (only when `actionEnabled`; `skipDuplicates: true`).
- Skips an item that already has a PENDING action **or** a COMPLETED/FAILED action with the **same config signature** (`actionConfigSignature`, `src/lib/lifecycle/action-signature.ts`: type, instance, quality profile, tags as sets, flags — not `actionDelayDays`), so non-destructive actions don't re-fire every cycle while a re-configured action does. Destructive (`DELETE*`) actions are always re-schedulable.
- **Episode coverage** (`coverageOf` + `uncoveredEpisodes`, `src/lib/lifecycle/episode-coverage.ts`): an episode-scoped Unmonitor/Search (series scope off, `ruleSetActsOnEpisodes`; the Query page's episode view sets `ActionRecord.episodeScope`) is blocked only for episodes a settled same-signature action of the rule set acted on — read per episode from every such action, not from the current representative. On a SERIES rule set the same coverage decides a whole-series non-destructive action; episodes matching later are scheduled as a new action carrying only them. Whether an action acts on its member list is `actsOnMembers(actionType, episodeScope)` (`action-types.ts`).
- The same signature and coverage rules drive the Pending page's "estimated" rows (`GET /api/lifecycle/actions`) and the pending-bytes estimate (`GET /api/lifecycle/stats`); the Pending page's Execute acts on exactly what the row lists (`episodesToExecute`).
- **Grouped-action hold**: `AppSettings.groupedActionsHeldUntil` (migration `0024`) is applied wherever a grouped action gets a date (`src/lib/lifecycle/grouped-action-hold.ts`: scheduling, the reschedule route, estimated rows); null on a new install, inert once passed.
- After **all** rule sets, `processLifecycleRules` calls `syncAllCollections(userId)` **once** (see "Plex Collections").

**Deletion ceiling** (`AppSettings.maxAutoDeleteItems`, `src/lib/lifecycle/delete-ceiling.ts`): opt-in limit on how many items one destructive run may act on. `null` (default) = unlimited; a non-positive value reads as `null`. Counted per run across all rule sets over `isDestructiveActionType` actions only, and it **holds the whole batch** rather than trimming. Enforced on all three bulk paths: `executeLifecycleActions` (blocked actions stay PENDING — the Pending page's Execute is the manual approval), `POST /api/lifecycle/actions/execute` and `POST /api/query/actions`. A held run notifies Discord (`src/lib/lifecycle/deletion-held-notice.ts`: a scheduled run every time, a hand-started one at most once per 15 min via a pinned stamp); `checkDeleteCeiling(userId, types, kind)` words the refusal per run kind.

**Phase 3 — Execution** (`executeLifecycleActions`)

- **Two passes**: pass 1 applies every cancel-or-narrow check (item existence, MUSIC+Seerr, exception, stale match, identity swap, member-set intersection, whole-record protection) and collects survivors; the deletion ceiling counts survivors only; pass 2 executes. Pass 1's cancellations are deleted in slices afterwards (`deleteMany`). Detection and execution read only the snapshot keys they use (`loadStoredMatches(ruleSetIds, keys)`, `loadStoredMatchMembers`, `src/lib/lifecycle/match-snapshot.ts`).
- **Identity-swap guard** (a Plex Fix Match / Jellyfin Identify rewrites a row to another work under the same id): before acting, the executor compares the action's own snapshot — `mediaItemTitle`/`mediaItemParentTitle`/`mediaItemYear`/`mediaItemExternalId` (written by `scheduleActionsForRuleSet`) — with the joined row via `matchIdentityChange` (`src/lib/lifecycle/match-identity.ts`), and on a change cancels the action **and clears that item's `RuleMatch`**. A grouped action's snapshot holds the GROUP (title = show/artist, parent null) against a representative episode/track — compare at the right level, never title to title. The snapshot lives on the action, not the match. Force-retry (`POST /api/lifecycle/actions/[id]`) runs the same check (409), narrows a member-scoped action's members to the current match's `memberIds`, drops excepted members, and refuses when none remain or a whole-record action has an excepted member.
- **Direct execution identity check**: `POST /api/lifecycle/actions/execute` compares each item with `RuleMatch.itemData` (title at the level Arr validates, the Arr-family id when the snapshot has one — a lost id is not a change — and the movie year ±1) and answers **409, executing nothing**, on a change; the refusal says to re-run detection, which re-snapshots via `identityFingerprint`. A snapshot without a title passes.
- **Whole-record exception guard** (`exception-guard.ts`): a whole-record destructive action (`DELETE_SONARR`/`DELETE_LIDARR`) is cancelled when ANY item of the same group carries an exception, even one never matched. The group is `protectionKey(item)` — **`seriesKey` for SERIES**, normalized artist title (+ id via `protectionKeys`/`isGroupProtected`) for MUSIC. Its lookup searches `parentTitle` OR `seriesKey` and re-keys through `protectionKey` (legacy rows collide via `seriesKeyFromTitle`). Enforced in the scheduled executor (batch-resolved once, skipped with no exceptions), the manual execute route, force-retry and the query-actions route.
- **Single-flight** (`src/lib/lifecycle/execute-in-flight.ts`, pinned set; `tryBeginExecute`/`endExecute`): the manual execute route and force-retry are scoped by rule set id — a run claims the whole scope (Execute All) or only its items — and the query-actions route by `query:<userId>`; a collision answers 409. The scheduled executor takes the same lock per item in pass 2 (an item held elsewhere stays PENDING). Query runs and rule-set runs exclude each other as whole runs: rule-set runs count themselves per user (`tryBeginRuleSetExecution`/`endRuleSetExecution`) and are refused while a query run holds `query:<userId>`; a query run claims through `beginQueryExecution`, waiting up to `QUERY_EXECUTION_WAIT_MS` (60 s) for counted rule-set runs. Under the item lock pass 2 re-reads the action and leaves for the next run one that is gone, not due, changed since load (`updatedAt`), on a disabled rule set, or newly protected (`newlyProtected`). Pass 1 cancels with `deleteMany`, pass 2 records with `updateMany`; a row removed mid-call has its result recorded as a new history row (`recordVanishedAction`; `recordHistory` in `run-actions.ts`). `tests/integration/lifecycle/execution-concurrency.test.ts`.
- Tag operations run first, then the main action. Title validation via `normalizeTitle()` stops acting on the wrong Arr record. `extractActionError()` extracts the HTTP status and body.
- Completed actions record `deletedBytes` (`MediaItem.fileSize` or the sum over members; a whole-series delete sums every episode of the show in its library by `seriesKey`). Deletion stats: `GET /api/lifecycle/stats`; reset via `POST /api/lifecycle/stats/reset` (`AppSettings.deletionStatsResetAt`).
- **The ad-hoc query-actions route** (`/api/query/actions`) refuses an action on any instance but the query's own (`arrServerIds[family]`) or a disabled one when the query uses Arr criteria; collapses items to one action per Arr record (`collapseActionItems`, `src/lib/query/collapse-actions.ts`, members unioned); checks the deletion ceiling against the whole run (client-sent `runUnits` from `countActionUnits` in `src/lib/query/batch.ts`, plus a per-`runId` total, answering `stopped: true` past the ceiling); `buildActionBatches` keeps an artist's tracks in one batch and the client refuses an oversized show for a whole-record action (`oversizedActionGroup`); records already acted on are remembered per `runId` (`src/lib/query/run-records.ts`, pinned store) and skipped. Tag changes on a whole-record delete (`deletesArrRecord`) → 400. **The query engine leaves out a media type whose Arr criteria nothing can answer** (`resolveQueryArrScope` in `fetch-arr-data.ts`) and says why in `QueryResult.warnings`.

**Lifecycle listings**

- `GET /api/lifecycle/actions` (Pending) reads PENDING actions, settled non-destructive actions, action-enabled match keys and lookups (`loadActionLookups`) in parallel, and loads full match rows only for matches with no action yet. Group rows are rolled up with `src/lib/lifecycle/group-aggregate.ts` (`loadGroupMemberStats`, `aggregateGroupMembers` — `null` for a movie — and `memberIdsFromItemData`), shared with `/api/lifecycle/rules/[id]/diff`; totals come from the members' current rows. A row without `matchedEpisodes` renders as an episode in `MediaTable` and the side panel.
- `GET /api/lifecycle/rules/matches` reads each snapshot as `"itemData"::text` and splices `detectedAt` in (`matchItemJson`, `src/lib/lifecycle/match-json.ts`, `jsonTextResponse`), ordered `detectedAt DESC, id`. The Completed/Failed/All listing picks the newest action per (rule set, item) with `DISTINCT ON` (`latestActionIdPerPair`). `GET /api/lifecycle/exceptions?idsOnly=1` answers `{ mediaItemIds }`.

**Rule set edits**: a PUT clears all `RuleMatch` rows and cancels all PENDING actions by default. `clearMatches=false` (config-only save) keeps matches and re-snapshots the action config onto PENDING actions — except when `arrInstanceId` changes on a rule set with Arr fields, or `seriesScope` changes, which always clear (the editor counts both in `rulesChanged`).

### Plex Collections (merge)

A `Collection` is a reusable Plex-collection definition (`name`, `sortName`, `homeScreen`, `recommended`, `sort`) scoped to one `LibraryType`; a `RuleSet` references it via optional `collectionId` (`onDelete: SetNull`), and several rule sets may share one.

- **Union membership**: `syncCollection(collection, contributions, cache)` (`src/lib/lifecycle/collections.ts`) sets membership to the union of every contributing rule set's matches — **never sync a collection per rule set**.
- **Driven from `RuleMatch`**: `syncCollectionById(id)` builds contributions from every enabled assigned rule set's persisted matches (`buildContributionsFromMatches`); an orphaned collection resolves to an empty union (removing it on Plex). `syncAllCollections(userId?)` does every collection in scope.
- **Ordering**: `ACTION_DATE` sort pools PENDING actions of all contributing rule sets, so collection sync runs **after** action scheduling (`processLifecycleRules` after its loop; the manual path via `syncCollectionsAfterDetection` from `/api/lifecycle/rules/run`).
- **Fewest Plex calls**: a pass shares a `CollectionSyncCache` (`collection-sync-cache.ts`) keyed by **library id**; settings Plex already holds are not rewritten; `ACTION_DATE` uses the fewest `move`s (`planCollectionMoves`). Exclusions go through `removeItemsFromCollections(userId, removals)`, grouped by library and collection (`removeItemFromCollections` is the one-entry form). Every write is preceded by `markSelfWrites` (see "Realtime & events").
- **CRUD**: `GET/POST /api/lifecycle/collections`, `PUT/DELETE /api/lifecycle/collections/[id]` (PUT renames on Plex + re-syncs; DELETE removes from Plex and detaches rules), `POST /api/lifecycle/collections/sync` (`{ collectionId }`). Managed from the rule editor's collection dropdown. `RuleSet` has no inline collection settings (migration `0010_add_collections`).

### AI Analysis

Read-only natural-language assistant over the library (`/tools/ai`, `src/lib/ai/`), configured in Settings → AI (`AppSettings.aiEnabled/aiProvider/aiBaseUrl/aiApiKey/aiModel`).

- **Provider-neutral, no SDK**: `provider.ts` is a thin axios client for `openai-compatible` (OpenAI, Ollama, LM Studio, OpenRouter, Groq, vLLM, LocalAI, …) and native `anthropic`. `aiBaseUrl` is admin-set (no SSRF block — local models live on private IPs).
- **Safety model**: the model can call only the fixed read-only tools in `tools.ts` (no mutating tools); tools take structured, Zod-shaped args (never model-written SQL) and delegate to `src/lib/media/*` + `executeQuery`, inheriting scoping and dedup. `search_media` excludes Arr/Seerr fields (vacuous-match hazard). The system prompt treats tool-result text as data.
- **Grounding**: `system-prompt.ts` is built from the field/dimension registries and forbids inventing numbers; scope is the user's library and watch history only.
- **Orchestration**: `analyst.ts` runs a bounded (≤ 6 iterations) tool-calling loop, streaming `status`/`tool` events via `progressStreamResponse`, returning `{ answer, evidence }`. Routes: `GET/PUT /api/settings/ai` (key masked; PUT skips `MASKED_VALUE`; can't enable without a model), `POST /api/settings/ai/test` (rate-limited), `POST /api/ai/chat` (streaming, `aiRateLimiter`, requires enabled + configured). `config.ts` resolves the config.

### Backup & Restore

`src/lib/backup/backup-service.ts`:

- `createBackup(passphrase?, configOnly=true)` exports tables in FK order (`BACKUP_TABLE_ORDER`), gzips, optionally encrypts (AES-256-GCM; `.json.gz.enc`, else `.json.gz`). A table that cannot be read fails the backup (no file, no prune). Files are mode `0600`, with sidecar `.meta.json` (incl. `configOnly`) so `listBackups()` needn't decompress. `getBackupPassphrase()` returns the saved password; the POST falls back to it.
- **Every table must appear in `BACKUP_TABLE_ORDER`** — restore truncates `"User" CASCADE`, so an omitted table is destroyed and never restored. `tests/unit/backup/table-order.test.ts` pins the list and `BACKUP_EXCLUDED_TABLES` to Prisma's `ModelName`, so a new model must be placed on purpose. `tableToDbName` derives table names from delegate names (no model uses `@@map`). **`ApiKey` is deliberately excluded**: a backup never carries key material and a restore revokes every key (`tests/integration/backup/api-keys-excluded.test.ts`).
- Config-only (default) skips `mediaItem`, `mediaItemExternalId`, `mediaStream`, `syncJob`, `ruleMatch`, `lifecycleAction`, `lifecycleException`, `watchHistory`, `logEntry`; full backup (`configOnly=false`, "Include media data") includes all.
- `restoreBackup(filename, passphrase?, onProgress?)` truncates in reverse FK order and re-inserts in batches of 100 in one transaction, streaming NDJSON progress. A failing TRUNCATE throws naming its table. **A restore never undoes a session revocation**: every restored user gets `sessionVersion = max(file's, in-use, seconds since 2024) + 1` (`revokeRestoredSessions`, `sessionVersionFloor`; `tests/integration/backup/restore-revokes-sessions.test.ts`). Values go to Prisma as the file holds them (`restore-string-values.test.ts`). `deserializeRow` drops columns the schema no longer has (via Prisma's `ScalarFieldEnum`). A rule set referencing a collection the file lacks is detached. Restore also invalidates watch-history evidence (see Lifecycle).
- **Create, download and restore need a recent sign-in** (see step-up); listing, deleting, scheduled backups and the setup-time `list-setup`/`restore-setup` routes (`SETUP_BUCKET` rate limit) do not. `GET /api/backup/[filename]` sends `Cache-Control: no-store` (`tests/integration/backup/file-permissions.test.ts`).
- Persistent paths are under `/config`: backups `/config/backups`, image cache `/config/cache/images` (`BACKUP_DIR`, `IMAGE_CACHE_DIR`, `LOG_ARCHIVE_DIR` override).

### Background Jobs (Graphile Worker)

- [Graphile Worker](https://worker.graphile.org/) (Postgres-backed) runs **in-process**, started from `src/instrumentation.ts` (guarded by `NEXT_RUNTIME === "nodejs"`). `startWorker()` is awaited so its `graphile_worker` schema migrations (needs `CREATE` privilege; untouched by `prisma db push`) apply before any enqueue. `instrumentation.ts` also starts the maintenance/preroll enforcers (30 s loops, deliberately outside the queue) and `startRealtime()`.
- **Boot recovery**: `cleanupOrphanedSyncJobs()` (the app's own `SyncJob` rows) is awaited and caught before `startWorker()`; `startWorker()` then calls `recoverOrphanedWorkerLocks()` to clear `locked_at`/`locked_by` on `_private_job_queues`/`_private_jobs` before the runner starts — with one in-process worker any lock at boot is orphaned, and a locked `MAIN_QUEUE` otherwise stalls every job for 4 hours.
- **Static crontab** (`src/lib/jobs/worker.ts`): the dispatcher every minute, action cleanup every 15 min, log archival hourly. Cleanup ages COMPLETED/FAILED actions by `executedAt` (`createdAt` only when null), then prunes `SyncJob` (`pruneSyncJobs`, own try/catch): finished jobs older than `SYNC_JOB_RETENTION_DAYS` (30) AND beyond the server's newest `SYNC_JOB_KEEP_PER_SERVER` (50); never PENDING/RUNNING.
- **Dispatcher** (`dispatch.ts`): reads the DB-stored schedules (`AppSettings.syncSchedule`, `lifecycleDetectionSchedule`, …) and enqueues due work. Heavy jobs (sync, lifecycle detection/execution, backup, Tracearr backfill) share the serial `MAIN_QUEUE`; the dispatcher and housekeeping omit a queue. Jobs use a `jobKey` to dedup and retry with backoff. The `lastScheduled*`/`lastBackupAt` watermark advances only **after** a successful enqueue (dispatcher and the manual route).
- `src/lib/jobs/`: `tasks.ts` (handlers), `client.ts` (`enqueueJob()`, `queuedSyncJobIds`, `isJobRetrying`), `schedule.ts` (`presetToCron`, `isScheduleDue`, `getSystemTimezone`, `isValidSchedule` — node-cron AND cron-parser must both accept an expression; the three schedule routes validate with it). `isScheduleDue` evaluates fixed-hour schedules on the server's local wall clock (a repeated DST hour runs once, a skipped one runs as the clock passes it) and logs once per process a schedule it cannot evaluate.
- Manual triggers enqueue durable jobs: sync (see "Sync engine"), and "Run Now" for detection/execution (`/api/settings/schedule-info/run`) on `MAIN_QUEUE` with jobKeys `detection:<userId>` / `execution:<userId>`. `syncMediaServer` also self-serializes via `sync-semaphore.ts` for any inline caller.
- Tasks: `TASK_SYNC_SERVER`, `TASK_SYNC_INCREMENTAL`, `TASK_SYNC_WATCH_HISTORY` (refreshes only watch history, reconciles, invalidates caches; skips itself when a full sync is running/queued), `TASK_TRACEARR_BACKFILL`, lifecycle detection/execution, backup — details under "Sync engine" and "Watch history & Tracearr".

### CI/CD

- `.github/workflows/ci.yml` — lint, test, build on pushes to main and PRs.
- `.github/workflows/release-please.yml` — on push to main runs release-please; a created release builds and pushes the Docker image with `latest` + semver tags.
- `.github/workflows/docker-nightly.yml` — on push to `main` (or manual dispatch) pushes the rolling `nightly` tag and immutable `nightly-<sha>` tags; never `latest`/semver.
- `.github/workflows/docker-publish.yml` — manual Docker Hub publish.
- `.github/workflows/e2e.yml` — Playwright compose stack on PRs.
- `.github/workflows/docs-deploy.yml` — docs site.
- `.github/workflows/pr-title-lint.yml` — validates every PR **title** against Conventional Commits (see below).

### Git Conventions

- Husky pre-commit runs `pnpm exec eslint --quiet`; commit-msg enforces [Conventional Commits](https://www.conventionalcommits.org/) via commitlint (`@commitlint/config-conventional`).
- Format: `type(scope): description` — e.g. `feat: add stream manager`, `fix(auth): handle expired tokens`.
- **Every PR title MUST be a Conventional Commit from the moment the PR is opened**, whoever creates it: `type(scope): description` or `type: description`, `type` one of `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `revert`, `style`, `test`; description starts lowercase, no trailing period. Good: `fix(auth): confirm identity in place instead of requiring sign-out`. Bad: `Add in-place re-authentication for sensitive actions`. Model it on the branch's own commit subjects. When updating a PR, check its title too.
- Squash-merging makes the PR title the commit subject on `main`, which release-please reads for the version bump and changelog — a non-conventional title drops the PR from the release. `pr-title-lint.yml` enforces it.
