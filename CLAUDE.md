# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Librariarr is a media library management webapp for Plex, Jellyfin, and Emby servers. It uses Plex OAuth for authentication, syncs media metadata from connected servers, provides filterable library browsing, and includes a lifecycle rule engine for automated media management.

**Librariarr is a single-user (single-admin) application.** Setup permits exactly one admin account, enforced by the `AppSettings.userId @unique` schema constraint and the setup gate in `src/app/api/auth/setup/route.ts`. A second user cannot exist. Do not add multi-tenant defensiveness — no per-user cache keys, no "cross-tenant leak" tests, no "tenant isolation" comments. See "Single-user model" under Critical Conventions for details.

### Testing

Requires the Docker DB to be running (`pnpm docker:dev` or `pnpm docker:dev:detach`).

```bash
pnpm test                    # Run full test suite
pnpm test:watch              # Watch mode
pnpm test:unit               # Unit tests only (no DB needed)
pnpm test:integration        # Integration tests only (requires DB)
pnpm test:coverage           # Run with coverage report
pnpm exec vitest run tests/path/to/file.test.ts  # Run a single test file
```

**Framework:** Vitest 4 with real PostgreSQL test database (`librariarr_test`), auto-created by global setup.

**Test structure:**

- `tests/setup/` — Global setup, test DB client, session mocks, data factories
- `tests/unit/` — Pure logic tests (rules engine, filters, sync detection, formatting, caching, validation schemas)
- `tests/integration/` — API route handler tests against real DB with mocked external services

**Key patterns:**

- Every integration test mocks `@/lib/db` to use test Prisma client and `@/lib/logger` to suppress DB writes
- External services (Plex, Sonarr, Radarr, Lidarr) are mocked via `vi.mock()`
- Auth is mocked via `setMockSession()` / `clearMockSession()` from `tests/setup/mock-session.ts`
- Constructor mocks must use `function()` keyword, not arrow functions (Vitest 4 requirement)
- Use `vi.hoisted()` when mock variables are referenced inside `vi.mock()` factory functions
- Route handlers are tested directly: `callRoute(GET, opts)` or `callRouteWithParams(POST, { id }, opts)`
- `expectJson<T>(response, status)` — parse response JSON + assert status in one call
- Data factories in `tests/setup/test-helpers.ts`: `createTestUser`, `createTestServer`, `createTestLibrary`, `createTestMediaItem`, `createTestRuleSet`, `createTestSonarrInstance`, `createTestRadarrInstance`, `createTestLidarrInstance`, `createTestSeerrInstance`, `createTestExternalId`, `createTestLogEntry`

**Config:** Tests run sequentially (`pool: "forks"`, `fileParallelism: false`) to prevent DB contention. Test timeout 15s, hook timeout 30s. Coverage scope: `src/lib/**/*.ts` and `src/app/api/**/*.ts` only.

**Test coverage requirement:** Every new or modified file under the coverage scope must have tests. In practice that means: every new route handler under `src/app/api/` gets an integration test in `tests/integration/`, and every new module under `src/lib/` gets a unit test in `tests/unit/`. Unit-level lib coverage is necessary but not sufficient — route handlers compose multiple lib modules with session state, validation, rate-limiting, and DB writes, and bugs hide in those seams. When the lib is fully covered but the route isn't, the route isn't tested.

## Architecture

**Stack:** Next.js 16 (App Router) · React 19 · TypeScript · PostgreSQL 18 · Prisma 7 · Tailwind CSS v4 · shadcn/ui · Docker

### Route Structure

- `src/app/(authenticated)/` — All protected pages. Auth enforced by layout.tsx which validates session and redirects if invalid.
  - Dashboard (`/`), System Logs (`/system/logs`)
  - Settings (`/settings`) — `page.tsx` is the orchestrator (all state + handlers); 7 tab components in `settings/tabs/` are pure render receiving props; shared types in `settings/types.ts`; tab navigation via URL hash (`#general`, `#servers`, etc.)
  - Library: `/library/movies`, `/library/series` (with `/seasons` and `/episodes` sub-routes), `/library/music`. The series `show`/`season`/`episode` detail pages each render `PlayHistory` (`src/components/play-history.tsx`) over `GET /api/media/series/watch-history` — the per-play list (user / date-time / episode) for the whole series, one season, or one episode. On the show/season pages it is a full-width section; on the episode page it is passed as `MediaDetailContent`'s `historySection` slot (`variant="card"`), which **replaces** the built-in per-user aggregate Watch History card and skips that card's live `/api/media/[id]/history` fetch — an episode gets one history section, not the same plays twice. **Movies and tracks get the same per-play card**, scoped to one item: `/library/movies/[id]` and `/library/music/track/[id]` pass `<PlayHistory variant="card" mediaItemId singleItem />` through the same `historySection` slot, backed by **`GET /api/media/[id]/plays`**. They were on the aggregate card until then, which is why the Tracearr detail was visible on the History page and on episodes but not on a film — a `where`, not a data, gap. `singleItem` drops the title line (every row names the item whose page you are on) and `PlayRow` links out only for a row whose `mediaItem.type` is SERIES, since `/library/series/episode/<id>` 404s for a movie. **`MediaDetailSidePanel` fills the same slot** for whichever row was opened — series identity + season/episode for an episode (so a second server's plays merge in, exactly as on the episode page), its own id otherwise — so opening an item from any library or lifecycle list shows per-play rows instead of `MediaDetailContent`'s built-in per-user aggregate. That aggregate card now renders only for a caller that leaves the slot empty, and a filled slot skips its live `/api/media/[id]/history` fetch (`hasHistorySection`), so the panel no longer round-trips the media server on open. Every one of these lists **pages 5 plays at a time** (`PAGE_SIZE` in `play-history.tsx`) rather than appending, through the shared `src/components/pagination-controls.tsx` — first/prev/typed-page-number/next/last, which `/library/history` renders too so the two can't drift. It is **centred, never flush right**: these controls end a page, and the fixed `BackToTop` button (`right-6`, 40px wide) covers the corner a right-aligned Next button would sit in. Last/Next are disabled off `totalCount`, not the API's `hasMore`, since a typed page number needs the page count anyway; `multiServer` is therefore derived from the servers seen across every page loaded in the current scope, not from the rows on screen, or the server chips would blink out on a page whose five plays happen to share a server. The two routes share `src/lib/media/play-history.ts` — `PLAY_HISTORY_SELECT`, `serializePlayRow`, `fetchPlayHistory`, `parsePlayHistoryPaging` — and differ ONLY in how they resolve which `MediaItem`s are in scope (series identity vs a single id, each applying its own ownership guard). Kept shared because a column added to one and not the other silently shows enriched detail on series pages and omits it on movies, which is exactly how the gap arose. That route matches the series on **`seriesKey`** — the **same series-identity key `/api/media/series/grouped` groups shows by** (see "Series identity" below) — so two genuinely different shows that share a title stay separate, while the same show on two servers still merges (shared TVDB-derived key) and keeps every server's plays. It accepts a `seriesKey` query param (preferred; the detail pages pass `item.seriesKey`) and still falls back to the legacy `parentTitle` param (matched case/space-insensitively) when no key is given. It resolves the in-scope episode ids first, then filters `WatchHistory` by `mediaItemId`, which also keeps the history query on the `WatchHistory(mediaItemId)` index. Every user's plays are included — `session.userId` is the Librariarr admin who owns the server record, not a media-server account, and nothing filters on `serverUsername`. It reads the stored `WatchHistory` table and deliberately does **not** apply dedup: a row is a real play event recorded against the copy that was actually played, so filtering to `dedupCanonical` would drop every play that happened on a non-canonical server. `/api/media/[id]/history` answers a different question (per-user aggregate for ONE item, fetched live from the server, no per-play timestamps, none of the Tracearr detail) and is **not** a substitute for `/api/media/[id]/plays` — the two are deliberate siblings, and `/history` remains the right answer where nothing is stored
  - Lifecycle: `/lifecycle/rules` (unified rules page with Movies/Series/Music tabs), `/lifecycle/matches`, `/lifecycle/pending`, `/lifecycle/exceptions`
  - Tools: `/tools/streams` (Stream Manager: active sessions, maintenance mode, transcode manager, blackout schedules), `/tools/preroll` (Preroll Manager: presets, schedules, combine modes), `/tools/trash` (TRaSH Guide Sync: import custom formats / quality profiles / quality sizes / naming from trash-guides.info into Sonarr/Radarr with an explicit per-item consent gate, diff preview, and dry-run), `/tools/ai` (AI Analysis: read-only natural-language assistant over the library — see AI Analysis below)
- `src/app/login/` and `src/app/onboarding/` — Public pages
- `src/app/api/` — API routes (all require authenticated session except auth endpoints)
  - `api/tools/sessions/` — Active session fetching, SSE streaming, termination, artwork proxy
  - `api/tools/maintenance/` — Maintenance mode toggle with configurable delay
  - `api/tools/transcode-manager/` — Transcode manager settings and criteria
  - `api/tools/blackout/` — Blackout schedule CRUD (one-time and recurring)
  - `api/tools/preroll/` — Preroll presets, schedules, path validation
  - `api/integrations/tracearr/` — Tracearr instance CRUD, `[id]/test-connection`, `[id]/servers` (the Tracearr-side server list the per-media-server watch-history mapping picks from), and `status` — per mapped server `{ backfillComplete, importedCount, oldestImported, newestImported, oldestPlayAt, backfillFraction }`, the UI's only signal for how far the background history backfill has got (see `TASK_TRACEARR_BACKFILL` below for what `backfillFraction` measures, and why a `null` fraction is not `0`)
  - `api/tools/trash/` — TRaSH Guide Sync: `instances` (Sonarr/Radarr picker), `catalog` (guide fetch + naming variants + custom-format list), `profiles` (the instance's quality profiles + current CF scores, plus `instanceFormatNames` — every CF name present in the app, so the UI can flag an assigned format that isn't in the app yet), `status` (per-item cross-reference), `assignments` (the consent gate — opt resources into management), `sync` (dry-run/diff or apply, writes only managed resources). Resource types: `CUSTOM_FORMAT`, `QUALITY_PROFILE`, `QUALITY_DEFINITION`, `NAMING`, and `PROFILE_CF` (overlay guide custom-format scores onto any quality profile — keyed by profile name, non-destructive to the rest of the profile)

### Key Libraries

- `src/lib/db.ts` — Prisma singleton (import as `@/lib/db`, NOT `@/lib/prisma`)
- `src/lib/auth/session.ts` — iron-session encrypted cookies (30-day expiry)
- `src/lib/validation.ts` — Zod schemas + `validateRequest` helper for all API mutation routes (see API Validation below)
- `src/lib/cache/memory-cache.ts` — In-process `MemoryCache` class with `appCache` singleton (see In-Memory Cache below)
- `src/lib/dedup/` — Multi-server dedup: `resolveServerFilter`, `server-presence` helpers (see Multi-Server Dedup below)
- `src/lib/filters/build-where.ts` — Shared filter query param parsing for media routes (see Filter Utilities below)
- `src/lib/plex/` — Plex OAuth flow and API client
- `src/lib/sso/` — OIDC (Authorization Code + PKCE) and forward-auth helpers. Manual-linking only: an admin must link an `ssoSubject` to a User before SSO login is accepted. When `AppSettings.ssoEnabled` is true, the local username/password form is hidden on the login page (Plex login remains by default). `AppSettings.plexLoginEnabled` (default true) independently controls whether the Plex login button is shown — toggling it off hides Plex from the login page without unlinking the Plex token from the User record (so server discovery and library sync still work). `/api/settings/auth` enforces a unified lockout guard: at least one of Plex login, local auth, or SSO must remain usable post-update.
- `src/lib/sync/sync-server.ts` — Media sync engine (fetches metadata from Plex)
- `src/lib/sync/watch-reconcile.ts` — Reconciles the `WatchHistory` table into the two denormalized columns the rule/query engines actually read, `MediaItem.playCount` / `lastPlayedAt`. Necessary because the item sync derives those from **account-scoped** server metadata (Plex `viewCount`/`lastViewedAt` are the admin token's own views; Jellyfin/Emby `UserData` is fetched with the admin `UserId`, and `JellyfinBase.getWatchCounts()` returns an empty map by design) while `WatchHistory` comes from the **server-wide, per-user** `getDetailedWatchHistory()`. Without it the History page could show an episode played two months ago while `lastPlayedAt` — and therefore `seriesLastPlayedAt` (**Series Last Played**), `watchedEpisodeCount` and `watchedEpisodePercentage` — still reported the admin's own view from two years earlier, arming destructive lifecycle rules against a series the household was actively watching. Both helpers are **monotonic** (`GREATEST` / `Math.max`), mirroring `buildItemData`'s existing max of metadata-vs-history: a server that prunes its history can never make an item look *less* recently watched. `reconcileWatchStateFromHistory(serverId)` runs at the end of every `syncWatchHistory` (non-fatal — the rows are already committed) **and** directly in `syncMediaServer` whenever `skipWatchHistory` is set — the per-library fan-out from `/api/sync/by-type` defers the one server-wide scan to a follow-up `TASK_SYNC_WATCH_HISTORY` job, so without the stored-history reconcile those runs would leave every item they upserted reporting the connected account's own last play; `loadWatchCountsFromHistory(serverId, ratingKeys)` gives the incremental sync the `watchCounts` map `processBatch` expects, sourced from stored history instead of a live server-wide scan. **Both helpers restrict their aggregate to `watched IS DISTINCT FROM false`** — `watched = true` (a Tracearr chain past its completion threshold) or `watched IS NULL` (a native row; the server only ever reports finished plays, so those count exactly as they always did). It is `IS DISTINCT FROM false` and not `= true` precisely because the native path leaves the column NULL. A Tracearr row can describe a 4%-watched abandoned play — or a stream still running right now — and must be stored and shown on the History page while staying out of these two columns: the writes are monotonic `GREATEST`, so **one** such row pins `lastPlayedAt` to "just now" *permanently*, with no later sync able to walk it back, and through it `seriesLastPlayedAt`, `watchedEpisodeCount` and `watchedEpisodePercentage`. That silently disarms every "not played in N months" rule set — the exact failure this module exists to prevent, inverted. The predicate must stay in **both** helpers: they answer the same question by different routes (one set-based `UPDATE`, one `Map` fed into `buildItemData`), so fixing only the reconcile leaves the next incremental sync re-inflating both columns from partial rows. Change both or neither
- `src/lib/sync/sync-server.ts` — the media sync engine. Its one raw `INSERT … ON CONFLICT` (`buildUpsertSql`, shared with the incremental sync via the exported `processBatch`) writes **`playCount` and `lastPlayedAt` with `GREATEST`, never a bare `= EXCLUDED`** (`GREATEST_ON_UPDATE`). Every other writer of those two columns is already monotonic — both `watch-reconcile.ts` helpers, and the Tracearr importer's own merge — and this is what makes that stated invariant actually true rather than merely intended. Both of `buildItemData`'s inputs can legitimately read zero for an item somebody else watched: Plex metadata carries only the admin token's `viewCount`, `JellyfinBase.getWatchCounts()` returns an empty map by design, and `loadWatchCountsFromHistory` returns nothing while `WatchHistory` is empty — which it deliberately is, for hours, from the moment a server's watch-history source is switched until the newest-first Tracearr re-import reaches back. A plain overwrite there wrote `playCount = 0, lastPlayedAt = null` over the real values for every item only another household member had watched, and the trailing reconcile could not undo it (monotonic over a table that is, at that moment, empty). Unlike `watchedByUser`, these two feed `playCount = 0` and "not played in N months" DELETE rules that the evaluability guard does **not** gate, so nothing else stands between that and a whole-library delete. Postgres `GREATEST` ignores NULLs, so a null on either side simply yields the other. The guarantee is scoped to play state on purpose — making titles, file sizes or resolutions monotonic would freeze them at their first-seen values
- `src/lib/media-server/item-types.ts` — `isMediaItem`/`partitionMediaItems`: the **non-media container guard**. Collections, box sets and playlists are not `MediaItem`s (no file, no streams, no size) — storing one creates a phantom row that pollutes listings, dedup, stats and lifecycle matches. Plex is the leaky server: `/library/sections/{key}/all` returns the section's collections unless an explicit `type` is sent, and librariarr *creates* Plex collections itself (`lifecycle/collections.ts`), so its own output would round-trip back in. Fixed server-side in `PlexClient.getLibraryItemsPage` (movie now sends `type=1`, not "no type") — filtering server-side rather than dropping from the response keeps `totalSize` consistent with the page, which the sync's paging and stale-purge accounting depend on. `sync-server.ts` and `sync-incremental.ts` apply the guard as defense-in-depth; in `sync-server.ts` skipped containers **still count toward `libraryItemCount`/`processedItems`** (the server counted them in its total) or the stale-item purge would be permanently disabled, and the page offset advances by the **raw** page size. It's a deny-list, not an allow-list — an unknown-but-real media type must keep syncing. Separately, `isItemForLibraryType` enforces that a library only ever stores its own item type (MOVIE→`movie`, SERIES→`episode`, MUSIC→`track`): the **full** sync gets this free from its one-type-per-library server-side filter, but the **incremental** sync fetches whatever ratingKeys a `library-changed` event carried — and one new episode makes Plex emit timeline entries for the episode, its season *and* its show (same for Jellyfin's `LibraryChanged.ItemsAdded`), which are real media that `isMediaItem` passes. Anything the full sync wouldn't have listed must not be written by the incremental sync either, or it's a phantom row until the next full sync purges it. In `sync-server.ts`, `libraryItemCount` (real media upserted, drives the "server returned nothing — refuse to wipe" guard) and `librarySeenCount` (every row traversed incl. containers, compared against the server's reported total) are deliberately **separate counters** — merging them lets an all-container listing pass the zero-item guard and wipe a populated library
- `src/lib/jobs/` — [Graphile Worker](https://worker.graphile.org/) background job queue (Postgres-backed), initialized via `instrumentation.ts`. `worker.ts` runs the in-process worker + static crontab; `dispatch.ts` is the per-minute dispatcher that fans DB-configured schedules into durable jobs; `tasks.ts` holds the task handlers; `client.ts` exposes `enqueueJob()`; `schedule.ts` has the pure cron/preset helpers (`presetToCron`, `isScheduleDue`, `getSystemTimezone`)
- `src/lib/rules/` — Lifecycle rule engine with recursive AND/OR groups
- `src/lib/arr/` — Sonarr/Radarr/Lidarr API clients (15s timeout, title validation via `normalizeTitle()`)
- `src/lib/trash/` — TRaSH Guide Sync engine: `catalog.ts` fetches + caches the guide JSON (from `raw.githubusercontent.com`, overridable via `TRASH_GUIDES_REPO`/`TRASH_GUIDES_REF`); `arr-guide-client.ts` is a focused Sonarr/Radarr v3 client for custom-format/quality-profile/quality-definition/naming endpoints (separate from `src/lib/arr` core clients); `translate.ts` converts guide JSON → Arr payloads (pure, unit-tested — CF field object→array, quality-profile builder resolving qualities/groups/cutoff/CF-scores against the live schema, plus per-profile options mirroring Recyclarr — `scoreSet` override and opt-in `resetUnmatchedScores` with exact-name/regex exceptions, both stored on the QUALITY_PROFILE managed row's `selection`; size + naming appliers); `diff.ts` + `signature.ts` power the change preview and upstream-change detection; `status.ts` cross-references guide↔instance↔managed rows; `sync.ts` builds the plan and applies it. **Consent gate**: nothing is written to an Arr app for a resource without a `TrashManagedResource` row; `sync.ts` only ever writes managed resources (dry-run `items` are preview-only), and taking over an item that already exists requires explicit confirmation in the UI
- `src/lib/media/watch-completion.ts` — the single definition of "a `WatchHistory` row that counts as a play", in both dialects (`completedPlaySql(alias)` for raw SQL, `COMPLETED_PLAY_FILTER` for Prisma relation filters). Exists because `WatchHistory` gained a second provenance whose rows can be partial: every consumer written when the table only held finished plays has to opt in to the same predicate, and Phase 1 and Phase 2 of the `watchedByUser` rule must use the *identical* one or the rule matches a different set depending on whether something else in the rule set forced in-memory re-evaluation. `IS DISTINCT FROM false` rather than `= true`, and an explicit `OR [true, null]` rather than Prisma's `not: false`, because both must admit the NULL a native row carries — silently excluding those would make a `watchedByUser` rule match nothing at all on an install with no Tracearr mapping
- `src/lib/tracearr/` — Tracearr (self-hosted Plex/Jellyfin/Emby playback monitor) as an alternative watch-history source. `tracearr-client.ts` is the read-only API client (axios, no SDK, mirroring `seerr-client.ts`) and deliberately spans **two API versions**: `/api/v1/public/health` for connectivity *and* the media-server list (v2 has no health route, and `HealthResponse.servers[]` is the only place the `server_id` UUIDs `MediaServer.tracearrServerId` stores are enumerated), `/api/v2/public/history` for the plays themselves (v1's `SessionHistory` carries **no media identifier at all** — only title strings — so it cannot be joined to a `MediaItem` without title guessing, while v2's `HistoryRecord` carries `rating_key` plus TVDB/TMDB/IMDB ids and is keyset-paginated with `since`/`until`, which is what makes an incremental import possible — but **newest-first** (a keyset on `started_at` descending), so the walk goes new → old and a lone forward watermark cannot express resume; see the two-boundary design under `TASK_SYNC_WATCH_HISTORY` below. It also **excludes any play whose sessions never reached 2 minutes**, so a very short play is absent from the API and therefore from `WatchHistory` — never read a missing row as a join failure). It retries a 429 exactly once with a bounded delay (the limiter is a rolling 1-minute window so a 429 is always transient, but a paging loop must stay bounded) and throws `IntegrationError` otherwise. **A `HistoryRecord` is an aggregate over a resume chain, not an immutable event**: `id` is the chain id, and resuming a play folds a new segment into the *same* `id`, moving `state`/`stopped_at`/`progress_ms`/`duration_ms`/`percent_complete`/`segment_count`/`watched` — so the import must UPDATE the stored row on a repeat sighting rather than skip it, and `segment_count` is the only field that reveals a resume (`reference_id` is documented as the chain key but currently just equals `id`). `findOldestPlayAt(tracearrServerId, { signal?, floor? })` answers the one question the keyset API otherwise cannot — *where does this server's history start* — by **bisecting the `until` filter** (ask for one record older than a candidate instant; empty means the history starts after it) at **hour precision**, rather than paging to the end: measured against a live instance, **19 calls for a 7-year history** versus ~1,600 pages. Returns `null` for a server Tracearr holds no plays for. `syncTracearrHistory` calls it **once per server**, at the start of a backfill pass, and stores the result on `MediaServer.tracearrOldestPlayAt` (migration `0017_add_tracearr_backfill_state`, alongside `tracearrBackfillComplete`); it is **best-effort** — a failure is logged and the pass continues, leaving progress merely indeterminate for that run rather than failing an import over a progress number. `src/lib/sync/tracearr-join.ts` resolves a record to one of our rows and is the genuinely dangerous half — see `TASK_SYNC_WATCH_HISTORY` below
- **Import progress is PUSHED, not polled.** `syncTracearrHistory` emits `tracearr:import-progress` (`meta.serverId`) on the app `eventBus` after each page **commits** — after, so a listener that refetches can never read a figure the run has not durably written — and once more, unthrottled, at the end of the run so the terminal state (final count, backfill just finished) always lands even if the throttle swallowed the last page. `/api/events/stream` forwards it, filtered by `userId`, and `useRealtime("tracearr:import-progress", …)` on the Settings and History pages refetches `GET /api/integrations/tracearr/status`. The event deliberately carries **no figures**: the status route stays the single place the readout is computed, and numbers on the event could silently disagree with it. Emission is **throttled to 2s per server** (`IMPORT_PROGRESS_THROTTLE_MS`, a module-level map so a fresh backfill slice cannot let its first page through unthrottled) because the archive walk commits a page roughly every second over thousands of pages and each event costs every listening client one status query. A **slow 30s poll remains, but only as the fallback for a dropped stream** — SSE dies to proxy buffering and idle timeouts, and this readout is the sole indication a multi-hour walk is progressing, so it must not depend entirely on a connection staying up. What it replaced was polling gated on `backfillComplete === false`, which meant a forward-pass import on an already-backfilled server (most syncs) updated nothing at all while the server rows beside it refreshed every two seconds
- `src/lib/sync/watch-history-progress.ts` — the progress contract both watch-history provenances report through (`WatchHistoryProgress`, `WatchHistoryProgressReporter`, `formatPlayCount`). A watch-history sync is the one sync a user waits on in the **foreground** — the History page's **Refresh** button runs it inline, and a first Tracearr import pulls a server's entire history — so `POST /api/media/history/sync` returns an NDJSON progress stream via `progressStreamResponse` (`src/lib/progress/`, the same protocol as the query page, the lifecycle rule preview and AI chat), with **one phase per server** (`key` = the server id, `label` = the server name) and the terminal result payload unchanged from before (`{ success: true, counts }`, a failed server still `-1`). **The determinate/indeterminate split is deliberate, not an oversight**: the native path learns its total the moment `getDetailedWatchHistory()` returns, so its write loop reports a genuine `i / total` `fraction`; the Tracearr path never learns one — `/api/v2/public/history` is keyset-paginated and its `CursorMeta` carries only `nextCursor`/`pageSize`, with no count endpoint and no total in the response — so it **omits** `fraction` and reports a live imported/pages count instead, which `useStreamProgress` renders as an indeterminate bar (`determinate: update.fraction !== undefined`). Never synthesise a percentage to fill that gap: it would be a guess at how much history a server holds, presented as a measurement. Both `syncWatchHistory(serverId, onProgress?)` and `syncTracearrHistory(serverId, onProgress?)` take the reporter **optionally**, precisely because the scheduled dispatcher, the realtime `TASK_SYNC_WATCH_HISTORY` job and `syncMediaServer` have no client to report to — progress must never be load-bearing for correctness

Uses the `ws` package; the socket is injected (`SocketFactory`) so the connection/manager are unit-testable without real sockets. Reconciles on `server:changed`/`settings:changed` app events (emitted by the server CRUD + `/api/settings/realtime` routes) plus a 60s safety pass. The sessions SSE stream (`/api/tools/sessions/stream`) subscribes to `realtimeBus` for instant pushes (throttled), falling back to its 5s poll when realtime is off. `GET /api/tools/realtime/status` exposes per-server connection state

## Critical Conventions

### Single-user model

Librariarr runs with exactly one admin account. This is enforced by:

- **Schema**: `AppSettings.userId @unique` in `prisma/schema.prisma` — the DB rejects a second admin row.
- **Setup gate**: `src/app/api/auth/setup/route.ts` and `src/app/api/auth/plex/token/route.ts` reject creating a second user (see the "single-admin app" comment in the latter).
- **Check-setup**: `src/app/api/auth/check-setup/route.ts` uses `findFirst()` because there is one and only one admin.

Code references `session.userId` because per-user resources (`MediaServer`, `RuleSet`, `LifecycleAction`, etc.) carry a `userId` FK — that's a normal Prisma relation, not a signal that more than one user could be present concurrently. **Never** add per-user cache keys, multi-tenant invalidation patterns, or "no cross-tenant leak" tests. If you find yourself writing one, stop and reread this section.

### API Request Validation

All mutation routes use centralized Zod validation via `src/lib/validation.ts`:

```typescript
import { validateRequest, someSchema } from "@/lib/validation";
const { data, error } = await validateRequest(request, someSchema);
if (error) return error;
```

- All Zod schemas live in `src/lib/validation.ts` — do not define schemas inline in route files
- Uses `zod/v4` subpath import
- Returns `{ error: "Validation failed", details: [...] }` with status 400 on validation failure
- Returns `{ error: "Invalid JSON in request body" }` with status 400 on malformed JSON

### API Response Security

All API routes that return server/integration records must wrap responses in `sanitize()` from `src/lib/api/sanitize.ts`:

```typescript
import { sanitize } from "@/lib/api/sanitize";
return NextResponse.json({ server: sanitize(server) });
```

- Recursively masks `accessToken`, `apiKey`, `plexToken`, `passwordHash`, `backupEncryptionPassword`, `oidcClientSecret`, `aiApiKey` fields with `"••••••••"` (exported as `MASKED_VALUE`)
- Error responses use `sanitizeErrorDetail()` to strip internal file paths and private IPs
- Integration edit flows use server-side `[id]/test-connection` endpoints (POST to `/api/integrations/{type}/{id}/test-connection`) instead of sending stored API keys to the frontend
- Auth endpoints (login, Plex init/callback) are rate-limited via `authRateLimiter` — check before processing, return 429 with `Retry-After` header
- Media queries must verify ownership: use `findFirst` with `library: { mediaServer: { userId: session.userId } }` instead of bare `findUnique({ where: { id } })`

### API Pagination

Media list endpoints support pagination via query params:

- Query params: `page` (1-based, default 1), `limit` (default 50, capped at 100-200; `0` = return all), `offset`, `sortBy`, `sortOrder`
- The flat list routes (`movies`, `series`, `music`) parse these through the shared `parseListPagination` in `src/lib/api/pagination.ts`, which returns `{ page, limit, skip }`. `offset`, when given, **overrides** the page-derived skip and applies even when `limit=0` — that combination ("everything after the first N") is what makes progressive loading possible; without it the only way to express it is to refetch the whole list
- **Every pageable list route must order by a total order** — the flat routes append `{ id: "asc" }` after the user-selected sort. Without a unique tiebreaker Postgres may return tied rows in any order, and two requests over the same data are planned differently (a bounded first page uses a top-N heapsort, an unbounded remainder uses quicksort or an external merge). The tie block straddling the page boundary then permutes between the requests, so a stitched list shows some rows twice and silently drops others — reproduced at 80 duplicated / 80 missing out of 20k rows, and regression-tested in `tests/integration/media/movies.test.ts` ("stable ordering")
- N+1 trick: fetch `limit + 1` items; if `items.length > limit`, pop last item and set `hasMore: true`
- Response shape: `{ items: [...], pagination: { page, limit, hasMore } }`
- `startsWith` param for server-side alphabet filtering (A-Z letters, or `#` for non-alpha titles)
- List state is typed `MediaListItem` (`Omit<MediaItemWithRelations, "summary">` in `src/lib/types.ts`), so reading a summary the list endpoint never sent is a **compile error** rather than a silently blank popover. `MediaTable` is generic over its row type with `MediaListItem` as the floor, so callers with richer rows (the lifecycle preview) keep their own type in the table's callbacks
- List payloads deliberately **exclude `summary`** — it is a paragraph of prose per row and only the hover popover renders it, so `MediaHoverPopover` fetches it for the single hovered item via its `summaryUrl` prop (module-level cache, fetched on open because the popover only mounts when open). Everything else in the popover comes from data the list already carried, so it still paints instantly

**Frontend loading strategy:** Main library views render through `@tanstack/react-virtual`. The flat, DB-paginated views (movies, all-episodes, all-tracks) load in two passes via `fetchListProgressively` (`src/lib/media/progressive-load.ts`): a first screenful (`FIRST_CHUNK_SIZE`, 100) paints immediately, then `limit=0&offset=100` fills in the rest, so nothing is transferred twice. Consumers that need the complete list — the header item count and `useScrollRestoration` — gate on the page's `loadingRest` flag rather than `loading`, or a restore to a deep index would land in a list that doesn't reach it yet. The **grouped** views (series grouped, music artists, albums, all-seasons) deliberately stay single-request: they aggregate the whole library in memory before slicing, so a second pass would re-run that aggregation for no earlier paint. Alphabet navigation uses client-side `scrollToLetter` from the alphabet hooks. The detail sub-views (a season's episodes, an album's tracks) fetch their whole child list in one `limit=0` request — they are bounded by the parent, so there is nothing to page.

### Multi-Server Dedup

When users connect multiple servers, dedup prevents duplicate items from appearing:

- `resolveServerFilter(userId, serverId, libraryType)` from `src/lib/dedup/server-filter.ts` — **required first step** for all media query routes. Returns `{ serverIds, isSingleServer, preferredTitleServerId, ... }`
- When `isSingleServer` is false, add `where.dedupCanonical = true` to filter to the preferred copy
- `dedupKey` is a normalized hash of item metadata; `dedupCanonical = true` marks the preferred copy across servers
- `getServerPresenceByDedupKey` (flat routes like movies) and `getServerPresenceByGroup` (grouped routes like series/music) attach a `servers[]` array showing which servers have each item. For SERIES, `getServerPresenceByGroup` keys by `seriesKey`; for MUSIC it keys by normalized `parentTitle` (there is no artist-identity column)

### Series identity

Librariarr stores episodes, not shows, so "which show does this episode belong to" is derived. It is keyed on **`MediaItem.seriesKey`**, never on the ambiguous `parentTitle` — two genuinely different shows that share a title (The Office UK 2001 vs US 2005, Battlestar Galactica 1978 vs 2004) would otherwise collapse into one series everywhere, blending `episodeCount` / `watchedEpisodePercentage` / `seriesLastPlayedAt` that drive destructive lifecycle rules, and letting a `DELETE_SONARR` resolve the wrong Sonarr series.

- **The key** (`src/lib/media/series-key.ts`, the single shared helper): `computeSeriesKey` returns `tvdb:<id>` → else `tmdb:<id>` → else `title:<lower(trim(parentTitle))>`, from the **series-level** external ids every episode already stores (the sync resolves show-level Guids via `grandparentRatingKey`, not the episode's own id). `resolveSeriesKey(row)` prefers the stored `seriesKey` column and recomputes from `parentTitle`+`externalIds` only for a row that predates the column. `seriesKeySqlExpression()` is the SQL twin used by the backfill and migration 0015 — keep the three in lockstep (asserted by `tests/integration/media/series-key-backfill.test.ts`).
- **Why not `grandparentRatingKey`**: it is per-server, so the same show on two servers would split. `seriesKey` keeps the same show merging across servers (shared TVDB id → shared key — the cross-server watch-history merge depends on this) while separating same-titled different shows (distinct ids).
- **Written by the sync**: `buildRowParams` in `sync-server.ts` computes `seriesKey` for SERIES rows from the same show-level Guids it uses for external-id persistence (movies/tracks get null); the incremental sync writes it too (its authoritative source, the show Guids, is fetched). Legacy rows are backfilled set-based by `backfillSeriesKeys` in `runBackfillIfNeeded` on startup.
- **Read everywhere series group**: `/api/media/series/grouped` (`group_key = seriesKey`), `seasons`/`series`/`all-seasons`/`watch-history` (accept a `seriesKey` query param, `parentTitle` kept as a legacy fallback), `group-summary`, `search`; the query engine's grouped-series SQL (`GROUP BY mi."seriesKey"`) and its ad-hoc actions route; both rule engines; and the **stats/analytics** layer — `library-stats.ts` (top-series `groupBy(["seriesKey"])`, and the series/season/genre `COUNT(DISTINCT …)` keyed on `seriesKey`), `breakdown.ts` (the JSON-array distinct count), and `watch-analytics.ts` (`computeWatchTrends` groups SERIES by `seriesKey`). Anything counting or ranking *distinct shows* keys on `seriesKey`; MUSIC (artist) still keys on `parentTitle` — there is no artist-identity column. The engines group **per library** (`libraryId::seriesKey`, in `evaluateSeriesScope`/`groupSeriesResults`/`aggregateEpisodesIntoSeries`) so a show on two servers stays two aggregates that `detect-matches` collapses by Arr id — merging them there would double-count episodes. The library grouped/presence/watch-history routes merge across servers by pure `seriesKey` (that is the desired dedup). Series detail responses (`grouped`, `all-seasons`) also return `seriesKey` so the frontend uses it as the React key and passes it back to the detail routes.

### In-Memory Cache

`appCache` from `src/lib/cache/memory-cache.ts` — in-process cache (no Redis), does not persist across restarts:

- `appCache.get<T>(key)`, `set(key, data, ttlMs?)`, `getOrSet(key, compute, ttlMs?)` (compute-and-cache, **single-flight**: concurrent misses for the same key share one `compute()` call)
- `invalidate(key)`, `invalidatePrefix(prefix)` (bulk invalidation by namespace), `clear()`
- Default 60s TTL; the store is **bounded** (evicts expired-then-oldest past `maxEntries`) so a long-running process can't grow unbounded
- Used by `resolveServerFilter`, available-letters endpoints, and other read-heavy paths
- **Always call `invalidateMediaCaches()` from `src/lib/cache/invalidate.ts`** after any mutation that changes media items, server membership, dedup canonical selection, or title/artwork preference — it drops every media-derived prefix (`server-filter:`, `stats:`, `letters:`, `group-summary:`, `cross-tab:`, `custom-stats:`, `timeline:`, `distinct-values`, `watch-history-filters:`) in one call. Used by sync, purge, server CRUD, and the dedup/title-preference settings routes. Do not hand-roll partial invalidation — it's the recurring source of stale-listing bugs.

### Data Patterns

- TV series episodes are stored as individual `MediaItem` records with `parentTitle` as the series name, `seasonNumber`, and `episodeNumber`. **Series identity is keyed on `MediaItem.seriesKey`, never on `parentTitle`** (see "Series identity" below)
- `LibraryType` enum: `MOVIE`, `SERIES`, or `MUSIC`
- External IDs (TMDB, TVDB, IMDB) stored in `MediaItemExternalId` table — used for Arr correlation
- Arr matching: Movies via TMDB ID → Radarr, Series via TVDB ID → Sonarr
- A `WatchHistory` row is **one play event**, not a per-item aggregate (that's `MediaItem.playCount`/`lastPlayedAt`, reconciled from these rows by `watch-reconcile.ts`). `source` is the provenance discriminator — `"NATIVE"` (the server's own history API; also the migration default, which correctly tags every pre-existing row) or `"TRACEARR"` — and it decides which columns can be trusted. Native rows populate only `serverUsername`/`watchedAt`/`deviceName`/`platform`; every column below is null on them. Tracearr rows add `sourceEventId` (Tracearr's stable resume-chain `id`, the dedup key behind `@@unique([mediaServerId, sourceEventId])` — null for native rows, and Postgres treats nulls as distinct in a unique index, so native rows never collide there) and `referenceId` (the documented chain key, which currently always equals `id`, so `segmentCount > 1` is what actually reveals a resumed play); the completion set `watched`/`percentComplete`/`state`/`progressMs`/`durationMs` (watch time summed across the play's in-window segments)/`totalDurationMs` (the item's full runtime — the denominator the other two are measured against)/`segmentCount`/`stoppedAt`; the client set `player`/`product`; and the stream set `isTranscode`/`videoDecision`/`audioDecision`/`bitrate` (kbps)/`resolution`/`sourceVideoCodec`/`sourceAudioCodec`/`streamVideoCodec`/`streamAudioCodec` plus three Json columns — `transcodeInfo` and `subtitleInfo` stored verbatim, and `streamQuality` bundling the source_/stream_ video+audio detail objects with their display strings (full fidelity without 20+ scalar columns). **`watched` is the load-bearing one**: it is Tracearr's completion verdict (85% threshold by default, configurable there), it is nullable *on purpose* so a native row reads as "counts, exactly as it always did". The predicate that acts on it lives in exactly one place, `src/lib/media/watch-completion.ts`, in both dialects — `completedPlaySql(alias)` for raw SQL and `COMPLETED_PLAY_FILTER` for Prisma — and its consumers gate on it: both helpers in `watch-reconcile.ts`; the `watchedByUser` rule field in *both* of its evaluation phases (the Phase-1 relation filter in `conditions/where-builder.ts` and the Phase-2 `watchHistory` eager loads in both engines, which must agree or the rule matches a different set depending on whether something else forced in-memory re-evaluation); the **removed-item eager load in `/api/lifecycle/rules/[id]/diff`**, which re-runs the Phase-2 evaluator to annotate `matchedCriteria`/`actualValues` and so must load the same rows Phase 1 kept — otherwise the preview a user reads *before* saving a rule edit that arms a DELETE explains an item with evidence the engine never saw; and **both** Seerr watch-correlation paths — `src/lib/seerr/request-stats.ts` (the aggregate counts) and `/api/seerr/users/[userKey]/requests` (the per-user list), which read the same table for the same user and would otherwise disagree about whether one request was watched. Storing partial plays silently redefines any consumer written when every row was a finished play, so a new one must adopt the predicate deliberately. `watch-analytics.ts` (trending/leaderboards) deliberately does **not**: it measures engagement, where starting something is real signal, and nothing there feeds a destructive rule. See the `watch-reconcile.ts` bullet under Key Libraries for why a `false` row reaching `playCount`/`lastPlayedAt` is unrecoverable
- Dynamic range detection: normalizes to "Dolby Vision", "HDR10+", "HDR10", "HLG", or "SDR"
- Audio profile detection: normalizes to "Dolby Atmos", "Dolby TrueHD", "DTS-HD MA", "DTS:X", etc.

### Rule Engine

- Rules are recursive `RuleGroup` structures with AND/OR operators, stored as JSON in `RuleSet`. Rules and groups support `negate`; group-level negation is normalized away before evaluation by `pushDownGroupNegation` (`src/lib/conditions/negation.ts`, De Morgan push-down into per-rule negation) so both evaluation phases share NULL semantics
- Two-phase evaluation: Phase 1 converts rules to Prisma WHERE clauses, Phase 2 post-filters in memory for Arr/Seerr metadata, stream aggregation, and wildcard pattern matching
- **The lifecycle rule engine (`src/lib/rules/lifecycle-engine.ts`) and the query builder (`src/lib/query/query-engine.ts`) share one implementation of both phases** so they can't drift: Phase 1 goes through the single `ruleToWhere` dispatcher in `src/lib/conditions/where-builder.ts` (both engines pass it to `buildGroupConditions`), and Phase 2 Arr/Seerr evaluation uses the exported `evaluateArrRule`/`evaluateSeerrRule` from `lifecycle-engine.ts` (the query side's `query/arr-filter.ts` / `query/seerr-filter.ts` are thin re-export shims). The JSON-array fields (`genre`, `labels`, `country`) are evaluated **only** in Phase 2, through the shared `matchArrayField` in `src/lib/conditions/array-field-eval.ts` — **case-insensitive** for all operators (regression-tested as "Bug 5"), matching the scalar-text convention, and treating a stored `[]` as empty. `genreLabelsHandler` returns `{}` and `hasArrayFieldRules` forces Phase 2 in both engines, exactly like `resolution`: Prisma's `array_contains` is case-sensitive with no insensitive form, so the SQL path disagreed with the evaluator on any value whose case differed from the stored tag — and `notContains`/`notEquals` disagreed by matching EVERY row. `/api/media/distinct-values` builds the dropdown with a case-sensitive `SELECT DISTINCT`, so a multi-server library really does offer "Sci-Fi" and "sci-fi" separately. The list-shaped fields follow the same rule: `hasExternalId` through `matchExternalIdField` (`external-id-eval.ts`) and the four NAME-LIST fields — `arrTag`, `seerrRequestedBy`, `watchedByUser`, `matchedByRuleSet` — through `matchNameListField` (`name-list-eval.ts`). Each previously had a hand-written operator switch (two of them duplicated byte-for-byte across both engines) and they drifted: `matchedByRuleSet` and `seerrRequestedBy` had no `matchesWildcard`/`notMatchesWildcard` cases while their siblings did, so those rules hit the `default` and matched NOTHING in both directions with no error. These shared evaluators return `boolean | null` — `null` means "unknown operator", and the caller must then match nothing **without** applying `negate` (a `default: false` fed through `negate` fails open to match-all). The two engines previously carried divergent inline copies (the query side compared case-sensitively), so keep this one shared. When fixing operator/NULL semantics, fix it once in these shared functions.
- **Stream language fields** (`audioLanguage`, `subtitleLanguage`) are **fail-closed on absent data**: an item with no KNOWN language of that type (no stream, or only `""`/`Unknown`) matches NO operator, positive or negative, and `negate` does not flip that — `"Unknown" != "English"` must not read as true. Phase 2 bypasses `negate` there like every other dead-rule guard; Phase 1 matches it by ANDing a "has a known language of this type" conjunct onto the **finished** clause, **after** `applyNegate`, for the four value operators (`equals`/`contains`/`notEquals`/`notContains`) — `isNull`/`isNotNull` are excluded because they *are* that question. Putting the conjunct inside the individual `notEquals`/`notContains` branches instead left every `negate: true` form failing open: a bare `NOT { streams: { some: … } }` is satisfied by a row with no such stream, so `NOT (audioLanguage equals German)` matched every item with no audio track — and a group-level NOT produces exactly that via `pushDownGroupNegation`. Phase 2 only runs when something else in the rule set demands it, so without that conjunct the same `subtitleLanguage notEquals English` rule matched a **different set** depending on an unrelated rule beside it — on a DELETE rule set, a different set of files. Codec fields (`streamAudioCodec`) carry no placeholder set and deliberately keep the plain semantics.
- File size rules: user inputs in MB, engine converts to bytes for DB queries
- **Series-aggregate fields** (`episodeCount`, `watchedEpisodePercentage`, …) can only be evaluated against an aggregated series record, never per-episode. A SERIES rule referencing one is routed through the aggregate path (`evaluateSeriesScope` in lifecycle, `aggregateSeriesAndFilter` in query) **regardless of `seriesScope`** — `hasSeriesAggregateRules` is part of the Phase-1 gate in both engines so the aggregate conjunct is never silently dropped from `where-builder` (which returns `{}` for aggregate fields)

### Lifecycle Processing Workflow

The lifecycle system operates in three phases, orchestrated by `src/lib/lifecycle/processor.ts`:

**Phase 1 — Detection** (`detectAndSaveMatches` in `detect-matches.ts`):

- Two modes: **incremental** (default — adds new matches and removes stale ones) and **full re-evaluation** (atomic delete + recreate all matches)
- Incremental mode is used by the scheduler; full re-eval is triggered manually via "Re-evaluate All" button or when a rule set is edited (clears all matches so next run starts fresh)
- Items that no longer match are automatically removed from `RuleMatch` during incremental runs
- Fetches Arr/Seerr metadata lazily and caches per type (Movie/Series/Music) to share across rule sets
- **Evaluability guard** (`src/lib/lifecycle/evaluability.ts` — the single policy point): a rule set whose rules use Arr fields is skipped (warning logged, matches untouched) when no enabled instance of the matching Arr family exists — evaluating against an empty metadata map would make `foundInArr = false` vacuously true for the entire library. Same for Seerr fields with no enabled Seerr instance. Seerr fields on MUSIC rule sets are **permanently** unevaluable (Seerr data is never fetched for music; the fields also carry `invalidForLibraryType: ["MUSIC"]` so create/update rejects them) — detection additionally **disarms** such rule sets (clears `RuleMatch`, cancels PENDING actions) and `executeLifecycleActions` cancels their actions as a backstop, so a vacuous flood armed before the guard existed can never fire. `processLifecycleRules`, `runDetection`, and (defense-in-depth) `detectAndSaveMatches` itself enforce this via `checkLifecycleRuleEvaluability`; the preview/test-item/diff routes return its reason as a 400. The ad-hoc query-actions route has the analogous guard: it refuses to act when the query's Arr rules have no selected/existing Arr server for the action's media type, or Seerr rules with no enabled selected instance (or a MUSIC action). **Watch history is the third external dependency and fails the same way**, so `checkWatchHistoryCompleteness(userId, serverIds?)` in the same module is the shared policy point for it — used by `checkLifecycleRuleEvaluability` and directly by the query-actions route, which needs it MORE than the lifecycle path does (a rule set schedules `actionDelayDays` out and shows on Pending first; the query route executes immediately). **The policy is that a criterion reading play activity may only be answered where play activity is known.** The trigger is therefore every field the registry marks `readsPlayActivity` — `watchedByUser`, `playCount`, `lastPlayedAt`, and the four series aggregates built on those (`seriesLastPlayedAt`, `latestEpisodeViewDate`, `watchedEpisodeCount`, `watchedEpisodePercentage`) — surfaced as `hasPlayActivityRules` in `conditions/helpers.ts` (groups) and `rules/lifecycle-engine.ts` (flat or grouped). Declared on the field definitions rather than as a hardcoded Set so a new play-derived field has to make the decision explicitly instead of silently defaulting to ungated. Gating only `watchedByUser` was not enough: that one reads the relation and goes vacuous the instant the rows are gone, but `playCount = 0` and `lastPlayedAt is null` go vacuous identically wherever the denormalized columns were never established, and those two are what "not played in N months" DELETE rules read. The state is `MediaServer.watchHistorySyncedAt` (migration `0018_watch_history_synced_marker`), a **positive** marker — when a sync last established what was played on this server — deliberately not a "cleared at" one. A `null` default then correctly reads as "we do not know", which covers a brand-new server that has never synced as well as one whose history was destroyed; a nullable "cleared" column reads as healthy by default, so absence of evidence presented itself as evidence of absence. A server is un-established when `watchHistorySyncedAt` is null, OR it is Tracearr-mapped with `tracearrBackfillComplete` false (history exists but the newest-first archive walk has not reached back yet). Written by `src/lib/media/watch-evidence.ts`: `markWatchHistoryEstablished(serverIds)` after a SUCCESSFUL sync — including one that legitimately finds no plays, because a server nobody watches is a real steady state that must not stay paused forever, and `playCount = 0` then legitimately matches everything on it — and `invalidateWatchHistoryEvidence(serverIds)` / `invalidateServersWithoutWatchHistory()` from **every path that destroys watch history in bulk**. `WatchHistory.mediaItem` is a required FK with `onDelete: Cascade`, so the rows die with the media: the `/api/servers/[id]` PUT (source switch), `/api/media/purge` (both branches), disable-with-`deleteData`, and `restoreBackup` — which `TRUNCATE`s every table in `TABLE_ORDER` including `MediaItem`/`WatchHistory` and re-inserts only what the file holds, so a **config-only** backup empties both and refills neither. Restore uses the row-derived variant because it truncates the whole database and re-inserts servers from the file, so the affected ids are not knowable up front. **`serverIds` must be passed at every call site** (`processLifecycleRules`, `runDetection`, the preview/`[id]`-preview/diff routes from their rule set or body, `test-item` from the tested item's own server, query-actions from `query.serverIds`): the check is scoped by it, so omitting it both pauses rule sets reading only established servers AND makes the manual and scheduled detection paths give different answers for the same rule set. A guard that never releases is its own outage
- Enriches items with `matchedCriteria`, `actualValues`, `arrId`, and `servers[]`
- For series with `seriesScope: false`, tracks individual episode IDs via `memberIds` in `itemData`
- **Multi-server**: when a rule set targets more than one server, matches that resolve to the same Arr record (same TMDB/TVDB/MBID) are collapsed by `arrId` (merging `servers[]`) so the same title doesn't schedule two destructive actions or double-count `deletedBytes`. Dedup is by Arr id (not `dedupCanonical`) because a rule set may target a server subset whose canonical copy lives on a non-targeted server

**Phase 2 — Action Scheduling** (in `processLifecycleRules`):

- Cancels pending `LifecycleAction` records for items no longer in matches (safety net for cascading deletes, rule set edits)
- Creates new `LifecycleAction` records with `scheduledFor = now + actionDelayDays` (only when `actionEnabled`)
- Skips scheduling for an item that already has a PENDING action (dedup) **or** a COMPLETED/FAILED action with the **same config signature** as the one being scheduled (`actionConfigSignature` in `src/lib/lifecycle/action-signature.ts` — action type + Arr instance + quality profile + tags-as-sets + flags; deliberately excludes `actionDelayDays`). This stops non-destructive actions (unmonitor/do-nothing/search/quality-change) re-firing every cycle on a still-matching item, while still letting a **changed or re-configured** action re-fire (different signature → never run before). Destructive (`DELETE*`) actions are always re-schedulable (a still-matching item after a "completed" delete likely failed silently). `skipDuplicates: true` guards concurrent runs. The **same** signature guard drives the Pending page's "estimated" rows (`GET /api/lifecycle/actions`) and the pending-deletion-bytes estimate (`GET /api/lifecycle/stats`), so Matches, Pending, and stats stay consistent
- After **all** rule sets are processed, `processLifecycleRules` calls `syncAllCollections(userId)` **once** to push Plex collections (see Plex Collections below) — never per rule set, because a collection's membership is the union of every rule set feeding it

**Phase 3 — Execution** (`executeLifecycleActions`):

- Validates each pending action against `RuleMatch` table before executing (stale check)
- **Whole-record exception guard** (`src/lib/lifecycle/exception-guard.ts`): a whole-record destructive action (`DELETE_SONARR`/`DELETE_LIDARR` — destroys every episode/track, not just matched members) is cancelled when ANY item of the same `parentTitle`+type carries a `LifecycleException`, even one the rule never matched (the member-based inviolability check only sees `matchedMediaItemIds`). Enforced in the scheduled executor (protected parents batch-resolved once per run, skipped entirely when the user has no exceptions), the manual execute route, force-retry, and the query-page actions route
- Tag operations execute first (add/remove Arr tags), then main action (delete, unmonitor, etc.)
- Title validation via `normalizeTitle()` prevents acting on wrong items when resolving Arr records
- `extractActionError()` extracts meaningful error messages from Arr API responses (HTTP status + response body)
- Completed actions record `deletedBytes` (from `MediaItem.fileSize` or sum of member items) for deletion stats tracking
- Deletion stats are aggregated via `GET /api/lifecycle/stats`; reset via `POST /api/lifecycle/stats/reset` (sets `AppSettings.deletionStatsResetAt`)

**Rule set edit behavior**: Any PUT to a rule set clears all `RuleMatch` records and cancels all PENDING `LifecycleAction` records. The next detection run evaluates everything fresh.

### Plex Collections (merge)

A `Collection` is a reusable, named Plex-collection definition (`prisma/schema.prisma`) owning the presentation settings (`name`, `sortName`, `homeScreen`, `recommended`, `sort`) and scoped to one `LibraryType`. A `RuleSet` references it via the optional `collectionId` FK (`onDelete: SetNull`). Multiple rule sets can point at the **same** collection — "merge".

- **Union membership**: `syncCollection(collection, contributions, cache)` in `src/lib/lifecycle/collections.ts` sets the Plex collection's membership to the **union** of every contributing rule set's matched items. Never sync a collection per rule set — that's how the pre-merge code clobbered shared collections.
- **Driven from `RuleMatch`**: `syncCollectionById(id)` builds contributions from the persisted matches of every enabled rule set assigned to the collection (`buildContributionsFromMatches`), so re-evaluating one rule still syncs against all of them, and orphaned collections resolve to an empty union (which removes the Plex collection). `syncAllCollections(userId?)` does this for every collection in scope and **replaces** the old per-rule "disabled collection cleanup" pass.
- **Ordering**: `ACTION_DATE` sort pools the PENDING `LifecycleAction` rows of **all** contributing rule sets, so scheduled-action order is correct across rules. Collection sync therefore runs **after** action scheduling (`processLifecycleRules` after its loop; the manual `runDetection` path via `syncCollectionsAfterDetection` called from `/api/lifecycle/rules/run` after `scheduleActionsForRuleSet`).
- **CRUD**: `GET/POST /api/lifecycle/collections`, `PUT/DELETE /api/lifecycle/collections/[id]` (PUT renames on Plex + re-syncs; DELETE removes from Plex + `SetNull` detaches rules), `POST /api/lifecycle/collections/sync` (`{ collectionId }`). Managed inline from the lifecycle rule editor's collection dropdown — settings edit the shared collection. There is no `collectionEnabled`/`collectionName`/inline-settings on `RuleSet` anymore (migration `0010_add_collections` backfills + auto-merges same `(userId, type, name)`).

### AI Analysis

A read-only natural-language assistant over the media library (`/tools/ai`, `src/lib/ai/`), configured under Settings → AI (`AppSettings.aiEnabled/aiProvider/aiBaseUrl/aiApiKey/aiModel`).

- **Provider-neutral, no SDK**: `provider.ts` is a thin axios client for two providers — `openai-compatible` (OpenAI, Ollama, LM Studio, OpenRouter, Groq, vLLM, LocalAI, …) and `anthropic` (native Messages API). This is deliberate: the "support any AI incl. local models" requirement needs OpenAI-compatible support, and the codebase's axios-everywhere/zero-SDK convention means no `@anthropic-ai/sdk`. `aiBaseUrl` is admin-configured (no SSRF block — local models live on private IPs, and only the single admin sets it).
- **Safety model** (the important part): the model can ONLY call the fixed read-only tools in `tools.ts` — there are no mutating tools, so it can't delete/unmonitor/act even if asked. Tools take **structured, Zod-shaped args** (never model-authored SQL) and delegate to the shared `src/lib/media/*` + `executeQuery` functions, inheriting per-user scoping/dedup. `search_media` excludes Arr/Seerr fields to avoid the vacuous-match hazard the lifecycle evaluability guard guards against (documented v1 limitation). The system prompt tells the model to treat tool-result text as data, not instructions.
- **Grounding**: the prompt (`system-prompt.ts`, built from the field/dimension registries) forbids inventing numbers — every claim must come from a tool result. Scope is local-only (the user's library + their servers' watch history), never global/outside-world trends.
- **Orchestration**: `analyst.ts` runs a bounded (≤6 iteration) tool-calling loop, streaming `status`/`tool` events via `progressStreamResponse` and returning `{ answer, evidence }` (evidence renders as charts/tables in the UI). Routes: `GET/PUT /api/settings/ai` (key masked via `sanitize()`; PUT skips writing the `MASKED_VALUE` placeholder; can't enable without a model), `POST /api/settings/ai/test` (test-connection, rate-limited), `POST /api/ai/chat` (streaming, rate-limited via a dedicated `aiRateLimiter` — 30 req/5 min, looser than the 10/15-min auth limiter since chat is interactive; `checkRateLimit(request, aiRateLimiter, …)`, requires enabled+configured).
- **Secret handling**: `aiApiKey` is in `SENSITIVE_FIELDS`; GET returns the mask, the client echoes it back, and PUT/test treat the mask as "keep saved".

### Backup & Restore

- `createBackup(passphrase?, configOnly=true)` exports tables in FK dependency order, gzips, optionally encrypts with AES-256-GCM. **Every integration table must appear in `TABLE_ORDER`** — restore begins with `TRUNCATE TABLE "User" CASCADE`, so a table omitted from the list is destroyed and never restored, silently. `TracearrInstance` was missing, which made a restore drop the instance while `MediaServer.tracearrServerId` (a column on a table that *is* restored) survived — leaving servers mapped to an instance that no longer exists, which the sync then skips outright rather than falling back to native
- Config-only (default): skips `mediaItem`, `mediaItemExternalId`, `mediaStream`, `syncJob`, `ruleMatch`, `lifecycleAction`, `lifecycleException`, `watchHistory`, `logEntry` — these are repopulated by sync and lifecycle processing
- Full backup: includes all tables when `configOnly=false` (UI checkbox: "Include media data")
- Encrypted backups use `.json.gz.enc` extension; unencrypted use `.json.gz`
- `restoreBackup(filename, passphrase?, onProgress?)` truncates all tables in reverse FK order, then re-inserts in batches of 100; streams progress via NDJSON. `deserializeRow` **drops columns the current schema no longer has** (checked against Prisma's generated per-model `ScalarFieldEnum`, so it can't drift): Prisma validates `createMany` arguments client-side, so one unknown key rejects the whole batch and aborts the restore — without the filter, a config backup taken before migration `0010` dropped the six `RuleSet.collection*` columns is permanently unrestorable
- Sidecar `.meta.json` files store metadata (including `configOnly` flag) so `listBackups()` doesn't need to decompress files
- `getBackupPassphrase()` returns the saved encryption password from AppSettings (used by both manual and scheduled backups)
- Backup API POST falls back to the saved encryption password if no explicit passphrase is provided
- All persistent data paths are under `/config`: backups at `/config/backups`, image cache at `/config/cache/images`
- `BACKUP_DIR` and `IMAGE_CACHE_DIR` env vars can override the defaults

### Background Jobs (Graphile Worker)

- Background work runs through [Graphile Worker](https://worker.graphile.org/), a Postgres-backed job queue. The worker runs **in-process** (not a separate container), started from `src/instrumentation.ts` (guarded by `NEXT_RUNTIME === "nodejs"` — skipped during Edge/build). `startWorker()` is awaited so the worker's own migrations (the `graphile_worker` schema, created automatically — the DB role needs `CREATE` privilege) are applied before any request can enqueue a job. This schema is separate from Prisma's `public` schema; `prisma db push` never touches it.
- **Orphaned-lock recovery on boot**: before the runner starts, `startWorker()` calls `recoverOrphanedWorkerLocks()` to null out any `locked_at`/`locked_by` on the `graphile_worker._private_job_queues` and `_private_jobs` rows. A hard kill mid-job (container restart, crash, OOM) leaves the `MAIN_QUEUE` row locked by a now-dead worker, and `getJob` will not run **any** job on a locked queue — so without this recovery every sync, lifecycle run, and backup stalls until graphile-worker's built-in stale-lock sweep clears it **4 hours** later (the "restart mid-sync ⇒ syncs stop working" bug). Because librariarr runs exactly one in-process worker, any lock present at boot is necessarily orphaned, so clearing unconditionally is safe; it must run before the runner so it can't race a lock the new worker just acquired. This is separate from `cleanupOrphanedSyncJobs()`, which only fixes the app's own `SyncJob` rows, not the queue lock.
- A static crontab (`src/lib/jobs/worker.ts`) drives recurring tasks: the **dispatcher** runs every minute, action cleanup every 15 minutes, log archival hourly.
- The **dispatcher** (`dispatch.ts`) reads the user-configured, DB-stored schedules (`AppSettings.syncSchedule`, `lifecycleDetectionSchedule`, etc.), advances the `lastScheduled*` timestamp, and enqueues durable jobs for any work that is due. Heavy domain jobs (sync, lifecycle detection/execution, backup) share the serial `MAIN_QUEUE` so they run one-at-a-time (mirroring the original sequential scheduler); the dispatcher and housekeeping tasks omit a queue so a long sync never blocks scheduling. Jobs use a `jobKey` to deduplicate and are retried with backoff on failure.
- Manual/API sync triggers (`/api/servers/[id]/sync`, `/api/sync/by-type`) enqueue durable `sync-server` jobs via `enqueueJob()` instead of fire-and-forget calls. `/api/sync/by-type` fans out one job **per library** with `skipWatchHistory: true` (the watch-history scan is server-wide, so running it per library repeats the same work), then enqueues one `TASK_SYNC_WATCH_HISTORY` per server — `MAIN_QUEUE` is serial and ordered by enqueue time, so it lands after the library jobs have finished and `syncWatchHistoryTask`'s "a full sync is already running" guard does not swallow it. `syncMediaServer` still self-serializes via its internal semaphore (`sync-semaphore.ts`), which guards all callers including the inline lifecycle re-sync.
- Manual "Run Now" triggers (`/api/settings/schedule-info/run`) for **detection** and **execution** also enqueue durable jobs on `MAIN_QUEUE` with a stable `jobKey` (`detection:<userId>` / `execution:<userId>`) rather than running inline, so a double-click or a collision with the per-minute dispatcher dedupes into one run. The schedule watermark (`lastScheduled*`/`lastBackupAt`) is advanced only **after** a successful enqueue (in both the dispatcher and the manual route) so a transient enqueue failure can't silently skip a window.
- Also starts the maintenance/preroll enforcers (30s `setInterval` polling loops) in the same `instrumentation.ts` — these keep cross-tick in-memory state and sub-minute cadence, so they intentionally remain outside the job queue. `startRealtime()` (the media-server WebSocket manager) is started here too.
- `TASK_SYNC_WATCH_HISTORY` (`sync-watch-history`) refreshes **only** a server's watch history (no full library re-scan), reconciles `MediaItem.playCount`/`lastPlayedAt` from it (`watch-reconcile.ts`), and invalidates media caches. Enqueued (debounced, on `MAIN_QUEUE`, jobKey `watch-history:<serverId>`) by the realtime manager on a `watch-changed` event; skips itself if a full sync is already running/queued for that server (the full sync already refreshes watch history). This path passes **no** progress reporter — `syncWatchHistory`/`syncTracearrHistory` take an optional `WatchHistoryProgressReporter` (`src/lib/sync/watch-history-progress.ts`) that only the streaming `POST /api/media/history/sync` route supplies, so a job with no client attached behaves exactly as it always did. **Cancellation follows the same shape but not the same policy**: both take an optional `AbortSignal` as their **third** argument (only the streaming route supplies one, as `request.signal`), and the two paths must react to it differently. The Tracearr importer checks the signal at the top of every page **and** threads it into the HTTP call — so a cancel lands within one page and interrupts a rate-limit backoff rather than waiting the rolling window out — then **breaks**, keeping every play it already wrote: append/upsert plus the two boundaries derived from those very rows (below) makes a partial run resumable **in both directions**, so stopping early is a normal outcome the route reports as `cancelled: true`, not a failure — provided the cancelled walk returns `"stopped"` and never marks the backfill complete. The native path **throws** on abort instead, because its write loop runs inside the full-replace transaction that has already deleted the server's rows — breaking there would commit a half-rewritten history, so it must roll back and leave the previous rows intact. The importer's page cap is a **runaway-cursor backstop only** (20,000 pages ≈ 2M plays at the API's 100-record maximum, not a budget): it was 2,000, which a real 160k-play library would have silently truncated at 1,600 pages — a cap reachable by legitimate data is a data-loss bug, not a safety valve. Its per-page dedup set is deliberately **page-scoped** for the same reason the first import is the dangerous one: it only exists to catch a cursor repeating records inside one page, and hoisting it out of the loop would grow it with the entire history. **Per-server source branch**: `syncWatchHistory` picks its path per server — a set `MediaServer.tracearrServerId` **plus** an enabled `TracearrInstance` runs the incremental Tracearr import; a server with **no** mapping runs the unchanged **native full-replace** (drop this server's rows, re-insert what the server currently reports). A mapped server whose instance was since disabled or deleted is **skipped outright** — falling back to native there is doubly destructive: the native DELETE is not scoped by `source`, so it destroys the imported rows, and because the importer's boundaries are derived from those very rows, re-enabling the instance then re-imports the entire history *on top of* the NATIVE rows the fallback wrote. `reconcileWatchStateFromHistory` counts both strata and `playCount` is monotonic, so every play is permanently double-counted. As a backstop the importer also drops any `source='NATIVE'` rows for the server once its own rows have landed, so the one-provenance-per-server invariant is enforced, not assumed. Which *instance* serves a mapping is resolved by asking each enabled instance which servers it monitors (`listServers()`) and taking the owner — a single-instance install, the common case, short-circuits with no network call, and an unreachable instance is skipped rather than letting a different Tracearr answer for it. `MediaServer.tracearrServerId` stores a Tracearr-side server UUID, not an instance id, so "the first enabled instance" would silently import nothing on a two-instance setup. The two row models cannot coexist in one table — a native row means "this item was played", a Tracearr row is one play carrying completion/transcode/stream detail — so **changing a server's source in either direction wipes that server's `WatchHistory` once** (in the `/api/servers/[id]` PUT, on a detected `tracearrServerId` transition, Tracearr→Tracearr included) and the next sync repopulates it. The wipe deliberately does **not** walk back `playCount`/`lastPlayedAt`; those are monotonic by design. The Tracearr path is **append-and-update, never delete**, and it pages `/api/v2/public/history` for the mapped `server_id` over **two independent boundaries**, not one. **`/api/v2/public/history` returns plays NEWEST FIRST** (the spec says "newest first" and the cursor is a keyset on `started_at` descending — verified against a live instance), and that single fact makes a lone forward watermark **unsafe**: the walk goes new → old, so `MAX(watchedAt)` is set by the FIRST page imported. An import interrupted partway — a crash, a container restart, the streaming route's 30-minute lifetime cap, or the user pressing **Stop** — then resumed from `MAX - overlap`, was handed `nextCursor: null` almost immediately, reported success, and **silently abandoned every older play**. Measured on a live instance with history back to 2021: after an interrupted import of 300 plays the old resume walked **3 plays and stopped**, where the two-pass version walked **2,500 older plays over 25 pages** and was still going. So `syncTracearrHistory` runs up to two passes: **FORWARD** — `since = MAX(watchedAt) - overlap`, new plays since the last run, with a **1-hour overlap** (a play that landed mid-page on the previous run must not fall through the gap), reaching further back when a still-in-progress chain sat at the boundary and clamped to **7 days** so one abandoned chain cannot pin the window; skipped entirely when there is no watermark (a first import — the backfill covers everything). **BACKFILL** — `until = MIN(watchedAt)`, keep walking older until the keyset is exhausted; `until` is **inclusive**, so the boundary play is re-delivered and merged by the upsert rather than stepped over. **Which passes run is the caller's choice, because the two have opposite cost profiles**: `syncTracearrHistory(serverId, { onProgress?, signal?, passes?, deadlineMs? })` → `{ count, backfillPending }`, where `passes` is `"forward" | "backfill" | "both"` (default `"both"`) and `deadlineMs` is an epoch-ms floor past which **no NEW page is started** (the in-flight page still finishes and commits, so a slice always ends on a page boundary). `syncWatchHistory` runs `passes: "forward"` **only** — every one of its callers is either a user waiting on a foreground request (the History page's **Refresh**) or a short scheduled/realtime job, and the forward pass is bounded to an hour of overlap so it answers in seconds no matter how much history the server holds — and enqueues `TASK_TRACEARR_BACKFILL` (below) whenever `result.backfillPending`, which is derived from `MediaServer.tracearrBackfillComplete` rather than from what *this* run did, so a forward-only run still reports that a backfill is owed. Both come from `resolveImportWindow(serverId, backfillComplete)` in one aggregate query (`MAX("watchedAt")`, `MIN("watchedAt")`, and the open-chain `MIN(...) FILTER (WHERE "watched" IS NOT TRUE OR "state" <> 'stopped')`), derived from the **rows** rather than a persisted cursor so the record of what was imported and the boundary that resumes it cannot disagree — conservative in the safe direction, since a page whose records were all skipped (unjoinable, wrong server, under Tracearr's 2-minute floor) leaves `MIN` where it was and the next run re-walks that stretch instead of stepping over unimported history. **`walk(pass, { since, until })` returns `"exhausted"` ONLY when `nextCursor === null`**; every other exit — cancelled, the `MAX_PAGES` cap, a stalled cursor, a fetch or write error — returns `"stopped"`. That distinction is the entire safety property: only `"exhausted"` may mark the backfill complete, and treating a cancelled walk as exhausted re-introduces the bug verbatim by permanently stranding the unread older history. `MediaServer.tracearrBackfillComplete` (migration `prisma/migrations/0017_add_tracearr_backfill_state`) is the one thing the rows cannot tell us — whether any previous walk ever reached the end — so it is the only persisted state; the `/api/servers/[id]` PUT **resets it to false whenever the mapping changes** (`tracearrMappingChanged`), because that same transition wipes the rows it describes, and it is **treated as false when the server holds no Tracearr rows at all** (`window.hasRows`) since "complete" with zero rows is a contradiction — something removed them out from under the flag (a manual delete, a partial restore) and the alternative is importing nothing forever. **The account-name map is a PRECONDITION of the archive walk, and an EMPTY map counts as a missing one.** `TracearrClient.getServerAccountNames()` bridges each record's `server_user_id` to the media server's own `UserAccount.username` — the vocabulary the native path stores in `WatchHistory.serverUsername` and the one `watchedByUser` rules match on. A record's `user.username` is instead Tracearr's cross-server identity label ("Nick W" the identity vs "weingart" the account), so storing it makes one human two people. Archive rows are effectively permanent — nothing re-delivers a page the walk has passed — so `syncTracearrHistory` **skips the backfill** when the map is unavailable and reports `backfillOutcome: "errored"` so the queued task backs off instead of spinning. It tests `size === 0` as well as absence, because the client returns `new Map()` rather than throwing on an unexpected `/users` response shape or a cut-short user walk, and an empty Map is truthy — testing truthiness alone let exactly the outcome the gate exists to prevent through the gate. The **forward** pass deliberately keeps running without it (an hour of overlap, whose rows the next successful run re-delivers and re-labels), **but withdraws `watchHistorySyncedAt` BEFORE writing a single row** — "self-healing eventually" is not "safe to answer questions about now". Those rows carry identity labels where the rest of the server carries account names, and a MISSING username arms a negative `watchedByUser` rule rather than disarming it: "delete unless watched by weingart" matches an item weingart did watch, the play filed under a name the rule does not recognise. Withdrawing at the END of the run would be too late — rows commit per page, the forward window has no upper bound (after downtime it walks days of plays in minutes), detection runs on its own dispatcher unserialised against a foreground Refresh, and a match formed inside that window SURVIVES the later pause because a transient refusal preserves matches and pending actions while the executor never re-checks evaluability. Conditioned on the map being unusable, not on any fallback name: a user Tracearr has since removed is legitimately absent from a healthy map, and pausing for that would never lift, and `recoverHistoryForNewItems` deliberately does **not** — its rows are old plays that `findCandidates` will never offer again once they exist, so it aborts exactly like the archive walk. **Only a walk that both exhausted the keyset AND saw at least one record may mark the backfill complete.** A first page of `{ records: [], nextCursor: null }` is "exhausted" too, and that is precisely what a mismatched mapping looks like — a `tracearrServerId` the resolved instance does not monitor (`resolveInstanceForServer` short-circuits on a single enabled instance without probing), or a freshly-installed Tracearr with no retained history. Declaring completion there would mark `watchHistorySyncedAt` established on a server whose native history the mapping change had already wiped, handing the evaluability guard a clean bill of health for an empty relation. The gate asks about **records returned**, not rows written, because ~41% of old plays reference media that has since left the library and are deliberately skipped — a legitimate walk can exhaust having stored nothing, and gating on rows would re-walk such an archive forever. Rows upsert on `@@unique([mediaServerId, sourceEventId])` with **ON CONFLICT DO UPDATE** — mandatory rather than an optimization, because a `HistoryRecord` is a resume-chain aggregate whose `watched`/`percent_complete`/`stopped_at`/`segment_count` all move when the user resumes, so DO NOTHING would freeze a play at its first-seen 12%-complete state forever (and `watch-reconcile.ts`'s `watched IS DISTINCT FROM false` gate would then never count the finished viewing). The UPDATE is deliberately **non-regressive rather than a blind `= EXCLUDED`**: the spec states that `since` scopes the *aggregation* as well as the selection ("duration_ms, segment_count and percent_complete cover only in-window segments"), so a chain that started before the window but has one segment inside it is re-delivered with truncated figures — and the 7-day lookback guarantees that eventually happens to any long-lived chain. `percentComplete`/`progressMs`/`durationMs`/`segmentCount`/`stoppedAt` therefore merge with `GREATEST`, `watched` and `isTranscode` latch (`stored IS TRUE OR excluded IS TRUE`), and the descriptive columns use `COALESCE(excluded, stored)` so a null in a narrow page cannot erase known detail. Same monotonic rule as the reconcile: a narrower view of history must never make an item look less watched. The consequence, stated plainly: **Tracearr-side deletions do not propagate** — nothing but a source switch clears imported rows. Joining is `src/lib/sync/tracearr-join.ts`, biased so that **a dropped play beats a wrong one**: `rating_key` → `MediaItem.ratingKey` scoped to the server — but a single hit is **corroborated, not trusted**: rating keys are not stable across a delete (Plex reuses them, they are rowids), so a key that identified a deleted film can later identify a different one, and an un-corroborated hit files the old item's plays against the new one under REAL usernames. That is the dangerous direction — play state is monotonic so inflating it only ever *disarms* a rule, whereas a wrong `serverUsername` ARMS a positive `watchedByUser` DELETE — and nothing revisits an upserted row, so it is permanent. So the hit must be the type the record claims, and where both sides carry a provider id from the same source those must agree (`contradictsProviderIds`); silence on either side proves nothing and is accepted, because provider ids are far from universally populated and refusing on absence would drop most legitimate plays. Season/episode numbers are deliberately NOT compared here, unlike on the provider path: the rating key already identifies the exact episode on that server, while Tracearr and the server can legitimately disagree about numbering (absolute vs aired ordering), falling back to `tvdb_id` → `tmdb_id` → `imdb_id` (the `computeSeriesKey` precedence) for a record whose rating key is null or went stale on a re-add. **Every ambiguity is a skip**: two rating-key hits skip — `@@unique([libraryId, ratingKey])` makes a rating key unique *within a library*, but a server has many libraries, so the same key can legitimately appear twice under one server and there is no principled pick between them, and because the sync stores **series-level** ids on every episode row of a show (see "Series identity"), a bare TVDB match returns the show's entire episode list — episodes are narrowed by `seasonNumber` + `episodeNumber` and a record missing either is skipped outright rather than guessed. The index is built once per sync with two queries; a first import is tens of thousands of records, so per-record lookups are not an option. The skip bias exists because these rows feed `watch-reconcile.ts` → `playCount`/`lastPlayedAt` under a monotonic `GREATEST`: a play attributed to the wrong item can never be walked back, and destructive rules read those columns. The realtime manager enqueues `TASK_SYNC_INCREMENTAL` (`sync-incremental`) on `library-changed` events — `src/lib/sync/sync-incremental.ts` `syncMediaServerItems()` fetches + upserts only the changed ratingKeys (reusing the full sync's exported `processBatch`) and deletes the removed ones (a `getItemMetadata` 404 counts as a deletion; a **transient** fetch error never guesses a delete — it returns `"fell-back"` and the task enqueues a full sync). It skips the server-wide play-count/watch-history scans and stale detection (those stay with the full sync, which remains the periodic reconciliation backstop). **The upsert overwrites every column it writes**, so any column whose authoritative source this path lacks must be handled explicitly or it is silently destroyed until the next full sync — three are: (1) `playCount`/`lastPlayedAt` are read back from the stored `WatchHistory` (`loadWatchCountsFromHistory`), which `buildItemData` maxes against the metadata, because the fetched metadata carries only the admin account's `viewCount`/`lastViewedAt`; (2) `isWatchlisted` is carried forward from the stored row **on Plex only** — Plex's watchlist lives behind the account-level plex.tv API (`getWatchlistGuids`) that only the full sync calls, and Plex item metadata has no watchlist field at all, whereas Jellyfin/Emby get theirs from the item's own `IsFavorite`, so carrying it forward there would instead make un-favouriting wait for a full sync; (3) the per-show `getItemMetadata` calls that supply series-level GUIDs run **before** any write and return `"fell-back"` on failure — `processBatch` reads a missing `showGuidsMap` entry as "this show has no series-level ids" and deliberately clears the episode's external ids rather than storing its (wrong) episode-level guid, so a transient failure would otherwise wipe the TVDB id the series' whole Arr/Seerr correlation hangs on and make `foundInArr` vacuously false for every Arr criterion. Then it runs `recomputeCanonical` + `invalidateMediaCaches` + emits `sync:completed`. **A mapping failure is classified PER ITEM and does not escalate the batch.** `return fellBack("cannot map item …")` on the first unmappable id used to discard the work already done for every other item and trigger a whole-server sync — and Plex guarantees unmappable ids on a routine add: one new movie arrived alongside 27 extras/trailers carrying `sectionID: -1` and no `librarySectionID` anywhere in their metadata. `normalize-plex` now drops `sectionID < 0` at the source (safe in both directions — real items keep a valid section even on deletion; only extras are sectionless) and dedupes by `itemID` (one added movie emitted seven frames for the same ratingKey as Plex walked it through create/analyze/load). Anything still unplaceable is counted `unresolved`, logged, and **dropped**: a full sync lists one type per enabled library and could not have stored it either, so escalating was pure cost. `libByKey` also loads **disabled** libraries (carrying `enabled`) so an item in one is *recognised and skipped*, not treated as unknown — and the delete path is scoped `AND l."enabled"=true`, because the full sync skips disabled libraries entirely so its stale purge never touches their rows; the old all-or-nothing `fellBack` was shielding them only by accident. `existingByRatingKey` maps to a **list**, not one row: `@@unique([libraryId, ratingKey])` lets one server hold the same ratingKey in two libraries, and collapsing let an arbitrary "last row wins" pick decide an item's `LibraryType` and its whole Arr correlation; ambiguity is `unresolved`. Two mapping failures still fall back: a section key with **no** `Library` row (a genuinely new library — only `syncMediaServer` creates those) and **any** unresolved id on Jellyfin/Emby, whose `normalizeItem` never populates `librarySectionID` at all (bounded there — no Plex-style extras storm; resolving them via `/Items/{id}/Ancestors` is a follow-up). Otherwise it falls back only on a >100 change set, a transient fetch/show-metadata error, or a full sync already running. `PlexClient.getItemMetadata` returns `Metadata?.[0]` and merges `librarySectionID` down from the `MediaContainer`: indexing `Metadata[0]` unguarded threw a `TypeError` on a 200-with-empty-container, which is not a 404, so a genuine removal was read as *transient* and escalated instead of deleting the row.
- `TASK_TRACEARR_BACKFILL` (`tracearr-backfill`, payload `{ serverId }`) walks the **older** half of a Tracearr-mapped server's history: `syncTracearrHistory(serverId, { passes: "backfill", deadlineMs: Date.now() + TRACEARR_BACKFILL_SLICE_MS })`, then `invalidateMediaCaches()`, then **re-enqueues itself** while `backfillPending` is still true. It is a separate task from `TASK_SYNC_WATCH_HISTORY` because the two have **opposite cost profiles**: that one is a bounded catch-up (an hour of overlap — seconds, whatever the server holds), this one is a server's entire retained archive — ~1,600 sequential pages at 160k plays given the API's 100-record page maximum, paced by Tracearr's rolling 1-minute per-key rate limit. It cannot live in a request (the walk dies with the tab, and `POST /api/media/history/sync` caps its stream at 30 minutes) and it cannot be one long job either, because `MAIN_QUEUE` is **serial** and an hours-long walk would park every sync, lifecycle run and backup behind it. Hence the **5-minute slice** (`TRACEARR_BACKFILL_SLICE_MS` in `tasks.ts`), which is bounded at **both** ends for different reasons: **below** by the per-run `buildTracearrJoinIndex(serverId)` cost (it loads every candidate item on the server plus its provider ids — slice too finely and each run re-pays that index build before importing a single page), **above** by `MAIN_QUEUE`'s serialism. Slicing is safe because **all resume state is in the DB** — the imported rows give `MIN(watchedAt)`, and `tracearrBackfillComplete` records whether any walk ever reached the end — so a slice killed by a restart, deploy or crash simply resumes from the oldest play it managed to import, and only an `"exhausted"` walk (`nextCursor === null`) may clear the flag; a deadline stop returns `"stopped"` exactly like a cancel. **The jobKey `tracearr-backfill:<serverId>` is deliberately shared by BOTH the task's self-re-enqueue and `syncWatchHistory`'s enqueue**: a **Refresh** pressed mid-backfill then collapses onto the walk already queued/running instead of starting a second one, which would be pure duplicated paging against a rate-limited API with two walkers racing the same `MIN(watchedAt)`. `queueName: MAIN_QUEUE`, `maxAttempts: 3`. The UI's completion signal is `GET /api/integrations/tracearr/status` — per mapped server `{ backfillComplete, importedCount, oldestImported, newestImported, oldestPlayAt, backfillFraction }` — which is what Settings → Servers renders as a progress bar plus "importing, N plays back to `<date>`" versus done. **`backfillFraction` measures TIME COVERED, not records imported**: `backfillComplete` → `1`; no `oldestPlayAt`, no imported rows, or a non-positive span → `null`; otherwise `clamp01((newestImported - oldestImported) / (newestImported - oldestPlayAt))` — the share of the server's history *span* the walk has reached, with `oldestPlayAt` measured by `TracearrClient.findOldestPlayAt` (above). A record ratio is not merely unavailable but **dishonest**: keyset pagination exposes no total and there is no count endpoint, and even given one it could never reach `1`, because a large share of fetched plays are deliberately not stored — `WatchHistory.mediaItemId` is a required FK, so a play whose media has since been deleted from the library has nothing to attach to and is skipped (~41% of pre-2023 plays on a real library; one slice logged `18144 new … skipped 12625 unresolved`). That skip is also why an import can legitimately finish with far fewer rows than Tautulli reports for the same server — Tautulli stores its own copy of the title, so it retains history for deleted media. Time coverage, unlike record count, does complete. **`null` and `0` are different states and must never be conflated**: `null` means "not yet measurable" (the oldest play hasn't been measured, or nothing has been imported to measure against) and must render as an **indeterminate** bar, never an empty one.
- **Deleting a `MediaItem` deletes its plays, and a re-add then reads as never watched — a lifecycle hazard, and a write race.** `WatchHistory.mediaItem` is a **required** FK with `onDelete: Cascade`, so the full sync's stale purge, the incremental sync's removal path, and the manual purge route each take an item's stored plays with them. Re-adding the same media later creates a *fresh* row with `playCount 0` / `lastPlayedAt null` — it looks **never watched**, which is precisely the state a "not played in N months" or `playCount = 0` DELETE rule arms on, while Tracearr still holds every one of those plays. The backfill will not recover it on its own: `tracearrBackfillComplete` is already true, so only the forward pass runs (a 1-hour overlap), and it never reaches back that far. Two mitigations, one per direction:
  - **`writeBatch` re-checks item existence immediately before it inserts** (`sync-tracearr-history.ts`). `buildTracearrJoinIndex(serverId)` is built **once per run** and its `mediaItemId`s are written minutes later, so an item deleted in between makes the INSERT die on the FK; the walk's catch keeps what it committed and returns `"stopped"`, so one deleted file burns the rest of a 5-minute slice (the next slice rebuilds the index and skips the item as `unresolved`, so it self-heals — expensively). The race is reachable in normal use because the History page's **Refresh** runs in a request, outside the serial `MAIN_QUEUE` that keeps the heavy jobs from overlapping. The check **narrows** the window, it does not close it — an item can still be deleted between the check and the INSERT — so the walk's catch stays the backstop for the residual case; do not delete it as "now unreachable".
  - **`recoverHistoryForNewItems` re-imports a newly added item's plays by asking Tracearr for that item's history directly**, bounded twice: candidates are items created in the last **7 days**, and only a capped number are looked up **per run**. Both bounds exist because `/api/v2/public/history` takes `rating_key` as a **single string, not a list** (verified against the published spec), so a targeted lookup costs **one request per item** against a per-key rolling-1-minute rate limit — an unbounded sweep over a large library is thousands of requests. They are also what lets the feature add **no new persisted state**: the window plus the cap *are* the bookkeeping, so there is no cursor, no per-item "recovered" flag, and nothing to migrate or reconcile. It runs from `TASK_TRACEARR_BACKFILL`, and **only once the archive walk is complete** — while the backfill is still walking it is already importing that history wholesale, so targeted lookups would spend the same rate limit twice.

### CI/CD

- `.github/workflows/ci.yml` — Lint, test, build on pushes to main and PRs
- `.github/workflows/release-please.yml` — On push to main, runs release-please; when a release is created, builds and pushes the Docker image with `latest` + semver tags
- `.github/workflows/docker-nightly.yml` — On push to `main` (or manual dispatch), builds and pushes the `nightly` rolling tag + immutable `nightly-<sha>` tags for the trunk-based bleeding-edge channel. Never publishes `latest`/semver (reserved for releases)
- `.github/workflows/docker-publish.yml` — Manual (`workflow_dispatch`) Docker Hub image publish
- `.github/workflows/pr-title-lint.yml` — Validates every PR **title** against Conventional Commits (mirrors `@commitlint/config-conventional`). Because squash-merging uses the PR title as the commit subject on `main`, and release-please classifies commits by that subject, a non-conventional title would be silently dropped from the release/changelog. The local `commit-msg` hook can't catch a title typed into GitHub's merge UI, so this check enforces it server-side.

### Git Conventions

- Husky pre-commit hook runs `pnpm exec eslint --quiet`
- Husky commit-msg hook enforces [Conventional Commits](https://www.conventionalcommits.org/) via commitlint (`@commitlint/config-conventional`)
- Commit format: `type(scope): description` — e.g. `feat: add stream manager`, `fix(auth): handle expired tokens`
- **When squash-merging a PR, the PR title becomes the commit subject on `main` — it MUST be a valid Conventional Commit** (enforced by `pr-title-lint.yml`). release-please reads that subject to decide the version bump and changelog; a squashed PR titled `Add X` (not `feat: add X`) is dropped from the release entirely. Merge-commit PRs are safe because release-please reads the inner commits, but squash collapses them into the one title.
