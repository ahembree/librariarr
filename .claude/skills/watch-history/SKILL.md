# Watch history & Tracearr

- A `WatchHistory` row is **one play event** (per-item aggregates are `MediaItem.playCount`/`lastPlayedAt`). `source` is `"NATIVE"` (the server's history API; also the migration default) or `"TRACEARR"`. Native rows populate only `serverUsername`/`watchedAt`/`deviceName`/`platform`. Tracearr rows add `sourceEventId` (the resume-chain id; `@@unique([mediaServerId, sourceEventId])`, NULL for native rows), `referenceId`, completion columns (`watched`, `percentComplete`, `state`, `progressMs`, `durationMs` (summed in-window watch time), `totalDurationMs` (runtime), `segmentCount` (>1 = resumed), `stoppedAt`), client columns (`player`, `product`) and stream columns (`isTranscode`, `videoDecision`, `audioDecision`, `bitrate` kbps, `resolution`, source/stream codecs, Json `transcodeInfo`, `subtitleInfo`, `streamQuality`).
- **Completed-play predicate** — `src/lib/media/watch-completion.ts`: `completedPlaySql(alias)` (raw SQL) and `COMPLETED_PLAY_FILTER` (Prisma), i.e. `watched IS DISTINCT FROM false` / an explicit `OR [true, null]` — both must admit the NULL a native row carries. A partial or still-running Tracearr play is stored and shown but must not count as a play: because `playCount`/`lastPlayedAt` are monotonic, one such row would permanently disarm every "not played in N months" rule. Consumers that must use it: **both** helpers in `watch-reconcile.ts` (change both or neither), the `watchedByUser` rule in **both** phases (Phase-1 relation filter in `conditions/where-builder.ts` and the Phase-2 eager loads in both engines), the removed-item eager load in `/api/lifecycle/rules/[id]/diff`, and **both** Seerr watch-correlation paths (`request-stats.ts`, `/api/seerr/users/[userKey]/requests`). `watch-analytics.ts` deliberately does not (engagement, not deletion). A new consumer must decide explicitly.
- **`src/lib/sync/watch-reconcile.ts`** — item sync derives play state from account-scoped metadata (Plex admin token views; Jellyfin/Emby admin `UserData`), so the server-wide per-user `WatchHistory` is reconciled into `playCount`/`lastPlayedAt` (and through them `seriesLastPlayedAt`, `watchedEpisodeCount`, `watchedEpisodePercentage`). Monotonic (`GREATEST`/`Math.max`). `reconcileWatchStateFromHistory(serverId, { mediaItemIds? })` runs (non-fatal) after every `syncWatchHistory` — scoped to the items written after an append, a Tracearr run or recovery (nothing when nothing was written), unscoped after a native full replace or with `reconcileAll` — and unscoped in `syncMediaServer` whenever `skipWatchHistory` is set.
- **Native path** (`syncWatchHistory`): full replace (delete this server's rows, re-insert what the server reports) in 5,000-row `unnest` batches (`BATCH_SIZE`). When the realtime manager enqueues `TASK_SYNC_WATCH_HISTORY` with `incremental: true` (jobKey `watch-history:<serverId>`, shared with `/api/sync/by-type`'s deferred full refresh; `enqueueJob` drops the flag while a full replace is still queued under the key, `keepQueuedFullReplace`) it appends instead — only with a client asserting `supportsHistorySince` (Plex), `watchHistorySyncedAt` set, and a stored row to resume from: Plex is asked `viewedAt>=` (newest stored play − 1 h; written into the URL verbatim — Plex ignores the percent-encoded form), older entries are dropped client-side, and the overlap is deduped on item + user + `watchedAt`. Both modes take a per-server `pg_advisory_xact_lock` (the History page's Refresh runs outside `MAIN_QUEUE`). The scheduled dispatcher, Refresh and the full sync keep the full replace (which also reconciles plays the server deleted). On abort the native path **throws** (rolling back the replace).
- **Progress** (`src/lib/sync/watch-history-progress.ts`): `POST /api/media/history/sync` streams one phase per server (`key` = server id), terminal result `{ success: true, counts }` (a failed server `-1`). Native reports a real `fraction`; Tracearr omits it (keyset API, no total) and reports counts, rendered as an indeterminate bar — **never synthesise a percentage**. The reporter and `AbortSignal` are optional; only the streaming route supplies them.
- **Source per server**: `MediaServer.tracearrServerId` + an enabled `TracearrInstance` → Tracearr import; no mapping → native; mapped but the instance is disabled/deleted → **skipped outright** (a native fallback deletes the imported rows and double-counts after re-enable). The importer drops any `NATIVE` rows for the server once its own rows have landed — only while the server is still mapped to the run's Tracearr server (`purgeNativeStratum`: the `FOR SHARE` check and the DELETE in one transaction, like `writeBatch`; skipped outright when a write already hit `TracearrMappingChangedError`), since after an unlink the NATIVE rows are the server's fresh history. The serving instance is found by asking each enabled instance which servers it monitors (`listServers()`; a single instance short-circuits; an unreachable one is skipped). Changing the mapping in `PUT /api/servers/[id]` (either direction, Tracearr→Tracearr included) wipes that server's `WatchHistory` once, resets `tracearrBackfillComplete`, `tracearrBackfillCursorAt`, `tracearrOldestPlayAt` and `tracearrForwardResumeAt` (`tracearrMappingChanged`), clears `watchHistorySyncedAt` in the same write, and is refused (409) when another server already maps that `tracearrServerId`. Play state is not walked back, and **Tracearr-side deletions do not propagate**.
- **Client** (`src/lib/tracearr/tracearr-client.ts`, read-only axios) spans two API versions: `/api/v1/public/health` for connectivity and the server list (where the client reads `server_id` UUIDs; the current v2 spec also lists them at `/servers`), `/api/v2/public/history` for plays (carries `rating_key` + TVDB/TMDB/IMDB ids, keyset-paginated, **newest first**; plays under 2 minutes that never crossed the watched threshold are absent — never read a missing row as a join failure), `/api/v2/public/users` for the account-name map. A 429 is retried once with a bounded delay (`BULK_RATE_LIMIT_MAX_RETRIES` = 5 for the archive walk, `getHistoryForItem` and `/users`). A `HistoryRecord` is a resume-chain aggregate: a re-sighting must UPDATE the row. `findOldestPlayAt(tracearrServerId, { signal?, floor? })` bisects `until` at hour precision between `floor` (default 2008-01-01) and the newest play (~19 calls); stored once per server in `MediaServer.tracearrOldestPlayAt`, best-effort.
- **Import** — `syncTracearrHistory(serverId, { onProgress?, signal?, passes?, deadlineMs?, yieldTo? })` → `{ count, backfillPending, backfillOutcome?, joinIndex? }`:
  - **FORWARD** pass: `since = MAX(watchedAt) − 1 h`, reaching further back to the oldest still-open chain (not watched, or not stopped), clamped to 7 days before `MAX` and never past now; skipped with no watermark. **BACKFILL** pass: `until = MIN(watchedAt)` (inclusive; the boundary play is merged), walking older until exhausted. A lone forward watermark is unsafe on a newest-first API: an interrupted first import would abandon all older history.
  - **An unfinished forward window is resumed**: a forward walk stores the newest plays of its window first, so one that stops after a page would leave the stretch below them unread while `MAX` moved past it. Before committing a page that stores rows while more pages follow, the walk records its `since` in `MediaServer.tracearrForwardResumeAt` (kept at the oldest; `recordForwardResume`); the next forward `since` is `min(row-derived since, resume point)` (past the 7-day clamp); only an exhausted forward walk clears it (`clearForwardResume`, only a point at or after its own `since`). No write in the steady state (a one-page catch-up). A targeted write (`importTracearrRecords`, i.e. recovery) that would store a play newer than the newest stored one records the current row-derived `since` the same way first (`holdForwardWatermark`, before the write commits), since that play would otherwise move the forward `since` past plays nothing has read; an older play, or a server with no rows (its resume point already is its watermark), records nothing.
  - Boundaries come from the rows (`resolveImportWindow`: three subqueries — not one `FILTER` aggregate, which defeats the `(mediaServerId, source, watchedAt)` index). `MediaServer.tracearrBackfillCursorAt` records how far a backfill walk reached (measured per walk, never inherited from the forward pass). `tracearrBackfillComplete` and `tracearrForwardResumeAt` are the only other persisted state. "Complete" with no Tracearr rows is **not** stale by itself — an archive whose every play is unjoinable completes having stored nothing, and resetting it re-walked the archive after every forward sync, forever. It is stale (`staleBackfillState`, reset in the DB together with the cursor and the resume point) only when `watchHistorySyncedAt` has also been withdrawn (a restore by an earlier version; purge, disable-with-delete, a source change and restore now reset the flag themselves) or no forward watermark is recorded (a walk completed before one was).
  - **A server holding no Tracearr rows** has no row-derived forward `since`, so `tracearrForwardResumeAt` is its forward watermark: a backfill slice that leaves no rows records its upper boundary (`until`, or its start when walking from the newest play) − 1 h when none is recorded (`rowlessForwardStart`, in the slice's compare-and-set state write); the forward `since` is that point; an exhausted forward walk that still stored nothing moves it to its own start − 1 h instead of clearing it. Not a gap for the marker (`forwardGapOpen` needs rows).
  - `walk()` returns `"exhausted"` **only** when `nextCursor === null`; cancel, page cap, stalled cursor, deadline, yield and a mid-run mapping change are `"stopped"`; fetch/write errors are `"errored"`. Only an exhausted walk that **saw at least one record** may mark the backfill complete.
  - `syncWatchHistory` runs `passes: "forward"` only (bounded; the user may be waiting) and enqueues `TASK_TRACEARR_BACKFILL` on every Tracearr run — not only while `backfillPending`, since a finished walk's job runs the re-added-item recovery — unless that job is backing off (`isJobRetrying`).
  - On cancel the importer breaks at the next page (the signal also aborts the HTTP call and rate-limit waits) and keeps what it wrote — resumable in both directions; the route reports `cancelled: true`.
  - **The account-name map is a precondition of every writing pass** (forward, backfill, recovery): `getServerAccountNames()` maps `server_user_id` → the media server's own username (the vocabulary `serverUsername` and `watchedByUser` use; `user.username` is Tracearr's cross-server label). Missing **or empty** → the run writes nothing and the backfill reports `"errored"`.
  - Upsert on `@@unique([mediaServerId, sourceEventId])` is `ON CONFLICT DO UPDATE`, **non-regressive** (`since` also narrows the aggregation): `GREATEST` for `percentComplete`/`progressMs`/`durationMs`/`segmentCount`/`stoppedAt`, `watched` and `isTranscode` latch, descriptive columns `COALESCE(excluded, stored)`.
  - `writeBatch` runs in a transaction that selects the `MediaServer` row `FOR SHARE` with the expected `tracearrServerId` (`TracearrMappingChangedError` → `"stopped"`), and re-checks item existence just before inserting (the walk's catch stays the backstop for the residual race).
  - `MAX_PAGES` (20,000) is a runaway-cursor backstop only; the per-page dedup set is page-scoped. The next page is prefetched while the current one is written (aborted if unused). The join index is built lazily on the first page holding this server's records and handed to recovery. Instance-ownership probes run in parallel.
  - `watchHistorySyncedAt` is written at the end of any run whose account map loaded, whose archive walk is complete, and that leaves no unfinished forward window (`forwardGapOpen`: one this run left, or a recorded one reaching back past the rows' own `since` that this run did not walk to its end) — the completion write omits it then too, and the run that closes the window writes it.
- **Joining** (`src/lib/sync/tracearr-join.ts`) — **a dropped play beats a wrong one** (a wrong `serverUsername` arms `watchedByUser` DELETE rules and nothing revisits the row). `rating_key` → `MediaItem.ratingKey` on the server, then corroborated: the type must match, plus `contradictsIdentity` at the same granularity — **episodes compare `grandparent_rating_key`** (never provider ids: Tracearr sends episode-level ids while we store series-level ones; never season/episode numbers); movies and tracks compare TMDB/IMDB ids (never TVDB) where both sides carry one. Absence on either side is accepted. The provider-id fallback (`tmdb_id` → `imdb_id`, never TVDB) is for movies and tracks only — **never episodes**. Every ambiguity (two rating-key hits, two same-type rows sharing a provider id, a type mismatch or contradiction) is a skip. The index is built once per run with two queries.
- **`TASK_TRACEARR_BACKFILL`** (`tracearr-backfill`, payload `{ serverId }`, `MAIN_QUEUE`, `maxAttempts: 3`): runs the backfill pass for a 5-minute slice (`TRACEARR_BACKFILL_SLICE_MS` — bounded below by the per-run join-index cost, above by `MAIN_QUEUE` being serial), then `invalidateMediaCaches()`, then re-enqueues while `backfillPending` (not after an `"exhausted"` walk with nothing found; an `"errored"` slice throws so graphile-worker's backoff and `maxAttempts` apply). Its jobKey `tracearr-backfill:<serverId>` is **shared** with `syncWatchHistory`'s enqueue so a Refresh mid-backfill collapses onto it. All resume state is in the DB, so a killed slice just resumes.
- **Re-added items**: `WatchHistory.mediaItem` is a required FK with `onDelete: Cascade`, so deleting an item deletes its plays and a re-add reads as never watched. Once the archive walk is complete, the backfill task runs `recoverHistoryForNewItems`: items created in the last 7 days holding no TRACEARR play from **before** their `createdAt` (a re-added item played again first holds only that newer play), a capped number per run (`DEFAULT_CANDIDATE_LIMIT` 200, `MAX_CANDIDATE_LIMIT` 500), one `rating_key` request each (plus one TMDB→IMDB request, deduped per run, for a non-episode whose key answer holds no play of this server from before `createdAt`; both answers go to the importer), skipping items Tracearr already answered for (`answeredItems`, in memory); it stops at the first host-level failure or 429. A recovered play newer than every stored one holds the forward watermark first (`holdForwardWatermark`, above). Bulk destruction (`/api/media/purge`, disable with `deleteData`) calls `restartTracearrBackfill` (`watch-evidence.ts`: flag false, cursor = now, forward resume point cleared); `restoreBackup` calls it, inside its transaction, for every mapped server it leaves holding no TRACEARR rows (`restartTracearrBackfillWithoutPlays` — the restored row's mid-walk cursor would otherwise strand the newer stretch). The backfill's end-of-slice state write is compare-and-set.
- **Status route** (`GET /api/integrations/tracearr/status`): `backfillFraction` measures **time covered, not records** (many fetched plays are never stored because their media is gone): `1` when complete; `null` without `oldestPlayAt`, without rows, or with a non-positive span; otherwise `clamp01((newestImported − reached) / (newestImported − oldestPlayAt))`, `reached` = `tracearrBackfillCursorAt` ?? `oldestImported`. **`null` (indeterminate bar) and `0` are different states.** `activeImport` (`{ pass, startedAt, pages, imported, oldestReached }` or `null`) comes from the in-process registry `src/lib/sync/tracearr-import-activity.ts` — entries per run, addressed by the handle `beginTracearrImport` returns (never by server id), pinned to `globalThis`. Settings renders one status line per server (`TracearrImportStatusLine` → `TracearrLiveImportLine`).
- Import progress is pushed: `tracearr:import-progress` (`meta.serverId` only) after each page **commits**, throttled 2 s per server (`IMPORT_PROGRESS_THROTTLE_MS`, a per-server map pinned to `globalThis`), plus unthrottled at run start and end. Settings and History refetch the status route; Settings' 30 s `useFallbackPoll` covers a dropped stream while a backfill is owed or any import is live, and History polls every 30 s (plain interval) until no backfill is pending.

Routes: `api/integrations/tracearr/` — also `[id]/servers` (the Tracearr-side server list for the per-server mapping) and `status` (see "Status route" above).

## Tracearr API reference

Tracearr monitors Plex, Jellyfin and Emby from one instance and exposes a read-only public REST API (plus one stream-termination endpoint).

**Source of truth — the OpenAPI spec, published as a GitHub release asset.** Every stable release attaches `openapi-v1.json` and `openapi-v2.json`; `releases/latest/download` tracks the newest stable release. No auth needed:

- v2: `https://github.com/connorgallopo/tracearr/releases/latest/download/openapi-v2.json`
- v1 (legacy — no media identifier, see below): `https://github.com/connorgallopo/tracearr/releases/latest/download/openapi-v1.json`

```bash
V2=https://github.com/connorgallopo/tracearr/releases/latest/download/openapi-v2.json
curl -sL $V2 | jq '.paths | keys'                                  # list endpoints
curl -sL $V2 | jq '.paths."/api/v2/public/history".get'            # one endpoint (params, responses)
curl -sL $V2 | jq '.components.schemas.HistoryRecord'              # a response schema
curl -sL $V2 | jq '.components.securitySchemes'                    # auth
```

Other sources: **docs.tracearr.com/api** renders the same two assets (browser only). A running instance serves its own build's spec at **`GET /api/v2/public/docs`** (bearer token). The route source (`apps/server/src/routes/publicV2/*.ts` + `publicV2.openapi.ts` in `connorgallopo/Tracearr`) is the last resort.

- **Auth**: `Authorization: Bearer trr_pub_<token>` (generated in Tracearr's Settings > Data & API > API; the v1 spec still says Settings > General).
- **Paths**: `/api/v1/public/*` and `/api/v2/public/*`; an instance may sit under a base path (`/tracearr/api/v2/...`), so never hardcode the root.
- **Rate limit**: per key, a per-minute budget every v2 route shares (240 by default, configurable in Tracearr) — handle 429 (`Retry-After`) and back off. Fastify backend: failures are real HTTP status codes.
- **Use v2 for anything that joins to a `MediaItem`.** v1's `SessionHistory` carries only title strings. v2's `HistoryRecord` carries `rating_key`, `parent_rating_key`, `grandparent_rating_key`, `media_id`, `show_media_id`, `imdb_id`, `tmdb_id`, `tvdb_id`, `library_id`, `server_id`, `server_type`, plus `state`, `percent_complete`, `progress_ms`/`duration_ms`, `is_transcode`, `video_decision`, `audio_decision`.
- **Pagination**: v1 `page`/`pageSize`; v2 keyset — an opaque `cursor` (pass back `meta.nextCursor`; a chain never splits across pages), `pageSize` default 25, max 100 (`HistoryResponse` + `CursorMeta`), newest first, no total.
- **v2 `/history` filters**: `user_id`, `server_id`, `media_id`, `rating_key` (a single string, not a list), `imdb_id`, `tmdb_id`, `tvdb_id`, `media_type` (`movie|episode|track|live|photo|trailer|unknown`; trailers are left out unless asked for), `watched`, `since`, `until`.
- **Other v2 routes** (all GET): `/media/{ref}`, `/media/{ref}/children`, `/media/{ref}/stats`, `/media/{ref}/watchers`, `/media/{ref}/history`, `/users`, `/users/{id}`, `/users/{id}/history`, `/users/{id}/stats`, `/recently-added`, `/libraries`, `/watched-media`, `/streams`, `/servers`, `/violations`, `/violations/{id}`, `/events` (SSE), `/docs`. The stream-termination endpoint is v1 (`POST /api/v1/public/streams/{id}/terminate`).
