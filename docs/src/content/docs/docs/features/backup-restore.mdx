Librariarr includes a full backup and restore system that can run on a schedule or be triggered manually.

## Backup Types

### Config-Only (Default)

Backs up your configuration, servers, rules, integrations, and settings. Excludes tables that are repopulated by syncing or lifecycle processing:

- Media items
- External IDs
- Media streams
- Sync jobs
- Rule matches
- Lifecycle actions
- Lifecycle exceptions
- Watch history
- Log entries

**Use case**: Routine backups. After restoring, run a full sync to repopulate media data.

### Full Backup

Backs up everything, including all media metadata.

**Use case**: Migrating to a new instance without wanting to re-sync, or when sync would take a very long time for large libraries.

Enable full backups by checking **Include media data** when creating a manual backup.

:::caution[Restoring clears watch history]
A restore replaces the whole database, and a **config-only** backup (the default) contains no watch history — so restoring one leaves every server with none. Your media returns on the next sync; your play history returns when the next watch-history sync refills it, which for a [Tracearr](/docs/integrations/tracearr/)-linked server means re-walking the archive.

In between, items come back with no record of ever being played. Librariarr handles this rather than letting it arm your rules: every restored server is held, which **pauses lifecycle rules that read play activity** — Watched By User, Play Count, Last Played and the series aggregates — until a **full** sync of it (the scheduled sync, or **Sync** under **Settings → Servers** — syncing only some of its libraries does not count), because a watch-history refresh that runs before then cannot attach plays to media that is not back yet. That includes a server whose media came back with a full backup: whatever was added after the backup was taken returns only with that sync. A server restored without its media waits for the full sync that brings every library back; one whose media came back is released by its next full sync, whatever that sync can list. That sync then refills the history and lifts the pause — for a Tracearr-linked server it starts a re-walk of the archive (every restore re-walks it, since even a full backup's imported plays stop where the backup was taken), and the pause lifts when the walk finishes.

A full backup also brings back the lifecycle matches and pending actions it held, and they are as old as the backup: an item watched since it was taken may still hold a match. So the actions of every rule set that reads play activity stay held after that sync too, until detection has evaluated the rule set again — the next scheduled detection run, or **Re-evaluate All** on the Lifecycle → Matches page — and an item watched in the meantime drops out first.

Take a **full** backup (tick *Include media data*) if you want history to come back with the restore.
:::


## Encryption

Backups can be encrypted with a passphrase for security.

- Minimum passphrase length: 8 characters
- Uses strong encryption (AES-256-GCM) with brute-force-resistant key derivation

Set the encryption password in **Settings → General → Backup & Restore**. While no password is set, the Create Backup panel shows a warning and every backup written (manual or scheduled) is logged as unencrypted in System Logs.

<Aside type="danger">
  If you lose the encryption passphrase, encrypted backups **cannot be recovered**. There is no passphrase reset or recovery mechanism. Store your passphrase securely.
</Aside>

<Aside type="caution">
  Backups contain **plaintext secrets** — Plex tokens, Sonarr/Radarr/Lidarr/Seerr API keys, the OIDC client secret, and the saved backup encryption password itself. Encrypted backups are strongly recommended whenever the file may leave the host or be stored on shared media.
</Aside>

### What's included

Configuration backups capture every column of the configuration tables, including:

- **User accounts** — usernames, hashed passwords, Plex IDs/tokens, and SSO linkage (`ssoSubject`, `ssoProvider`, `ssoEnabled`)
- **App settings** — schedules, notifications, theme, and the full SSO configuration (mode, OIDC issuer/client ID/client secret/scopes/username claim, forward-auth header names, master `ssoEnabled` toggle)
- **Media servers, libraries, and integrations** (Sonarr, Radarr, Lidarr, Seerr)
- **Lifecycle rule sets and the Plex collections they feed, blackout schedules, preroll presets and schedules, saved queries**
- **TRaSH Guide Sync assignments** (which custom formats, quality profiles, sizes and naming Librariarr manages on each Sonarr/Radarr instance)

Backups made before collections and TRaSH assignments were included still restore: rule sets that were assigned to a collection come back without one (reassign it in the rule editor), and TRaSH assignments need to be made again.

**API keys are never included** — not even their hashes — and restoring a backup deletes every existing API key, so a key you deleted can never be brought back by restoring an older backup. After a restore, create new keys under **Settings → Authentication → API Keys** for the applications that use the [public API](/docs/advanced/api/).

After restoring, SSO is restored exactly as configured at backup time. If the restored backup has SSO enabled but you cannot reach the IdP from the new environment, use the [`SSO_DISABLE_OVERRIDE`](/docs/advanced/sso/#recovery--locked-out-of-sso) env var to recover access.

## Scheduling

Configure automatic backups in **Settings → General**:

| Schedule | Frequency |
|----------|-----------|
| Manual | No automatic backups |
| Every 6 hours | 4 times per day |
| Every 12 hours | Twice per day |
| Daily (default) | Once per day |
| Weekly | Once per week |

### Retention

Set how many backups to keep. Older backups are automatically deleted when the limit is reached. Default: **7** backups.

Scheduled backups are always **config-only** and use the saved encryption password (if set).

## Creating a Manual Backup

<Aside>
  Creating, downloading and restoring a backup need a sign-in from the last 15 minutes. If it has been longer, Librariarr asks you to confirm it's you — with your password, or by signing in again with Plex or SSO in a pop-up — and then carries on, without signing you out. A backup holds your Plex token, and a Plex token is enough to sign in to Librariarr on its own, so a browser session alone must not be able to take a copy. Scheduled backups are not affected.
</Aside>

<Steps>

1. Go to **Settings → General → Backup & Restore**
2. Optionally check **Include media data** for a full backup
3. Click **Create Backup**
4. The backup is created and appears in the **Available Backups** list

</Steps>

## Restoring a Backup

### From Settings (While Logged In)

<Steps>

1. Go to **Settings → General → Available Backups**
2. Find the backup you want to restore
3. Click **Restore**
4. If encrypted, enter the passphrase
5. Confirm the restore — this replaces **all current data**
6. Monitor progress as each table is restored
7. After completion, you are automatically logged out

</Steps>

### From Login Page (No Account)

If no account exists (fresh install or after data loss):

<Steps>

1. Navigate to the login page
2. Backups from `/config/backups/` are automatically listed
3. Select a backup to restore
4. Enter passphrase if encrypted
5. After restore, log in with your restored credentials

</Steps>

<Aside>
  After restoring a backup, trigger a full sync from **Settings → Servers**: it repopulates the media metadata a config-only backup leaves out, and it is what lifts the pause on lifecycle rules that read play activity. After a full backup's restore, the actions it brought back for those rules then wait for detection to evaluate them again: run **Re-evaluate All** on the Lifecycle → Matches page, or let the scheduled detection run do it.
</Aside>

## Restore Process

The restore process:

<Steps>

1. Clears all existing data from the database
2. Restores data table by table (progress is shown in the UI)
3. On completion, logs you out and redirects to the login page

</Steps>

## Storage

| Path | Description |
|------|-------------|
| `/config/backups/` | Default backup directory |
| `BACKUP_DIR` env var | Override the default backup directory |

Backup files follow the naming pattern: `librariarr-backup-{timestamp}.json.gz[.enc]`

Each backup file is written readable and writable by its owner only (mode `600`), the user the container runs as (`PUID`), because it holds your integrations' credentials. To copy backups off the host as another user, read them as root or as that user. Downloads from Settings are sent with `Cache-Control: no-store`, so no browser or proxy cache keeps a copy.

## Managing Backups

From the **Available Backups** section:

- **Download** — Save a backup file locally (needs a recent sign-in)
- **Restore** — Restore this backup (replaces all data; needs a recent sign-in)
- **Delete** — Remove a backup file

## Limitations

- Restoring replaces **all** data — there is no selective/partial restore
- Encrypted backups require the exact passphrase used at creation time
- The restore process logs out all sessions — plan accordingly
- Restoring deletes every API key; applications using the public API need new keys
- Full backups can be large for libraries with tens of thousands of items
