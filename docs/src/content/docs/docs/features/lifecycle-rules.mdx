The lifecycle rule engine lets you define conditions to automatically identify and act on media in your library. It uses a flexible rule group structure with AND/OR logic.

## Concepts

### Rule Sets

A **rule set** is a named collection of rules and actions. Each rule set targets a specific media type (movies, series, or music).

### Rule Groups

Rules are organized into **groups**. Each condition (and each nested sub-group) connects to the one above it with **AND** or **OR**:

- **AND**: must match together with everything above it
- **OR**: matches if either side does

When a group uses a single connector throughout, this reads exactly as you'd expect — all conditions must match (AND) or any condition may match (OR). When AND and OR are **mixed**, conditions combine **top to bottom**, each connector applying to the combined result of everything above it — so `A OR B AND C` means `(A OR B) AND C`. The builder shows a hint whenever this applies, and the **Logic Preview** panel beside the builder always spells out the exact grouping with parentheses (hovering a condition highlights its line in the preview).

Groups can be **nested** to make grouping explicit — a sub-group is evaluated on its own first, then joins its parent as a single result.

### Rules

Each individual rule consists of:

1. **Field** — what property to evaluate (e.g., `playCount`, `resolution`, `addedAt`)
2. **Operator** — how to compare (e.g., `equals`, `greaterThan`, `before`)
3. **Value** — the target value

Negation is part of the operator choice: alongside each comparison the picker offers its inverse — `Not Equals`, `Not Contains`, `Not Greater Than`, `Not Between`, and so on.

**Whole groups can be negated too.** Every group has a **NOT** toggle that inverts its entire result — for example `NOT (watched by Alice OR watched by Bob)` matches items watched by neither. The Logic Preview shows the negation in place, and items the group would have matched are excluded instead. (Stream query groups negate through their quantifier rather than a NOT toggle.)

### Stream query groups

A **Stream Query** group tests an item's individual audio, video or subtitle tracks instead of the item's summary fields, so every condition inside it is checked against the **same** track — "an English audio track that is also Dolby Atmos", not "an English track and, separately, an Atmos one". The group reads `<quantifier> <stream type> stream where …`:

| Quantifier | Matches an item when… |
|---|---|
| **ANY** | at least one track of that type meets every condition in the group |
| **NO** | no track of that type meets them (an item with no track of that type matches) |
| **ALL** | it has at least one track of that type, and every one of them meets the conditions |

Each stream type offers only the fields its tracks carry:

| Label | Field | Stream types |
|-|-|-|

| Bitrate (kbps) | `sqBitrate` | audio, video |
| Is Default Track | `sqIsDefault` | audio, video, subtitle |
| Display Title | `sqDisplayTitle` | audio, video, subtitle |
| Extended Display Title | `sqExtDisplayTitle` | audio, video, subtitle |
| Channels | `sqChannels` | audio |
| Sample Rate (Hz) | `sqSamplingRate` | audio |
| Channel Layout | `sqAudioLayout` | audio |
| Audio Profile | `sqAudioProfile` | audio |
| Bit Depth | `sqBitDepth` | video |
| Width | `sqWidth` | video |
| Height | `sqHeight` | video |
| Frame Rate | `sqFrameRate` | video |

In rule JSON a stream query group is a group with a `streamQuery` object — `{ "streamType": "audio", "quantifier": "any" }` (`any`, `none` or `all`) — whose conditions use the fields above. Changing a group's stream type clears its conditions, since the fields differ.

## Limiting how much one run can delete

By default there is no limit. Librariarr is built to run unattended, and if your rules
legitimately select thousands of items, it deletes thousands of items — that is the point
of the tool, not a bug to guard against.

You can opt into a ceiling under **Settings → General → Delete without asking, up to N
items per run**. A run that would delete more than N is **held**: nothing is deleted, the
actions stay on the [Pending](/docs/features/lifecycle-rules/) page, and you execute them
from there once you have looked at them. That review step is the approval — there is no
separate queue to manage.

What it is for is worth being precise about. It is **not** a safety net for a rule you
wrote wrong; a rule that selects 40 items you did not mean will happily delete 40 items
under a limit of 50. It bounds the other case — where something *upstream* of the rule is
wrong and the match set is far larger than anything you intended. Librariarr already
refuses to evaluate rules whose evidence is missing (unavailable Arr metadata, unestablished
play history), but those guards each cover a hazard someone found. A ceiling covers the
ones nobody has found yet.

Details worth knowing:

- **Deletions only.** Unmonitor, tag and search actions never count toward it and are never held.
- **Per run, across every rule set** — one number for the whole execution pass.
- **Counted after the safety checks, not before.** The figure is what the run would actually
  delete, so actions about to be cancelled anyway — the item stopped matching, it (or a
  sibling) is on the exception list, the item's identity changed since it was scheduled —
  are not counted, and they are still cleaned up even on a run the ceiling holds.
- **All-or-nothing.** Exceeding the limit holds the entire batch rather than deleting up to
  the limit. Acting on an arbitrary slice of a match set you already have reason to distrust
  is not safer.
- **It applies to manual bulk actions too** — **Execute** and **Execute All** on the Pending page and the
  [Query page's actions](/docs/features/query/#the-deletion-limit) — not just scheduled runs.
- If you have a [Discord webhook](/docs/features/notifications/) configured, a held run
  notifies you, so it cannot fail silently.

Use the field name wherever a rule is written as data: the `field` of a condition in an exported or imported rule set (see the [Rule Set Library](/docs/guides/rule-set-library/)), and in the JSON sent to the rule set and query routes.

:::note[Missing *arr data is fail-closed]
If an item isn't in the linked *arr instance, or a specific field has no value (for example a movie with no downloaded file has no quality name, quality-cutoff, or size), **no comparison operator matches it** — including negative operators like *Not Equals* / *Not Contains* and the *NOT* toggle. This is deliberate so lifecycle rules never delete an item on the strength of absent *arr data. To target items with missing data, use the *Is Empty* (`isNull`) operator, or the `foundInArr` field.
:::

:::caution[*arr criteria need at least one enabled instance]
If you disable or delete your only Radarr, Sonarr, or Lidarr instance, rule sets using that family's fields are **skipped entirely** by detection, with a warning in System Logs, and previews return an error. This is deliberate: without an instance to check against, `foundInArr = false` would be true for your whole library. Re-add the instance and the rule set resumes on the next detection run.

When a rule set's action is linked to an *arr instance, its *arr criteria are read from **that instance only** — the same one its action runs against. With a 1080p and a 4K Radarr, a rule set acting on the 4K instance sees the 4K copy's tags, monitored state and quality profile, never the 1080p copy's. If that instance is disabled, the rule set is skipped in the same way, even while another instance of the family is enabled. The editor requires an instance for a rule set that uses *arr fields (an **"… instance required"** warning disables Preview, Test Media and Save until you pick one). A rule set saved without one, such as an older one, reads every enabled instance; a title on more than one of them takes the record from the instance that was added first. Changing the *arr instance of a rule set that uses *arr criteria clears its matches and cancels its pending actions, since they were judged on the old instance; the editor asks how to handle matches as it does for a rule change.
:::

### Seerr Fields

These fields require a configured [Seerr](/docs/integrations/seerr/) integration.

| Label | Field | Description |
|-|-------|-------------|
| Has Request | `seerrRequested` | Whether requested in Seerr |
| Request Date | `seerrRequestDate` | When the most recent request was made |
| Request Count | `seerrRequestCount` | Number of requests |
| Requested By | `seerrRequestedBy` | Who requested it |
| Approval Date | `seerrApprovalDate` | When the most recent request was approved (including requests Seerr has since marked Completed or Failed) |
| Decline Date | `seerrDeclineDate` | When the most recent request was declined |

An item with no such date (never requested, never approved, never declined) fails every date comparison except **Not Equals**, exactly like the library's own date fields, and **Not** then applies as usual — so NOT (Request Date in the last 90 days) includes titles nobody ever requested, while NOT (Request Date not equal to a date) does not. Use **Is Empty** / **Is Not Empty** to target them directly. If Seerr's request list can't be read in full, rule sets using Seerr fields are skipped for that run rather than evaluated against a partial list.

:::caution[Seerr criteria need a connected Seerr instance]
With no Seerr instance connected — after **importing** a rule set, say — the rule builder shows a **"Seerr instance required"** warning and disables Preview, Test Media, and Save until you connect one under Settings → Integrations. Detection skips such rule sets too, for the same reason as *arr fields above.

Seerr fields work on **movie and series** rule sets only; Seerr doesn't manage music requests, so music rule sets reject them at save time. A music rule set that somehow already carries Seerr criteria is disarmed — its matches are cleared and its pending actions cancelled.
:::

## Operators

| Operator | Label | Applicable Types | Description |
|----------|-------|-----------------|-------------|
| `equals` | Equals (dates: Is On) | text, number, date, boolean | Exact match |
| `notEquals` | Not Equals (dates: Is Not On) | text, number, date, boolean | Not an exact match |
| `greaterThan` | Greater Than | number | Greater than value |
| `greaterThanOrEqual` | `>=` | number | Greater than or equal |
| `lessThan` | Less Than | number | Less than value |
| `lessThanOrEqual` | `<=` | number | Less than or equal |
| `contains` | Contains | text | For free-text fields (e.g. title, path): substring match (case-insensitive). For enumerable fields (e.g. quality profile, tag, codec) the operator presents a multi-select and matches if the item's value equals any selected value (list membership, not substring). |
| `notContains` | Not Contains | text | Inverse of `contains` — same free-text vs enumerable distinction. |
| `matchesWildcard` | Matches Wildcard | text | Wildcard match (`*` = any characters, `?` = single character) |
| `notMatchesWildcard` | Not Matches Wildcard | text | Does not match wildcard pattern |
| `before` | Is Before | date | Before a specific date |
| `after` | Is After | date | After a specific date |
| `inLastDays` | In Last X Days | date | Within the last N days |
| `notInLastDays` | More Than X Days Ago | date | More than N days ago |
| `between` | Between | number, date | Within an inclusive range |
| `isNull` | Is Empty | text, number, date (and the booleans *arr may leave unset: `arrQualityCutoffMet`, `arrEnded`, `arrHasUnaired`) | The item has no value for this field (takes no value of its own) |
| `isNotNull` | Is Not Empty | same as Is Empty | The item has some value for this field (takes no value of its own) |

Boolean fields (`isWatchlisted`, `foundInArr`, `hasPendingAction` and so on) take *Equals* / *Not Equals* `true` or `false`.

All text comparisons are case-insensitive, including genres, labels and
countries. Servers do not agree on casing — one may report `Sci-Fi` where
another reports `sci-fi`, and the dropdown lists both — so a rule written
against either spelling matches copies on every server.

### What "Is Empty" means per field

*Is Empty* / *Is Not Empty* take no value; what counts as "empty" depends on the
field's shape:

| Field shape | Examples | *Is Empty* matches |
|-------------|----------|--------------------|
| Nullable column | `studio`, `rating`, `lastPlayedAt`, `arrQualityName`, `arrEnded` | The value is missing |
| List | `genre`, `labels`, `country`, `arrTag`, `seerrRequestedBy`, `watchedByUser`, `matchedByRuleSet` | The list has no entries — e.g. an item that is in *arr but carries no tags |
| Always-present text | `title`, `arrQualityProfile` | The value is the empty string |

Fields whose value is always present and has no meaningful "empty" reading —
`foundInArr`, `arrMonitored`, `seerrRequested`, `seerrRequestCount`,
`playCount`, `isWatchlisted`, `serverCount`, `hasPendingAction` — don't offer the two operators at all, because
*Is Not Empty* on them would just match everything.

:::note[List fields ask about membership]
On a list field, every operator compares case-insensitively, and *Equals* /
*Contains* ask whether a value is **in** the list — not whether it appears
inside one: `Tag Contains "kee"` does not match the tag `Keep`, but
`Tag Matches Wildcard "kee*"` does.

`arrTag Is Empty` means "in *arr, but carries no tags". An item that isn't in
*arr at all doesn't match it — use `foundInArr` for that question.
:::

:::note[Audio and subtitle language are fail-closed]
An item with no **known** language for a track type — no track at all, or only
tracks the server reports as `Unknown` — matches **no** language rule, positive
or negative. `Subtitle Language Is Not English` finds items that *have* a
subtitle track in another language; for items with no subtitles at all, use
`Subtitle Language Is Empty`. Wrapping the rule (or its group) in **NOT** does
not change this: `NOT (Audio Language Is English)` still skips items with no
audio track, rather than sweeping them in.

Track **codec** fields have no such placeholder, so they read plainly: an item
with no audio track does match `Stream Audio Codec Is Not AAC`.
:::

## Building Rules

### Using the Rule Builder

1. **Create a Rule Set**: Give it a name and select the target media type
2. **Add rules**: Select a field, operator, and value
3. **Group rules**: Use AND/OR groups to combine conditions
4. **Nest groups**: Create sub-groups for complex logic
5. **Toggle rules**: Enable/disable individual rules or groups without deleting them
6. **Negate**: Pick a "Not …" operator to invert a condition, or flip a group's NOT toggle to invert the whole group
7. **Reorder**: Drag rules to change their position within a group

### Example: Identify Old, Unwatched Movies

Create a rule set with an AND group containing:

- `playCount` equals `0` — Never watched
- `addedAt` before `2023-01-01` — Added over a year ago
- `resolution` notEquals `4K` — Not 4K quality

### Example: Find Duplicate Quality

Create a rule set with an OR group:

- `resolution` equals `480P`
- `resolution` equals `SD`
- `videoCodec` equals `mpeg2video`

### Example: Watched Only By Departed Household Members

Create a rule set with an AND group:

- `watchedByUser` contains `alice|bob` — Only watched by people no longer in the household
- `watchedByUser` notContains `carol|dave` — Never watched by current household members
- `addedAt` notInLastDays `180` — Been in the library for at least 6 months

The `watchedByUser` field reads from the per-user play history synced from Plex / Jellyfin / Emby. "Watched by" means **any counted play by that user**: every play the media server's own history records, and, for history imported from [Tracearr](/docs/integrations/tracearr/), only plays that reached Tracearr's completion threshold. The dropdown is populated with usernames that have at least one counted play on your connected servers — a user whose only [Tracearr](/docs/integrations/tracearr/) plays stopped short of Tracearr's completion threshold is not offered, since no rule could match them.

### Switching between rule sets

Saved rule sets are always within reach of the editor, so switching never means scrolling back to the top of a long rule set:

- **Wide screens with a mouse or trackpad**: a slim strip beside the editor shows each rule set as a coloured monogram (the one being edited is outlined, an amber dot marks an armed action, a faded one is disabled). It stays in place while the editor scrolls. Hover over it — or tab into it — and it opens over the editor with each rule set's name, its feature chips, an on/off switch and a delete button; move away (or press Esc) and it folds back. The pin button at its top keeps it open beside the editor instead.
- **Phones, tablets and narrower windows**: a bar pinned to the top of the editor names the rule set being edited (**Rule set 3 of 12**). The arrows step to the previous or next rule set, and tapping the name opens the full list as a sheet.

With six or more rule sets the list adds a filter box that narrows it by name. Switching away from a rule set with unsaved edits asks before discarding them, and **New Rule Set** asks the same.

### Building rules on the Query page

The [Query Builder](/docs/features/query/) at `/library/query` uses this same builder and engine to search your library on demand. A query you'd like enforced on a schedule can be turned into a rule set with **Convert to Lifecycle Rule** — see [Converting a query into a rule set](/docs/features/query/#converting-a-query-into-a-rule-set). The Query page can also run an action on its results straight away, without a rule set and without the action delay — see [Running actions on results](/docs/features/query/#running-actions-on-results).

### Importing and Exporting Rule Sets

**Export**, beside **Save** in the rule editor, shows the rule set as JSON to copy: its rules and groups, the action and its options, the collection settings, the Discord toggles and **Sticky matches**. **Import** takes that JSON back — on the tab matching the rule set's `type` — and fills the editor with it as a new, unsaved rule set.

Two things are deliberately left out of an export because they belong to one install: the *arr instance (and, for **Change Quality Profile**, the quality profile, whose id is specific to that instance) and the servers the rule set targets. After an import you pick the **Media Servers** and the *arr server at the top of the editor — an import targets no server, and **Preview** and **Save** wait until it does. Collection settings import as **+ Create new collection…** with the exported name; if a collection of that name already exists for the library type, saving is refused as a duplicate, so pick the existing one in the **Collection** dropdown instead.

The [Rule Set Library](/docs/guides/rule-set-library/) has ready-made rule sets in this format.

## Previewing Matches

Before executing any actions, use the **Preview** feature to see which media items match your rules:

- Shows a count of matching items, in a card or table view
- On an existing rule set, marks each item as **new**, **retained** or **removed** compared with its current matches
- Runs when you click **Preview** (and **Test Media** checks one item of your choice against the rules)
- Shows a live progress bar through each phase (fetching *arr/Seerr metadata, evaluating rules, computing matched criteria) so large libraries don't just spin
- Reuses the *arr and Seerr data it fetched for 45 seconds, so **Preview**, **Test Media** and the **Match Changes Preview** of **Save and re-detect**, pressed one after another, share one read of your *arr and Seerr libraries instead of each reading them again. A change made in Sonarr, Radarr, Lidarr or Seerr (a tag added there, say) can therefore take up to 45 seconds to show in a preview. Adding, editing or removing an *arr or Seerr instance in Librariarr discards the kept data at once, and running actions discards the *arr data. Detection and the actions themselves never use it: they always read fresh data.
- **Test Media** asks each *arr instance for the one item being tested rather than its whole library, unless a preview has just fetched the library anyway
- Radarr's **Custom Format Score** is fetched only for a rule set that uses it, since it is the slowest part of reading Radarr (one request per 100 movies)

Preview is **refused** whenever the rules can't be evaluated faithfully, and the reason is shown as an error notification rather than an empty or stale result list. The same guard that pauses detection applies here, so a preview never shows matches that detection would refuse to produce:

- *arr criteria with no enabled Sonarr/Radarr/Lidarr instance, or Seerr criteria with no enabled Seerr instance (Seerr criteria on a music rule set are refused permanently).
- Criteria that read play activity — *Watched By User*, *Play Count*, *Last Played*, and the series rollups built on them — while any targeted server's play history isn't established yet: it has never synced, was recently cleared, or a [Tracearr](/docs/integrations/tracearr/) history import is still backfilling. Until the history is known, every item looks never-watched, so *Play Count = 0* or *not played in N months* would match the entire library. The warning names the server and which of those applies: a server that is **still importing** clears itself when the import finishes (Settings → Media Servers shows its progress), while one where **no sync has established what was played** clears on the next successful watch-history sync — run one from **Library → History → Refresh**.

The last case also shows a **"Play history not established yet"** warning in the rule editor, naming the servers involved, so you can see a rule set is paused without having to run anything. It clears itself when the import finishes — no reload needed. The same warning pattern already covers a missing *arr or Seerr instance.

Saving with **Save and re-detect** (then **Confirm and Save**) reports the same thing: if detection refuses the rule set, you stay on the editor with the reason rather than being sent to Matches, where the previous run's matches would otherwise look like the new result.

**Re-evaluate** and **Re-evaluate All** on the Matches page report it too. A refused rule set keeps the matches it already had — detection preserves them deliberately — so its row is left as it was and a notification names the rule set and the reason. It is not shown as having zero matches; that would be the opposite of what happened.

## Actions

Actions determine what happens to matched media. Configure them in the action section below the rule builder, which opens once **Enable lifecycle action** is switched on.

### Available Actions

Every library type offers the same eight actions, against Radarr (movies), Sonarr (series) or Lidarr (music):

| Action | Description |
|--------|-------------|
| **Do Nothing** | Track matches without taking action (no *arr server needed unless it manages tags) |
| **Delete from Radarr / Sonarr / Lidarr** | Remove the whole movie, series or artist from the *arr app **and delete its files**. Optionally adds an import list exclusion so lists don't add it back |
| **Unmonitor & Delete Files** | Unmonitor, then delete the matched files |
| **Monitor & Delete Files** | Delete the matched files and keep (or set) them monitored, so the *arr app grabs them again |
| **Delete Files Only** | Delete the matched files without changing monitoring |
| **Unmonitor Only** | Stop monitoring in the *arr app; nothing is deleted |
| **Change Quality Profile** | Switch the *arr item to a different quality profile |
| **Search for New Copy** | Trigger an *arr search for a new copy of the item |

The three file-delete actions can **Search for new copy after file deletion**.

**Manage Tags** adds or removes *arr tags alongside the action, including **Do Nothing**. It is unavailable only with **Delete from …**, which removes the *arr record and its tags with it; the file-only deletes keep the record, so tags apply to them.

### Which files a file delete removes

**Delete Files**, **Unmonitor & Delete Files** and **Monitor & Delete Files** act only on the episodes or tracks that matched, never on the whole series or artist:

- **Sonarr** finds each matched episode by its season and episode number. If your media server's air date for that episode is more than two days from Sonarr's, the two number the show differently (common with absolute-ordered anime), and the episode is skipped. A file that holds several episodes (a double episode) is deleted only when every episode in it matched: otherwise it would also delete an episode that did not match, or one you protected with an exception. **Search after** searches the deleted episodes by id, and **Monitor & Delete Files** also monitors those episodes after the delete, since Sonarr can unmonitor episodes it deletes.
- **Lidarr** finds each matched track by its MusicBrainz track id, then by its disc and track number on the album of the same name, then by its exact title on that album. Anything ambiguous is skipped. A track is never matched to the same song on a different album.
- When none of the matched episodes or tracks can be found in the *arr app, the action is recorded as **failed** rather than completed. The deletion stats count only the files actually deleted.

On a music rule set evaluated per artist, the artist is every track in the library with that artist name, except when every track of that name carries a MusicBrainz artist id and they carry two or more different ones: then each id is its own artist, so two bands called "Nirvana" are evaluated, and deleted, separately. If any track of the name has no id, the name stays one artist, since an untagged track could belong to either and splitting it off would leave its plays out. Before **Delete** removes such an artist, Librariarr asks Lidarr about the other ids under the same name, and refuses if Lidarr says one of them is the same artist (an artist MusicBrainz has merged can appear under its old and new ids).

On a music rule set evaluated per track, an artist-level action (**Delete**, **Unmonitor**, **Change Quality Profile**, **Search**) runs once per artist, covering the artist's matched tracks; file deletes stay per track. Copies of the same track on two servers count as one.

### Change Quality Profile

This action switches a movie, series, or artist to a different quality profile in the linked *arr instance.

- The dropdown is populated live from the selected *arr instance's quality profiles, so it always reflects what the *arr server currently offers.
- Items that are **already on the selected profile are skipped** at execution time. No update call is made and the action completes as a no-op.
- Combining this action with `arrQualityProfile` rule conditions lets you upgrade or downgrade items that don't match your desired profile (for example: "any movie whose current quality profile is `SD` → switch to `HD-1080p`").
- The target profile is required when the action is enabled — Save is disabled until one is selected.
- Toggle **Search for upgrade after profile change** to trigger an immediate *arr search after the profile is updated. The search only fires when the profile actually changed — skipped (no-op) items don't trigger a search.

### Search for New Copy

This action triggers an *arr search for a new copy of the matched movie, series, or artist without changing monitoring, quality profile, or deleting anything. It is a standalone alternative to the **Search after** / **Search for upgrade** toggles that accompany the delete-files and quality-profile actions — use it when all you want is to kick off a fresh search.

### Configuring Actions

Each action links a rule set to an *arr instance:

1. Select the *arr server at the top of the editor (e.g., "My Radarr") — the rule set's *arr criteria are also read from this instance
2. Switch on **Enable lifecycle action** and choose the **Action type**
3. Set the **Delay (days)** — how long after a match the action runs (default 7)
4. Set action-specific options (import list exclusion, target quality profile, search after)
5. Optionally turn on **Manage Tags** to add or remove tags

<Aside type="caution">
  The **Delete** action permanently removes files from your *arr instance and, optionally, from disk. Preview your matches carefully before enabling deletion rules.
</Aside>

<Aside type="note">
  **Repeat scheduling.** A non-destructive action (Unmonitor, Do Nothing, Search for New Copy, Change Quality Profile) leaves the item in your library, so it keeps matching the rule. To avoid re-running the *same* action every cycle, Librariarr won't re-schedule an item that already has a completed action with an **identical configuration**. The comparison covers the whole action — its type, target quality profile, Arr instance, search-after toggle, and tag set — so you can **re-configure a rule's action without recreating the rule** and it will fire again. For example, changing the action from *Search for New Copy* to *Delete from Radarr*, editing the tags an action applies, or pointing a *Change Quality Profile* action at a different profile all schedule the action again, because the new action has never run on that item. Completed **Delete** actions are always eligible to re-schedule, so a deleted title that is re-downloaded (or whose delete failed silently) is acted on again. With series scope off, a completed **Unmonitor Only** or **Search for New Copy** covers only the episodes it acted on: an episode of the same show that matches later (one watched since, under an "unmonitor watched episodes" rule) gets an action of its own, for just the new episodes. On a Series rule set this is tracked per episode, whichever episode the show's match happens to be stored against, so an episode an earlier run covered is never acted on twice. A whole-series action (series scope on) waits while every episode it matches has been covered; when one it never covered starts matching — including after a switch from series scope off — the series action runs once more.
</Aside>

<Aside type="tip">
  See [Deletion Safety](/docs/features/deletion-safety/) for an in-depth, layer-by-layer description of every check that stands between a rule firing and a file being deleted, including the exact source locations and tests that enforce each one.
</Aside>

### Recycle Bin Safety Check

When you configure a destructive action (Delete, Delete Files, Unmonitor & Delete Files, Monitor & Delete Files) for an *arr instance, Librariarr queries that instance for its **Recycle Bin Path** (Settings → Media Management in Sonarr/Radarr/Lidarr).

- If a recycle bin path is set, deleted files are sent to that path before being permanently removed (per the configured cleanup days).
- If no path is set, deletes are immediate and unrecoverable.

When the recycle bin is disabled, Librariarr surfaces the risk in two places:

1. An inline amber warning appears under the **Action type** select.
2. On save, a confirmation modal blocks the save until you check **"I understand that deletes will be permanent and unrecoverable."** The modal includes a deep link to the *arr instance's Media Management settings so you can configure a recycle bin without leaving the page.

The acknowledgement is remembered per *arr instance for the current session — once you accept, you won't be re-prompted for that same instance until the page is reloaded.

## Plex Collections

A rule set can keep a **Plex collection** in sync with its matches — useful for surfacing a "Leaving Soon" shelf to your users. In the rule editor, turn on **Sync matches to a Plex collection**, then pick a collection from the dropdown or choose **Create new collection…**.

Collections are reusable, saved definitions (Plex only). Each one owns its presentation settings:

- **Collection name** — the title shown in Plex.
- **Sort name** *(optional)* — a sort title prefix (e.g., `!001`) to pin the collection to the top of a library.
- **Sort order** — `Alphabetical`, `Release date`, or `Action date`.
- **Display on home screens** / **Display in library recommended** — Plex visibility toggles.

Because the settings live on the collection (not the rule), editing them from any rule applies to **every** rule synced to that collection.

### Merging rules into one collection

Multiple rule sets can target the **same** collection. When they do, the collection's membership is the **union** of all of their matches — Librariarr never lets two rules fight over the same collection. For example, separate "4K movies leaving soon" and "unwatched series leaving soon" rules can both feed a single **Leaving Soon** shelf (within the same library type).

A collection is scoped to one library type (Movies, Series, or Music), since a Plex collection lives inside a single library. To use the same name for both movies and series, create two collections.

### Action-date ordering across rules

With **Sort order: Action date**, items are arranged soonest-scheduled-action first. When several rules feed the collection, the ordering pools the scheduled action dates of **all** of them, so the shelf is correctly interleaved regardless of which rule scheduled each item. (Items without a pending action are placed last.)

### Lifecycle of a collection

- Disabling collection sync on a rule, or deleting the rule, simply detaches it — the collection is re-synced to the remaining rules' matches. The Plex collection is removed only when it has no remaining members.
- The collection Librariarr writes to Plex is never read back in as a library item. Collections are containers, not media, so the [library sync](/docs/features/library/#library-views) skips them — a "Leaving Soon" shelf can't turn into a fake movie in your Movies list, and it can never be matched by a rule.
- Writing the collection does not trigger a library sync. Plex reports the write back as a change to the collection and to every item it tagged, and the [real-time sync](/docs/features/real-time-sync/) recognises that echo as Librariarr's own and ignores it — so a detection run cannot cause an off-schedule full sync of the server.
- To delete a collection definition outright, select it in the dropdown and use the **trash** button. You can delete it from the **last rule that uses it** — doing so removes the collection from that rule and deletes it from Plex. The button is disabled (and the API refuses) only while **other** rules still reference it, so remove it from those first.

### Troubleshooting: matches exist but the collection is empty

The Matches page reads directly from the database, but the Plex collection is populated by a separate sync step that pushes each matched item to Plex by its rating key. If a rule has matches yet the Plex collection shows **0 items**, check **System > Logs** for a line like `Failed to sync collection "…" for library …` — it now names the exact Plex request, HTTP status, and Plex's own error message so you can tell what was rejected. Common causes:

- **The Plex server has no stored machine identifier.** Collections are written using the server's identifier, so a server added without it is skipped (you'll see a `… has no machineId` warning). Re-add the server through the Plex picker to store it.
- **Stale rating keys.** If Plex regenerated its rating keys (a library rebuild, "Optimize database", or removing and re-adding the section), the stored keys no longer resolve and Plex rejects the update. Run a full **sync** of that library so Librariarr relearns the current keys.
- **The matched copy lives on a different (or non-Plex) server.** A movie present on more than one server resolves to whichever copy was matched; only its own server's library can hold it in a Plex collection.

As a safety measure, Librariarr will **not** empty or delete a collection when its rules matched items but none of them resolved to that Plex library — it leaves the collection intact, so a resolution problem never silently wipes a shelf. When the matched items belong to that library but couldn't be resolved to Plex rating keys (stale series titles, for example), a warning is logged; when they simply live in another library or server — normal in multi-library setups — the skip is only visible in debug logs. A collection is only removed when its rules genuinely match nothing.

## How Rules Are Evaluated

Rules are evaluated in two steps:

1. **Step 1 — Local data**: Rules based on your media's own properties (resolution, play count, dates, file size, etc.) are evaluated first using your database — this is fast.

2. **Step 2 — External data**: Rules based on Sonarr, Radarr, Lidarr, or Seerr data (tags, quality profiles, monitored status, requests) require live lookups to those services, so they run after Step 1 narrows down the results.

<Aside>
  Rules using external data (Step 2) are slower because they query your integrations. Use local-data rules to narrow your matches first for best performance.
</Aside>

### Series scope and aggregate fields

For **Series** rule sets, the **Match against entire series** toggle (series scope) controls the unit of evaluation:

- **Series scope on** — the rule is evaluated against the whole show, and an action applies to the entire series. Every episode is a member of the match.
- **Series scope off** — the rule is evaluated against individual episodes, then results are grouped by show. A member-scoped action (such as **Delete Files Only**) acts only on the episodes that matched. **Unmonitor Only** and **Search for New Copy** also act only on the matched episodes: Sonarr unmonitors or searches those episodes and leaves the rest of the show as it is. **Delete from Sonarr**, **Change Quality Profile** and tags are properties of the series in Sonarr and still apply to the whole show.

Some fields are **series-aggregate** fields — `availableEpisodeCount`, `watchedEpisodeCount`, `watchedEpisodePercentage`, `lastEpisodeAiredAt`, `lastEpisodeAddedAt`, `latestEpisodeViewDate`, and `seriesLastPlayedAt` (**Series Last Played**). These describe the show as a whole and can only be computed across every episode, so a rule that references one is always evaluated at the series level — even with Series Scope off.

**Series Last Played** is the most recent play date across *all* episodes (the max of every episode's last-played date). Use it to find shows nobody has touched in a while — e.g. *Series Last Played is not in the last 365 days* matches only series where **every** episode was last played over a year ago. This differs from the per-episode **Last Played** field (which would match a series as long as it has *any* old episode, even if another episode was watched yesterday) and from **Latest Episode View Date** (the play date of the *newest* episode by number — "did they watch the latest episode?").

:::note[Plays by other users count too]
**Play Count**, **Last Played** and **Series Last Played** reflect plays by **every** user on your media server, not just the account Librariarr signs in as. They're kept in step with the same watch history the [History page](/docs/features/library/) shows, so if a rule ever disagrees with History for a title, run a sync.

**Is Watchlisted** is different: a Plex watchlist belongs to *your* Plex account, and Librariarr reads it during a full sync — so watchlist changes appear on the next full sync rather than instantly. Every item in the library is checked against the watchlist on that sync, whether or not its own metadata changed, so removing a title from your watchlist clears the flag just as adding one sets it. If the watchlist cannot be fetched in full (plex.tv unreachable, token expired, or its pages stopping before the total it reports), the stored flags are kept unchanged for that sync and the failure is logged, rather than every item missing from a partial answer being marked as not watchlisted. The watchlist is read in pages, so a watchlist of any size is read whole.
:::

**Matched By Rule Set**, **Has Pending Action** and **Server Count** are read across the whole show in series scope, and across the artist's tracks in artist scope: a show is matched by a rule set if any of its episodes is (every episode a series match covers counts), has a pending action if any episode does (every episode a show or artist action acts on counts as pending, not only the one it is stored against), and takes the highest server count of its episodes. So *NOT Matched By Rule Set = Keep* excludes a show the Keep rule set matched, in either scope, and *Has Pending Action = false* skips every episode another rule set has already scheduled. **Has Pending Action** also counts another server's copy of an item an action is pending on — the copies a merged match lists, and the same title on another server — since every copy is backed by the one *arr record the action acts on; and it never counts the rule set's own actions, so *Has Pending Action = false* does not cancel the action its own rule set scheduled on the previous run.

When Series Scope is **off** and your rule mixes an aggregate field with a per-episode field (for example, *available episode count ≥ 20 **and** resolution = 4K*), the show first has to qualify on the aggregate, and then a member-scoped file delete acts only on the episodes that individually satisfy the per-episode conditions (here, just the 4K episodes) — not every episode of the series. With Series Scope **on**, the same rule deletes the whole series.

### Artist scope

**Music** rule sets have the same switch, **Match against entire artist**. On, the rules are evaluated against each artist's tracks taken together and an action covers the artist. Off (track scope), the rules are evaluated per track, then grouped by artist; file deletes act on the matched tracks only.

### How series actions are named

A series match and its action are always named by the **show**. This holds on the Matches and Pending pages, in the action history, in System Logs and in Discord notifications. It is never named by the episode Librariarr stores the match against. An action that acts on **exactly one episode** is named by the show plus that episode's season and episode number, for example *Breaking Bad S03E10*. That happens with a file delete whose rule matched a single episode, or a Query-page action on one episode. The history keeps that name after the episode has been deleted from your server.

## Scheduling

Lifecycle processing runs on two independent schedules (configured in **Settings → Scheduling**):

- **Detection**: Evaluates rules and identifies matching media
- **Execution**: Performs configured actions on matched media

Both can be run manually via the **Run Now** button at any time.

### Detection: incremental and full

Scheduled detection is **incremental**: it adds new matches, refreshes the ones it keeps, and removes matches whose items no longer satisfy the rules — cancelling their pending actions. **Re-evaluate** (per rule set) and **Re-evaluate All** on the Matches page run a **full re-evaluation** instead, replacing each rule set's matches with exactly what its rules select now.

Turn on **Sticky matches** in a rule set to keep items matched after they stop meeting the rules: incremental runs then only add matches, and only a manual re-evaluation removes them.

### Action delay

When a match is found and the rule set's action is enabled, an action is scheduled **Delay (days)** after detection (0–365, default 7) and appears on the Pending page until it runs. An item that already has a pending action is not scheduled again. When you change the delay, the editor offers to reschedule the actions already pending to the new delay from today.

### Editing a rule set

Changing the rules prompts **Save and re-detect** (shows a **Match Changes Preview** — new, retained and removed — and **Confirm and Save** runs detection for the rule set at once) or **Save only** (the matches stay as they are until the next detection run). Action-only changes save directly and are copied onto the pending actions. Turning off **Enabled** or **Enable lifecycle action** cancels the pending actions.

## Deletion Stats

The **Pending Actions** page displays a running total of data deleted by lifecycle actions — including the total bytes removed and the number of completed actions. This gives you visibility into how much storage the lifecycle system has reclaimed.

- Stats are computed from completed actions that have recorded file sizes
- Click the **reset** button to start counting from zero — historical action records are unaffected
- After a reset, only actions completed after the reset point are included in the totals

## Limitations

- *arr actions require the corresponding integration to be configured and reachable
- Rules using integration data are slower and scale with the number of matches
- File size rules accept input in MB but are stored and compared in bytes
- Wildcard matching uses `*` (any characters) and `?` (single character), not regex
